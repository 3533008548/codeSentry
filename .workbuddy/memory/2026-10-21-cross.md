# 2026-10-21（续三）

## 跨项目验证 · Knowledge Loop（TypeScript 侧）

目标：`D:\develop\agent for obsidian`（23 提交，TypeScript 26,075 行 / 140 文件 / 1,153 符号）

### 关键发现 1：项目自带《项目接手指南.md》= 现成 ground truth

该文档列出 9 个"读懂项目必读"的核心文件，**直接作为评测集**，无需人工标注、无需 git 历史构造。**这是 v0.2 §8 待确认项 #5（clean/holdout 集构造）的一个解法**：任何认真维护的项目都有 README/架构文档/接手指南，天然含"核心文件是什么"的答案。

### 关键发现 2：TS 解析器用 TypeScript 编译器 API，零新增依赖

`ts.createSourceFile` 即可拿到完整 AST + import 表。**ts-morph 的核心价值是类型信息（getType），M0 用不上**。实测 68,618 行/秒（是 Python ast 的 3.1 倍）。v0.2 §4.2 的"轻量抽取"具体化为此，**不是正则**。

### 关键发现 3（最重要）：纯 PageRank 排序在 TS 侧失败

Top10 命中人工标注仅 **2/9**。两个根因：
1. **PageRank 衡量「下游地位」，架构入口是「上游组装者」**。`src/main.ts` import 31 个模块但入度 0，纯 PR 只排第 7
2. **依赖图发现不了「语义关键但引用少」的模块**。`desktop-answer-loop.ts` 是问答心脏但只被 6 文件引用，纯 PR 进不了前 12

### 解法：四信号重要度模型

```
重要度 = 0.25·norm(PR) + 0.15·norm(出度) + 0.25·norm(入度) + 0.35·norm(角色权重)
```

角色信号 = 8 类确定性规则（entry 1.00 / guard 0.95 / contract 0.85 / orchestrator 0.85 / proposal 0.70 / service 0.60 / store 0.60 / infra 0.50 / 无匹配 0.20），不调 LLM、可单测。

**TS 侧效果：Top10 命中 2/9 → 5/9，Top20 4/9 → 7/9**
**Python 侧对照：Top20 命中 4/9 → 5/9**（四信号跨语言可复用，角色语义一致）

### 关键发现 4：两类排除必须分开

- **不解析**：runtime/ papers/ node_modules/ dist/
- **不参与重要度排序**：scripts/ evals/ tools/ tests/

后者是源码但不是产品架构的一部分。Python 侧首次应用时 scripts/evals 霸占 Top10（entry 规则命中其 `__main__` 守卫），排除后 Top20 命中从 1/9 回到 5/9。

### 关键发现 5：Windows 路径分隔符 bug

`f.replace("\\","/").split(os.sep)` 在 Windows 上永远切不开（os.sep 是 `\`）。必须先统一分隔符再 split。**这类只在 Windows 复现的 bug 最容易在交付时炸。**

### 关键发现 6：四信号也不是万能的

`tool_schemas.py`（纯定义文件，29 个工具 schema）纯 PR 第 4 → 四信号第 30（出度为 0）。"契约/定义文件"是第四种架构角色，当前规则只能靠 `contract` 关键词偶然命中。**改进方向：识别"只有常量/类型/接口定义、无函数实现"的形态特征**（TS 侧已有 interface/type/enum 计数信号）。
