# 2026-10-22

## M1 第一步：L2 阅读顺序改为 BFS + 补 import 边

### 三处设计改进（均为实测驱动）

**① 阅读顺序从「入口 + PageRank TopN 拼接」改为「入口 → 契约层 → 沿依赖 BFS 展开」**

理由（实测）：PageRank 对入口/编排类文件无系统性偏好——
research_agent 入口类排名中位 70 vs 全部中位 60，编排类中位 77。
因为 PageRank 衡量"被引用的中心性"，而入口与编排器是"引用别人"的一方。

BFS 而非 DFS：BFS 保证"先读骨架层再深入细节"，符合"先建立全局印象"。

**② 补 import 边（调用图和依赖图是两回事）**

实测：Knowledge Loop 有 5 个核心文件在调用图里**入度出度全为 0**——
`knowledge-repository.ts`（只读接口）、`desktop-api.ts`（类型契约）、
`json-post.ts` / `fetch-api-request.ts`（HTTP 工具）、`preload.ts`（桥接）。
它们只有 import 关系、没有任何函数调用，是调用图里的孤立点。

**import 边只用于阅读顺序与影响面，不进 PageRank** —— 保持"重要度 = 调用结构中心性"语义不变。

**③ 区分主入口与叶子入口**

只有出度 > 0 的入口是阅读起点。实测 `src/preload.ts` / `App.tsx` / `main.tsx`
出度都是 0（渲染层叶子），从它们读起会走进死胡同。

### 实测效果

| | 拼接版 | BFS 版 |
|---|---|---|
| research_agent Top30 | 19/44 (43.2%) | **23/44 (52.3%)** |
| Knowledge Loop Top30 | 7/11 (63.6%) | **9/11 (81.8%)** |

Python 侧前 12 名 12/12 全命中 ground truth。

### 契约层判据（三条同时满足）

1. 向下依赖为 0（自己不依赖别人）
2. 向上依赖 ≥ 2（被多个模块依赖）
3. 含 interface/type/enum 定义且实现型符号不多

**位置必须在细节之前**——契约层是架构骨架（"这个项目有哪些接口"）。
收紧判据（加第 3 条）代价是 Python 侧 24→23，可接受。

### 实现细节

- `codesentry/output/reading_order.py` —— 新模块，含 BFS + 契约层 + 兜底
- `IndexResult` 新增 `dependencies`（正向）/ `dependents`（反向）/ `import_edge_count`
- `SymbolResolver.resolve_import_edges()` —— 相对路径（`../core/x`）按调用方目录求绝对路径
- `tests/test_reading_order.py` —— 8 个单测（42 total）

### 踩坑

- `IndexResult` 是 dataclass 不是 Pydantic，`field()` 不支持 `description` 参数（两次踩）
- TS 相对路径 import 必须按调用方目录解析，绝对路径匹配不到
- 测试数据要满足契约层判据（向上依赖 ≥2），否则测的是兜底分支
