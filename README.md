# CodeSentry

> 本地优先的代码学习与审查工作台。每个项目有独立的浏览器工作空间：与Agent讨论代码、逐步理解设计、对照源码并讨论重构；CLI保留自动化入口。

**当前工作台**由项目文件、Agent 对话和源码预览组成。用对话理解代码和讨论重构，用 CRAP 报告检查 Python 函数的复杂度与覆盖率。左右两栏可独立收起和调宽。项目和文件访问范围按工作空间保存。

产品与数据边界见[工作空间与本地前端方案](docs/CodeSentry_工作空间与本地前端方案_v0.1.md)，技术决策以[修订十八](docs/CodeSentry_技术选型定稿_v0.2.md)为准，任务按[P0–P7执行方案](docs/CodeSentry_分阶段执行方案_v1.0.md)推进。工作空间隔离不代替执行沙箱，静态解析不等于运行或类型验证。

2026-11-04修复：[对话引用与输出诊断](docs/execution/P4_对话输出与引用修复_20261104.md)。模型按本轮片段编号引用，路径/行号由服务端生成；空白、截断、JSON及引用错误分别显示，避免反复遇到同一句笼统提示。零自动重试与项目文件权限继续生效。

**文件访问范围**：提供“完全排除”“仅限本地分析”和“模型候选”，默认遵守`.gitignore`；浏览、索引、worker、CLI及对话取材使用统一策略。候选资格不代表发送授权；DeepSeek配置与项目对话授权分别开启。旧空间先确认范围再恢复内容；改变范围会清理旧分析、对话、项目约束和反馈。详见[权限合同](docs/CodeSentry_工作空间与本地前端方案_v0.1.md#31-文件访问范围)。

新建网页工作空间默认勾选“普通文件默认允许模型取材”，免于逐文件添加候选。敏感文件、Git忽略项及明确的“完全排除/仅限本地”仍然优先；可在设置中关闭并改用候选名单。旧空间沿用原设置，需显式更新；2026-11-02用户已批准的三个项目升级见[默认范围记录](docs/execution/P4_模型默认范围升级_20261102.md)。

## 这是什么

一个代码目录对应一个工作空间，配置、任务、快照和结果各自关联。重复打开同一规范目录复用工作空间，独立副本或worktree分开；源码默认只读，状态不写进被分析项目。

- **理解代码**。在对话中问结构、入口和调用流程，点击引用查看源码。
- **检查复杂度**。在对话中运行 CRAP，查看分数、圈复杂度、覆盖率和补测建议。
- **讨论重构**。在对话中说明目标和约束，让 Agent 根据源码解释改动取舍与验证方式。

原有静态分析和审查命令见下方 CLI 说明。

---

## 为什么先做「理解」

多数代码审查工具假设你**已经熟悉这个项目**。但真正卡住人的往往是"我根本不知道从哪看起"。

CodeSentry 的入口层先解决这个问题：给出一张**带证据的架构地图**（文件、符号、行号），而不是一份泛泛的总结。因为可验证的结论才能建立信任——而信任是审查工具被采用的前提。

## 快速开始

### 本地网页工作台

当前从源码仓库本地构建，尚无安装包。以下为Windows PowerShell运行方式，需要Python 3.11及以上、仓库内的`.venv`虚拟环境及Node.js/npm；若尚无虚拟环境，先在仓库根目录运行`python -m venv .venv`。

在仓库根目录安装依赖并构建网页：

```powershell
.venv/Scripts/python.exe -m pip install -e ".[dev,web]"
cd frontend
npm ci
npm run build
cd ..
```

回到仓库根目录启动：

```powershell
.venv/Scripts/codesentry.exe serve --data-dir .venv/workbench-data --open-browser
```

默认地址为 `http://127.0.0.1:8765`。打开项目并确认文件访问范围后，在中央提问，在右侧查看源码。通过对话的「对话设置 → 打开模型设置」启用 DeepSeek，再确认自动取材授权。CRAP 从对话输入区发起。

示例把工作空间配置、任务和结果保存在CodeSentry自身的`.venv/workbench-data`；状态目录须与被分析项目源码分开。省略`--data-dir`时使用用户本地应用数据目录。可用`--port`更换端口、`--frontend-dir`指定已有构建资源；本地前端开发才需显式配置`--dev-origin`，正常启动不需要。

长期使用DeepSeek时，在CodeSentry根目录的`.env`中填写 `DEEPSEEK_API_KEY=你的密钥`，然后重启服务即可；空模板见[`.env.example`](.env.example)，`.env`已加入Git忽略。也支持启动环境同名变量（优先）或 `serve --env-file "D:/private/codesentry.env"`。默认不会读取被审项目的`.env`，配置密钥也不会自动启用模型或扩大文件范围。页面输入仍是工作空间临时覆盖；清除和显式恢复行为见[配置说明](docs/execution/P4_持久密钥配置.md)。

Windows下希望固定使用本仓库`.env`时，可运行根目录的[`start-workbench.cmd`](start-workbench.cmd)。它仅在本次工作台进程中排除同名环境变量，防止另一把密钥覆盖文件；不更改系统环境变量。现有服务运行时先停止旧服务，再用此脚本启动。HTTP401来源冲突的实测记录见[排查记录](docs/execution/P4_密钥来源冲突排查_20261030.md)。

### 现有CLI

```bash
pip install -e .

# 可选：安装固定版本并校验来源的TS解析工具（需要Node；不安装目标依赖）
python -m codesentry.environment install-typescript

# 未注册项目显式确认本次本地范围；默认仍遵守.gitignore
codesentry doctor /path/to/project --confirm-access

# 理解一个项目（可加--no-cache禁止解析缓存读写）
codesentry onboard /path/to/project --level 2 --confirm-access --exclude "private/" --local-only "internal/"

# 显式重建索引
codesentry index /path/to/project --confirm-access

# 查看索引是否过期
codesentry status /path/to/project --confirm-access

# P3只报告预览；返回3表示预览完成、门禁未评估，不能作为CI通过依据
codesentry scan /path/to/project --preview --max-function-lines 80 --confirm-access --json
```

已在工作台确认范围的项目可直接复用策略；若网页使用示例状态目录，CLI增加`--workspace-data-dir .venv/workbench-data`。`--confirm-access`不能绕过已注册空间的待确认/待清理状态；`--access-policy`可提供项目目录之外的可信JSON，只能额外收紧已有工作空间限制。访问范围排除实际源码/配置时，结果会说明范围受限，CLI可返回1，不能据此宣称完整审查通过。多硬链接文件属于首版不读取范围。

默认缓存/索引按`scopes/<access_fingerprint>/`隔离；缓存落在源码目录内时禁用。显式`--save-to-project`导出的索引名含权限摘要，普通源码读取和模型原文入口会拒绝这些受管产物。旧用户`index.json`及其他已导出副本不自动删除或撤回。

### 审阅覆盖清单

用 `review-plan` 检查获准的文本文件能划入哪些审阅行段。JSON 给出各文件的 SHA-256、规划行段和覆盖缺口，超长行与预算限制单列。清单就绪表示本地取材计划已生成，审阅状态仍为未开始。

```powershell
.\.venv\Scripts\codesentry.exe review-plan 'D:\path\to\project' --confirm-access --json
```

已在本地网页确认范围的项目，可用 `--workspace-data-dir .venv/workbench-data` 复用策略。需要保存 JSON 时，输出路径应放在被审目录之外。

### 批次审阅

在工作台确认模型候选范围并启用 DeepSeek 后，先生成并核对 `review-plan` 的 JSON。用审核过的 `plan_sha256`、要使用的模型和批次数上限发起审阅。

```powershell
.\.venv\Scripts\codesentry.exe review-run 'D:\path\to\project' --workspace-data-dir '.venv/workbench-data' `
  --approve-plan '<核对过的 plan_sha256>' --model deepseek-flash --question '梳理关键流程和待验证的边界' --max-batches 1
```

报告输出 JSON，并区分完成、失败、拦截和待处理行段。可用 `--first-batch 3 --max-batches 1` 单独补跑第 3 批，新旧报告分别保留。`model_scope_complete` 表示当前计划中的模型候选行段均有合格回包，报告仍是模型观察。CLI 使用 CodeSentry 启动环境变量或 `.env` 密钥。

同批中能独立校验的行段会保留。可加 `--retry-requests 1`，额外授权一次请求，只补跑格式、缺项或引用校验失败的行段。默认补跑预算为 0，每批最多补跑一次，`--max-batches` 和 `--retry-requests` 合计最多 100 次。报告的 `attempted_requests` 和 `retries` 分别记录请求尝试数和补跑原因。

把各次 `review-run` 的标准输出分别保存为 JSON，路径放在被审目录之外。然后用 `review-merge` 合并，沿用原来的计划摘要、问题和模型。

```powershell
.\.venv\Scripts\codesentry.exe review-merge 'D:\path\to\project' --workspace-data-dir '.venv/workbench-data' `
  --approve-plan '<核对过的 plan_sha256>' --model deepseek-flash --question '梳理关键流程和待验证的边界' `
  --report 'D:\reports\review-first.json' --report 'D:\reports\review-retry.json'
```

默认在本机合并。完全相同的观察去重，已完成行段可填补旧报告缺口。同一行段的不同完成结果标为 `conflict`。合并要求报告保有本机凭据，并匹配当前源码、工作空间、权限和模型配置。旧版报告需要重新生成后才能合并。

要生成带文件和行号的跨文件结论，可加 `--summary-requests 1`。只有模型候选行段齐全、计划无缺口且无冲突时才发出汇总请求。汇总使用前序模型观察。输入较大时会分组，预算不足会返回 `minimum_requests`，可据此明确批准更高的请求数。覆盖状态与结论质量分别判断，需运行验证的事项保留为未知。

单次汇总可用 `--summary-requests 2` 给校验失败预留一次补跑。分组模式先为各组和最终汇总保留基本请求数，余量用于失败的分组或最终汇总。每个步骤最多补跑一次，已通过校验的分组直接沿用。认证、限流和源码或权限变动会阻止继续发送。

追踪分支或推导整数边界时，可同时指定 `--summary-source-evidence`，明确允许把批次报告已引用行段的源码再次发送给模型。复核会检查当前源码摘要、引用的行号与短引文，并在本地重算模型列出的整数加减项。报告保留引用位置和通过检查的等式。引用和算术校验通过后，仍需判断模型是否选对了可达条件。大输入分组后如果汇总材料超出预算，会标记 `intermediate_size_limit`。

源码复核可为已完整引用的 Python 文件补充静态导入绑定。报告的 `static_call_links` 用行段 ID 和行号标出调用点及函数定义，帮助模型把实参和返回值接回调用方。分组汇总在预算内补入已引用且直接相连的行段。动态回调和实际运行结果仍需相应证据。

### 项目笔记

在带源码引用的回答下点 **记下这点**，手动保存一条源码观察或待验证的判断，范围可选当前话题或本项目。点对话顶部的 **项目笔记** 查看状态或跳到证据。相关源码或选定跟踪的环境声明变化后，笔记会标为过期。笔记留在本机。

### CRAP 维护风险报告

在项目对话点 **CRAP 报告**，或输入 `/crap`，即可运行 Agent 的本地评分工具。可选填工作空间内的覆盖率报告，分数和建议会保存在本话题。报告包含分支与语句覆盖率、未覆盖路径示例、修改建议和源码跳转。对话展示排序靠前的最多 60 项，完整逐函数结果可通过 CLI 的 `--json` 查看。

在模型候选文件的函数行点 **讨论改法**，会打开右侧源码并在输入区准备可编辑的问题。发送时使用当前项目的对话授权，只把该函数的片段和当前问题交给模型。评分与覆盖率留在本地。若文件已修改，先用对应版本的覆盖率重新生成报告。

`codesentry crap` 按函数给出圈复杂度、覆盖率、分数和源码位置，按分数从高到低排列。圈复杂度从 1 起算，计入条件、循环、异常捕获、布尔短路、模式匹配和推导式中的决策。嵌套函数独立计数。分数使用 `CC² × (1 − 覆盖率)³ + CC`，覆盖率取 0 到 1。原始指标采用基本路径覆盖率。这里优先用 coverage.py 的函数级分支覆盖率，未开启分支测量或函数无可测分支时用语句覆盖率。报告标出每个函数的口径。见[原始 CRAP 说明](https://testing.googleblog.com/2011/02/this-code-is-crap.html)。

```powershell
# 只计算圈复杂度
.\.venv\Scripts\codesentry.exe crap . --confirm-access

# 读取已有覆盖率报告，输出逐函数评分
.\.venv\Scripts\codesentry.exe crap . --confirm-access --coverage-json coverage.json --json
```

覆盖率文件应由 coverage.py 7.13.1 或更新版本在相同源码版本上生成。在项目的测试环境收集覆盖率后，从项目根运行 `python -m coverage json -o coverage.json` 导出格式 3 的 JSON，并放在允许读取的项目内路径。匹配依据是文件相对路径、函数限定名和起始行。缺失、无法匹配或无可测项的覆盖率显示 `N/A`，实测 0% 仍参与计算。JSON 报告记录覆盖率文件和源码摘要，导入报告与源码版本的对应关系由提供方保证。见[coverage.py 版本说明](https://coverage.readthedocs.io/en/latest/changes.html#version-7-13-1-2025-12-28)。

`--reference` 可调整参考线，默认为 10，沿用 ub-mode 的参考目标 `<10`。该命令仅报告 `.py` 中的函数和方法。超过参考线用于安排补测或重构，退出码 0 表示报告生成，1 表示扫描不完整，2 表示输入或权限错误。见[ub-mode 的 Crapper 用法](https://github.com/unclebob/ub-mode#companion-tool-repositories)。

### 设计与实施边界

- P4首轮选择DeepSeek，默认关闭且模型范围为空；在工作空间访问设置中指定模型候选，在“模型审查”使用启动配置或临时key、选文件及起止行，核对完整请求后确认发送一次。启动配置只读可信`.env`或环境变量；页面临时key仅存服务内存，所有key不写数据库或API返回；供应商默认缓存提示在确认前展示。3请求/32768token为每workspace每次服务预算，不是金额硬上限；真实模型效果仍待评估。
- P3已实现Finding信任基础：默认unknown/0/未验证；JSON、复制或模型输出不能取得当前上下文资格。门禁使用原始上下文凭据、可信必检清单和完整性检查；当前规则未准入。外来回验只返回警告，原债务基线不自动取得正式豁免。
- P1已实施作用域与保守绑定：符号身份包含完整作用域；启发式猜测须与确定绑定分开，排除在确定调用图及 PageRank 之外。升级时应使旧解析缓存与索引快照失效。
- P3已实现v2身份/完整证据分离并保守保留原文；批准基线保存在项目外，须显式选项、理由及版本校验，随时可撤销，精确匹配也保留原问题。旧`sha1:`不自动继承，格式/注释变化可以使证据失效；当前不执行正式门禁豁免，缓存`content_hash`仍为原SHA-1。
- P@10 是前10项的标注命中比例，Recall@K 是全部标注关键文件的覆盖率。验收脚本应将未知标注、解析不全、空 GT 或不足10项报告为不可验收，并通过退出码体现结果。
- 确定性规则独立于 LLM 过滤、超时和返回内容执行。门禁框架区分通过、阻断、不完整和错误；预览仍不作门禁判定，当前生产门禁因未准入返回不完整。可信策略、规则与已审基线不能由被审改动自行放宽。
- 差异扫描要报告比较基点与范围；云端发送、索引/缓存保存与清理须有明确的数据边界。
- 文档标签仅是代理标注；建立评测集时即隔离训练/开发/封存集，另测候选召回与实际理解效果，不能等到 M6 才处理评测污染。

## 设计要点

以下记录既有设计与早期试验；历史样本结论有明确范围，不能替代当前导航质量或新工作台的独立验收。

### 重要度 = 纯 PageRank，不做加权

曾经尝试「PageRank + 出度 + 入度 + 角色权重」的四信号模型。历史结果因项目而异，现阶段保留纯 PageRank 为基准，不能据此声称它普遍优于其他排序：

| 模型 | Python Top10 命中 / 历史标签总数 | TS Top10 命中 / 历史标签总数 |
|---|---|---|
| **纯 PageRank** | **8/30** | **2/9** |
| 四信号模型 | 5/30 | 4/9 |

原因：角色权重经全局归一化后，同类文件集体霸榜（某项目 `api/` 下 7 个文件全部命中 `contract`，归一化后全部满分，把 Top15 里 9 个位置吃掉）。

**架构角色标签不参与 PageRank 加权**，用于说明入口、守卫、契约等职责。启动角色另行区分为进程入口、界面挂载、桥接上下文、应用装配和待确认候选；启动声明或静态证据支持的角色可影响阅读路线的展示优先级，名称线索只保留候选，均不能当作人工标签或运行成功证明。

> 详细的自我纠错过程见 [技术选型定稿 §4.3.2](docs/CodeSentry_技术选型定稿_v0.2.md)。

### 两张图：调用图 + 依赖图

**它们是两回事。** 一些只含接口、类型或常量的模块可能只有 import 关系，在调用图里是孤立点；依赖图用于补充这类关系。

实测某项目有 5 个核心文件（只读接口、类型契约、HTTP 工具、桥接层）在调用图里入度出度全为 0——只用调用图会全部漏出阅读顺序。

import 边只用于阅读顺序与影响面分析，**不进 PageRank**（保持"重要度 = 调用结构中心性"的语义不变）。

### 阅读顺序：有证据的入口与分支线索优先

只有带启动声明或静态证据的进程入口（`process`）、界面挂载（`mount`）作为距离根，零出度也可以成立。启动声明未覆盖的分支，可从有向不可达的应用装配（`assembly`）或桥接（`bridge`）线索选择展示锚点；它们不会因此变成进程入口，名称候选也不会仅凭文件名获得优先位置。

路线对各分支轮询，并按深度分配优先阅读预算；契约可适量前置，PageRank用于候选内排序。`L0/L1/…`始终是距有证据入口的最短静态依赖距离，展示顺序不改变距离；`·`表示在展开深度内未到达，不能理解为文件缺失。`max_items`只控制优先窗口，完整合格文件清单仍保留。静态依赖距离不代表实际启动或调用顺序。

这一轮修正了角色与层级的表达，质量判断仍须看固定范围的开发对照和独立验收；不能由结构反例或单测通过宣称导航质量提升、人工标签成立或P1达标。详细规则见[技术定稿§4.4与§5.4.1](docs/CodeSentry_技术选型定稿_v0.2.md)。

### 增量缓存：只有 parse 走缓存

| 阶段 | 耗时 | 是否缓存 |
|---|---|---|
| parse | 0.87–1.32 s | ✅ |
| resolve / pagerank / entrypoints / roles | 合计 < 0.2 s | ❌ 每次重算 |

PageRank 也重算是有意的：实测 30,000 节点仅 169 ms，而局部近似的 Top50 重合度只有 11/50。缓存它会引入"索引陈旧"的第二个来源。

**增量结果与全量重建逐项比对**：符号数、边数、PageRank、入口点、调用分类全部一致。

### 缓存不写进被审查项目

默认落 `%LOCALAPPDATA%/codesentry/`。写进项目内会生成 4.7 MB 缓存并污染其 `git status`——**一个"帮你审查代码"的工具，在被审查方留垃圾是减分项**。

显式导出到项目时可用 `--save-to-project`；索引可能包含签名、文档字符串等源码信息，缓存和日志也可能含敏感数据。纳入版本控制、保留期限与清理方式须按当前技术定稿的数据边界审查，不能将缓存目录在项目外等同于没有泄露风险。

## 索引陈旧问题

> 索引是快照，代码改了索引不知道，直到下次重建。

本项目的答案：内容哈希 + 增量重解析，`codesentry status <path>` 显式报告陈旧程度。

P1已在扫描前后核对源文件与配置，变化则标为不完整。已保存的历史结果仍可能与当前代码不同，工作台须显示stale并提示重新分析，不能把旧行号当成当前精确证据。

## 方法论：评测的诚实性

这个项目踩过一次很典型的坑，记录下来以免重犯。

**用主观挑选的少数样本当 ground truth 前，必须先问：这个样本的选择是否与被测机制相关？**

- 相关 → 循环论证，指标虚高
- 未发现相关 → 仍须核查标签质量、样本代表性与评测独立性

**真实案例**：曾用 9 个"角色多样"的文件测「角色识别」机制，得到"四信号 5/9 优于纯 PR 2/9"的结论。换用项目自带文档的**全量**标注清单（30 个文件）重测，结论反转为「纯 PR 8/10 优于四信号 5/10」。

**当前代理测法**：可先用项目自带文档的全量清单，报告去重、未匹配和排除项；文档没提到的文件保持未知。正式验收还须有独立标注、裁决流程和封存集，不能把文档全量清单当作完整真值。

详见 [技术选型定稿 §4.3.2](docs/CodeSentry_技术选型定稿_v0.2.md)。
