# CodeSentry

> 本地优先的代码理解与审查 Agent。确定性 AST 分析 + LLM 语义裁决 + 发布门禁，输出可定位到行号的结论。

**当前状态**：M0–M1 已完成（索引层 + 阅读顺序 + 增量缓存），M2 检查器开发中。

---

## 这是什么

两个场景共用一套索引层：

| 场景 | 命令 | 解决的问题 |
|---|---|---|
| **理解**（优先） | `onboard` | 读懂陌生项目：入口在哪、核心模块是什么、按什么顺序读 |
| **审查** | `scan` | 提交前的问题检出与门禁阻断（M2 起） |

一句话：**它先帮你读懂，再帮你把关。**

---

## 为什么先做「理解」

多数代码审查工具假设你**已经熟悉这个项目**。但真正卡住人的往往是"我根本不知道从哪看起"。

CodeSentry 的入口层先解决这个问题：给出一张**带证据的架构地图**（文件、符号、行号），而不是一份泛泛的总结。因为可验证的结论才能建立信任——而信任是审查工具被采用的前提。

|---|---|---|
| `research_agent` | 41.6k 行 · 85 提交 | Python + TypeScript |

## 快速开始

```bash
pip install -e .

# 理解一个项目
codesentry onboard /path/to/project --level 2

# 显式重建索引
codesentry index /path/to/project

# 查看索引是否过期
codesentry status /path/to/project
```

## 设计要点

这些不是"看起来很优雅的抽象"，而是**实测数据逼出来的决定**。

### 重要度 = 纯 PageRank，不做加权

曾经尝试「PageRank + 出度 + 入度 + 角色权重」的四信号模型，实测**劣于纯 PageRank**：

| 模型 | Python Top10 命中 | TS Top10 命中 |
|---|---|---|
| **纯 PageRank** | **8/30** | **2/9** |
| 四信号模型 | 5/30 | 4/9 |

原因：角色权重经全局归一化后，同类文件集体霸榜（某项目 `api/` 下 7 个文件全部命中 `contract`，归一化后全部满分，把 Top15 里 9 个位置吃掉）。

**角色信号保留但降级**——不参与排序，只作输出分组标签（"这是入口/守卫/契约"）。

> 详细的自我纠错过程见 [技术选型定稿 §4.3.2](docs/CodeSentry_技术选型定稿_v0.2.md)。

### 两张图：调用图 + 依赖图

**它们是两回事。** 接口文件、类型契约、常量模块只有 import 关系、没有任何函数调用，在调用图里是孤立点。

实测某项目有 5 个核心文件（只读接口、类型契约、HTTP 工具、桥接层）在调用图里入度出度全为 0——只用调用图会全部漏出阅读顺序。

import 边只用于阅读顺序与影响面分析，**不进 PageRank**（保持"重要度 = 调用结构中心性"的语义不变）。

### 阅读顺序 = 入口 → 契约层 → 沿依赖 BFS

不用纯 PageRank 排序。实测 PageRank 对入口/编排类文件没有系统性偏好：

| 项目 | 入口类排名中位 | 全部文件中位 | 编排类中位 |
|---|---|---|---|
| research_agent | 70 | 60 | 77 |

因为 PageRank 衡量"被引用的中心性"，而入口与编排器是"引用别人"的一方。

### 增量缓存：只有 parse 走缓存

| 阶段 | 耗时 | 是否缓存 |
|---|---|---|
| parse | 0.87–1.32 s | ✅ |
| resolve / pagerank / entrypoints / roles | 合计 < 0.2 s | ❌ 每次重算 |

PageRank 也重算是有意的：实测 30,000 节点仅 169 ms，而局部近似的 Top50 重合度只有 11/50。缓存它会引入"索引陈旧"的第二个来源。

**增量结果与全量重建逐项比对**：符号数、边数、PageRank、入口点、调用分类全部一致。

### 缓存不写进被审查项目

默认落 `%LOCALAPPDATA%/codesentry/`。写进项目内会生成 4.7 MB 缓存并污染其 `git status`——**一个"帮你审查代码"的工具，在被审查方留垃圾是减分项**。

需要纳入版本控制时用 `--save-to-project`。

## 索引陈旧问题

> 索引是快照，代码改了索引不知道，直到下次重建。

本项目的答案：内容哈希 + 增量重解析，`codesentry status <path>` 显式报告陈旧程度。

**但必须承认一个残留窗口**：单次扫描过程中代码被修改，索引与工作区会短暂不一致。这个窗口是显式声明的，不是隐藏的。

## 方法论：评测的诚实性

这个项目踩过一次很典型的坑，记录下来以免重犯。

**用主观挑选的少数样本当 ground truth 前，必须先问：这个样本的选择是否与被测机制相关？**

- 相关 → 循环论证，指标虚高
- 不相关 → 有效

**真实案例**：曾用 9 个"角色多样"的文件测「角色识别」机制，得到"四信号 5/9 优于纯 PR 2/9"的结论。换用项目自带文档的**全量**标注清单（30 个文件）重测，结论反转为「纯 PR 8/10 优于四信号 5/10」。

**正确做法**：ground truth 用项目自带的**全量**清单（README 结构表 / 接手指南全表），让工具去比，而不是由人挑。

详见 [技术选型定稿 §4.3.2](docs/CodeSentry_技术选型定稿_v0.2.md)。

## 路线图

- [x] **M0** 索引层：符号图 · PageRank · 入口点 · 增量缓存
- [x] **M1** 阅读顺序：从入口沿依赖展开 · 契约层前置
- [ ] **M2** 检查器：候选漏斗 + 负例集 + 真实误报率
- [ ] **M3** LLM 语义裁决（关键路径才调）
- [ ] **M4** 跨语言影响面 + ts-morph 类型信息
- [ ] **M5** 知识层：项目专属角色词表沉淀
- [ ] **M6** 规则层自进化（PR 形态提案 + 留出集零回归护栏）

**自进化只做两层（知识 + 规则），不做代码层。** 实证依据：投毒评测集可致永久污染，且 LLM 评审委员会拦不住——护栏必须写在架构里，不能指望模型自觉。
