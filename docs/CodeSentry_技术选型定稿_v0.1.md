## 一、本文档解决什么问题

v1.0 方案确立了"确定性 AST 分析 + LLM 语义审查 + 发布门禁"的三层结构，这个方向**经过技术选型讨论后确认成立，不做修改**。

v0.1 定稿解决的是方案里**尚未定型的部分**，共五项：

| # | 议题 | v1.0 方案的状态 | v0.1 定稿结论 |
|---|---|---|---|
| 1 | 解析层工具选型 | 只说"必须自研 AST"，未定用什么 | 各语言原生 + 统一 Finding 契约 |
| 2 | 评测集构成 | fix 提交与规模失衡样本混在一张表 | 拆为 bugs / clean / debt 三个子集 |
| 3 | LLM 在语义层的角色边界 | 只定义了输出协议，未定义驱动机制 | 候选驱动（默认）+ explore 模式（可选） |
| 4 | 修复建议的形态与可信边界 | 未区分 | 三级分类，`extraction` 字段提供机器可读依据 |
| 5 | 基线的问题标识方式 | 未定义key | 内容指纹，禁用行号 |

另有一处**里程碑判定标准**被判定为不可验证，M1/M2 已重写（见 §7）。

## 二、项目定位与设计前提

### 2.1 真实用途（已确认）

CodeSentry 同时承担三个用途，**优先级从高到低**：

1. **能力提升** —— 通过完整实现一个 Agent 工程产品，覆盖 Agent 架构、Context Engineering、评测与质量门禁三类能力
2. **改进既有项目** —— 用它审查并改进 `research_agent` 与 Knowledge Loop 两个自建项目
3. **简历素材** —— 产出的可量化数据需具备真实性与不可编造性

>用途2 给了本项目一个别人难以复制的优势：**真实被审查对象**。不需要另找开源项目当靶子，且"用自建工具审查自建项目并修复"构成一条完整、可量化的叙事线。

### 2.2 时间预算

**无硬性截止**。因此不追求快速验证，M1 阶段应做扎实而非求快。

### 2.3 由此确立的两条工程原则

**原则一：不确定的结论不得进阻断路径。**

任何无法通过确定性手段复验的判断，只能以warning 形式输出。这直接决定 §5.4 的置信度分级设计。

**原则二：先用窄方案跑通，再扩宽。**

不为尚未验证的能力提前支付架构成本。典型例子：TypeScript 解析在 M1–M3 采用轻量方案，直到 M4 确实需要类型信息时才引入 ts-morph。

## 三、架构总览

```
CodeSentry/
├── analyzers/                     # 确定性检查器（AST / 静态分析，必须可单测）
│   ├── complexity.py              # 函数/文件规模、圈复杂度、嵌套深度
│   ├── naming.py# 命名一致性
│   ├── dead_code.py               # 不可达分支、未使用导出
│   ├── silent_failure.py          # 静默失效模式（except: pass 掩盖保护逻辑）
│   └── interface_contract.py      # 跨语言接口字段比对（M4）
├── core/
│   ├── finding.py                 # Finding 数据契约（Pydantic）
│   ├── fingerprint.py             # 内容指纹计算
│   ├── policy.py                  # policy.yaml 加载与校验（Pydantic）
│   └── cache.py                   # 增量缓存（mtime + 内容哈希）
├── llm_reviewer.py                # 语义裁决层
│   ├── candidates.py              # 候选聚合：从 analyzers 收集待裁决项
│   ├── protocol.py                # 强制结构化输出 schema
│   ├── verifier.py                # 结论回验
│   └── explore.py                 # 自由扫描模式（可选，默认关闭）
├── gates/
│   ├── gate.py                    # 判定逻辑：阻断 / 警告 / 通过
│   └── baseline.py                # 基线对比（内容指纹匹配）
├── report/
│   ├── terminal.py                # 终端输出
│   └── web/                       # Web 报告（M5）
├── evals/
│   ├── cases/
│   │   ├── bugs/                  # 有正例 → 测召回
│   │   ├── clean/                 # 无正例 → 测精确
│   │   └── debt/                  # 架构债 → 测报告质量
│   ├── gate_eval.py               # precision / recall 门禁
│   └── reports/                   # 历史对比
└── cli.py                         # codesentry scan <path>
```

**分层职责的边界**：

- **解析层**：把代码变成结构化事实（各语言用各自最优工具）
- **规则层**：在结构化事实上做判定（跨语言比对在这一层完成）
- **裁决层**：LLM 只对候选做判断，不主动发现问题
- **门禁层**：确定性的最终判定与基线比对

## 四、解析层与 Finding 契约

### 4.1 选型结论

v1.0 方案 §4.1 明确"结构层必须自研 AST 分析，不能全靠 LLM"——这个判断成立，保留。但**用什么解析**需要选型。

| 方案 | 成本 | 结论 |
|---|---|---|
| tree-sitter 统一 | Windows 下需编译 C 扩展；CST 含标点空白需自写裁剪层；拿不到类型信息 | ❌ 不采用 |
| 各语言原生 + 统一 Finding 契约 | Python 用标准库 `ast`（零依赖）；TS 用轻量抽取，必要时 `ts-morph` | ✅ 采用 |

**核心认知：跨语言能力不应该做在解析层，而应该做在规则层。** 统一的是"发现问题"的形状（Finding 契约），不是"解析代码"的工具。

### 4.2 TypeScript 解析的分阶段策略

| 阶段 | 方案 | 依据 |
|---|---|---|
| M1 – M3 | 轻量抽取（正则/ AST 子集），仅支持字段级声明提取 | 够用于命名、规模、契约字段比对 |
| M4 起 | `ts-morph` Node 子进程 | 唯一能拿到**类型信息**的方案；跨语言契约深度比对必须要类型 |

`ts-morph` 是 Node 包，意味着需要 Python 侧起子进程通信，会增加架构复杂度。**因此不为 M4 提前引入**——先用窄方案跑通，确认确实需要类型深度后再升级（依据 §2.3 原则二）。

### 4.3 Finding 数据契约

```python
class Finding(BaseModel):
    file: str
    line: int
    end_line: int | None
    symbol: str | None
    
    rule_id: str                    # 如 complexity.function_length
    severity: Severity              # critical / high / medium / low
    source: Source                  # deterministic / llm
    
    reason: str
    evidence: str                   # 人类可读的证据描述
    
    extraction: Extraction | None   # 机器可读的事实（见 §6.2）
    suggestion: str | None
    suggestion_type: SuggestionType | None   # structural / patch / advisory
    confidence: float
    
    fingerprint: str                # 内容指纹，见 §7
```

**为什么用 Pydantic 而非 dataclass**：同一份模型需要同时满足三件事——向 LLM 提供 JSON Schema 做结构化输出约束、在 Web 报告中序列化、在 `policy.yaml` 中做校验。Pydantic 一次覆盖三者，dataclass 三倍成本。

## 五、LLM 语义层

### 5.1 三种角色边界方案对比

v1.0 方案 §4.3 定义了输出协议（JSON schema），但**协议约束的是格式，不是机制**。实现方式的选择决定了 precision 的来源。

| 方案 | 谁决定"这里有问题" | precision | 可复现 | 可单测 | 结论 |
|---|---|---|---|---|---|
| **A. 候选驱动** | 确定性层决定位置，LLM 决定是否成立 | 高 | ✅ | ✅ | **默认采用** |
| B. 自由扫描 | LLM 决定位置与结论 | 低（必然崩） | ❌ | ❌ | 仅作 explore 模式 |
| C. 只打分 | LLM 不指出位置 | 无判定 | — | — | 不满足门禁需求 |

**为什么门禁类产品必须用 A**：门禁要求"确定地阻断"，B 与 C 都给不了确定性。B 的 precision 崩塌是prompt engineering 的确定性现象——要求 LLM 找问题，它就一定会"找到"问题，且每次结果不同，无法验证是真实问题还是幻觉。

**A 的隐藏优势**：两个优化变量彼此独立。候选过多 → 调阈值；LLM 判定过松 → 调 prompt。可以分别度量、分别优化。

### 5.2 候选驱动的执行流程

```
1. analyzers 产出候选（位置 + 触发规则 + 机器可读事实）
2. candidates 聚合，按规则分组
3. 并发提交 LLM 裁决（asyncio + Semaphore）
4. verifier 回验：不通过的直接丢弃
5. 合并为 Finding，进入门禁判定
```

LLM 的输入是**一条候选**，不是一片代码。输出只有"成立/ 不 成立 + 严重级别 + 依据"。

### 5.3 explore 模式（可选，默认关闭）

`--explore` 开关，仅在人工指定的小范围（如单个 PR diff）开启自由扫描，用于演示"规则之外还能发现什么"。

**约束**：
- 两种模式的 precision / recall **分开统计**，不得混合
- explore 模式的结论**不得进入阻断路径**（依据 §2.3 原则一）

其价值在于展示"我理解这条 trade-off"，而非成为默认路径。

### 5.4 置信度分级与阻断边界

| 来源 | 置信度 | 门禁行为 |
|---|---|---|
| deterministic + 回验通过 | 1.0（确定） | 可阻断 |
| llm + 回验通过 | 0.5 – 0.9 | **仅警告** |
| llm + 回验失败 | — | 丢弃 |
| explore 模式 | 不定| **仅展示** |

**回验能挡什么、不能挡什么**（必须写进 README，这是理解本项目可靠性的关键）：

- ✅ 挡得住：**幻觉型误报** —— 行号不存在、符号未出现、证据无法复现
- ❌ 挡不住：**判断型误报** —— 行号真实存在，但"这构成问题"的论断是错的

精确率的保障主要来自候选驱动的漏斗收敛，回验是第二道保险而非唯一保障。

## 六、修复建议的设计

### 6.1 三级分类

用户明确提出需要"报出问题的同时给出修复建议"，同时表明"不可能完全信任它"。**这个不信任恰好划定了可信边界**——三种建议形态的可信度差异极大，混为一谈会导致误用。

| 形态 | 生成方 | 可信度 | 使用方式 | `suggestion_type` |
|---|---|---|---|---|
| 重构建议（拆分函数） | LLM 自由生成 | 低。拆分边界、方式、顺序均由 LLM 猜测 | 仅参考，需人工设计 | `structural` |
| 修复补丁（修正常量/条件） | LLM 生成 + 门禁验证 | 高。测试可验证 | 可用（前提是过门禁） | `patch` |
| 定位 + 依据 | 确定性层 + LLM 裁决 | 很高 | **主力形态** | `advisory` |

**结论**：M1–M3 只实现第三种 + 第二种的最小形态，第一种明确标注"仅供参考，需人工设计"。

真正提效的是第三种：扫出 200 条，其中大部分是确定性判定的真问题，按清单修即可，无需逐条读代码。前两种都需要再做一遍 review，反而没有省事。

### 6.2 `extraction` 字段：让修复建议有据可依

```json
{
  "file": "graph_builder.py",
  "line": 120,
  "rule_id": "complexity.function_length",
  "severity": "medium",
  "source": "deterministic",
  "reason": "函数同时包含构图、路由表定义与工具执行三种职责",
  "evidence": "add_node(7) / add_conditional_edges(2) / ToolNode(3) 均在此函数内",
  "extraction": {
    "sub_symbols": ["add_node", "add_conditional_edges", "ToolNode"],
    "sub_symbol_counts": [7, 2, 3],
    "function_lines": 793,
    "call_depth_max": 4
  },
  "suggestion": "可按 add_node / add_conditional_edges / ToolNode 三段切分",
  "suggestion_type": "structural",
  "confidence": 0.9
}
```

**这是本设计的关键**：LLM 说"这个函数有三种职责"，而 `sub_symbol_counts` 是**确定性层数出来的**。回答"你怎么知道它职责过载"时，答案是"我统计了子结构出现次数，不只是看行数"。

把"行数超阈"这种弱信号升级为"子结构计数"这种强信号，是确定性层真正建立护城河的地方。

## 七、基线与指纹

### 7.1 问题标识方式

v1.0 方案 §4.2 定义了基线机制，但未定义**如何标识"同一个问题"**。

**如果用 `file:line` 作key，必然失效**：

```
在 graph_builder.py 开头插入 3 行 import
  → 所有问题的行号 +3
  → 基线中 200 条全部匹配失败
  → 全部变成"新增问题"
  → 门禁疯狂误报，一周内必然被关掉
```

### 7.2 内容指纹方案

```
fingerprint = sha1(rule_id + normalized_symbol_name + normalized_code_snippet)
```

- `normalized_code_snippet`：去空白、去注释后取前 N 行
- **行号仅作为展示信息，不参与匹配**
- 插行、改注释、调格式均不导致基线失效；仅代码实质变化才计为新增

该细节应在 README 单独成节说明——它是"知道 naive 方案会在何处失效"的直接证据。

### 7.3 基线存储

**git 跟踪的 JSON**，不使用 SQLite。基线必须可 diff、可 review、可回滚。

存量问题按 `policy.yaml` 配置降级为警告或豁免，并作为"待偿债务"可视化，随版本逐步清零。

## 八、评测集设计（对 v1.0 §5.2 的重构）

### 8.1 原方案的问题

v1.0 §5.2 把 8 个 fix 提交与 3 个规模失衡样本放在同一张表里，但**它们不是同类样本**：

| 样本类型 | 修复前后代码 | 可测量目标 |
|---|---|---|
| fix 提交（8 个） | **不同** | 有正例 → 测召回 |
| 规模失衡（3 个） | **完全相同** | 它不是 bug，是长期存在的架构债 |

`build_graph` 793 行从未在任何 fix commit 中被"修好"。把它当bug 样本时标注答案是什么？人工 reviewer 看到 793 行也不会报"这里有 bug"——这个假正例会污染 precision 指标。

### 8.2 更严重的问题：没有负例集

**一个什么都不报的检查器 recall=0、precision=1.0。** 没有负例集，precision 数字无意义。

要使precision 指标具备说服力，必须引入第三类样本：已被广泛审查过的干净开源代码（如 `flask` / `httpx` / `requests` 的特定文件），检查器在其上**不应报出问题**。

误报率是这个产品最硬的指标，重要性高于召回率。

### 8.3 三个子集

| 子集 | 内容 | 测量目标 | 来源 |
|---|---|---|---|
| `evals/cases/bugs/` | 8 个真实 fix 提交 | **recall** | git 历史反向构造 |
| `evals/cases/clean/` | 已审计的开源代码 | **precision**（误报率） | 开源项目选定文件 |
| `evals/cases/debt/` | 规模失衡样本 | **报告质量**（该报时是否报准） | 已知架构债 |

`debt/` 子集的判定标准不是"是否命中"，而是"是否应当报出且理由准确"——这类样本用于校准报告质量，不混入 recall / precision 计算。

### 8.4 bug-reintroduction 构造流程

```
1. 取 fix 提交（如 ad36172）
2. checkout 到父提交（有 bug 的状态）
3. 以 commit message + diff 作为标准答案（label）
4. Agent 审查该状态，检查能否检出
5. 统计 precision / recall，纳入 release_gate
```

### 8.5 跨项目规则一致性验证

在`research_agent` 上调完阈值后，**在第二个项目（Knowledge Loop）上再跑一遍**：

- 两者误报率接近 → 规则具备通用性，阈值非过拟合
- 两者差异大 → 阈值过拟合了第一个项目

这个"跨项目误报率一致性"指标比"precision = 0.85"更具说服力：后者是自划靶点，前者是在未知答案的真实代码上测出的。

## 九、里程碑（对 v1.0 §8 的修正）

### 9.1 M1 判定标准不可验证

v1.0 §8 规定 M1 判定标准为"在 research_agent 上检出 §3.1 §3.2 全部样本"。但这两节的样本是**已知答案的**（自己统计出的 793 行、2,582 行）。

**检出已知答案只证明代码能跑，不证明任何东西。**

M1 真正应验证的是：在真实代码上的**误报率**。v1.0 §5.3 已正确指出"误报比漏报更致命"，但里程碑中无对应动作。

### 9.2 修正后的 M1 / M2

| 里程碑 | 内容 | 判定标准 |
|---|---|---|
| **M1 结构层** | complexity + naming + Finding 契约 + 指纹 + CLI + 报告 | 在 research_agent 全量跑通；**人工标注前 50 条的真实误报率**；据此调整 policy.yaml 默认阈值 |
| **M2 评测集** | bugs / clean / debt 三子集 + gate_eval | recall ≥ 0.70；precision ≥ 0.85；**且在两个项目上误报率数值接近** |
| **M3 语义层** | 候选驱动裁决 + 协议 + 回验 | 静默失效类用例可检出；LLM 结论回验通过率 |
| **M4 契约层** | interface_contract + ts-morph 接入 | 能报出人为制造的 TS 字段缺失 |
| **M5 门禁** | 基线对比 + CI 集成 + Web 报告 | 两个真实项目上跑通，存量不再阻断 |
| **M6 生成** | 受约束的修复补丁生成 | 补丁不过门禁则拒绝写入 |

M1 + M2 完成后，项目即"立得住"——那时手上会有的数字是：**"检查器在两个 30k 行真实项目上的误报率分别为 X% 和 Y%"**。
