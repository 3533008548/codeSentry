## 二、场景定位

### 2.1 两个场景

| | 场景 A · 理解 | 场景 B · 审查 |
|---|---|---|
| 用户是谁 | 刚接手一个陌生项目的人 | 提交代码前需要把关的开发者 |
| 核心问题 | "从哪开始读？" | "这次改动有没有问题？" |
| 输出 | 导航图 + 阅读顺序 + 关键路径 | Finding 列表 + 影响面 + 门禁判定 |
| 优先级 | **高（先做）** | 中 |

### 2.2 场景定位的确认

用户明确：**主要目的是用这个 agent 帮助理解其他项目的代码**。审查场景降为第二优先级，但保留——因为它是"能作为 CI 门禁"这一工程说服力的来源，且与场景 A 共用同一套索引。

### 2.3 两个场景是流水线，不是并列功能

```
接手陌生项目（场景 A）
  → codesentry onboard  →  5 分钟搞懂骨架与入口
  → 开始改代码
  → codesentry scan --diff  →  基于图索引给出影响面 + 候选问题
  → 修完提交
  → 门禁拦截 / 通过
```

**这条因果链是本项目最强的叙事结构**：

> "审查工具之所以不准，是因为它只知道 diff、不知道 diff 之外的调用关系。
> 所以我先做了代码理解能力，有了图索引之后，审查的误报率从 X 降到了 Y。"

它把两个场景从"两个功能"讲成"一条因果链"——**这比功能罗列强十倍**，且是 M0 索引层存在的正当性来源。

### 2.4 行业路线对照（为何占位成立）

| 路线 | 代表 | 上下文范围 | 实测表现 | 结论 |
|---|---|---|---|---|
| diff-only | CodeRabbit | PR diff + 变更文件 | 检出 ~82% / 误报 ~8% | 跨文件缺陷结构上不可见 |
| 向量索引 | Cursor / Greptile | 全仓库 embedding | 检出 ~44% / **误报 ~22%** | 精确率与召回双低 |
| Agent 自由探索 | Claude Code | 按需 Glob/Grep/Read | 不可复现 | 无法进 CI 门禁 |
| **图索引 + 候选驱动** | Aider repo map / Coldstart | 结构图 + 符号重要性 | SWE-bench Lite 26.3% 解决率，70.3% 文件定位准确率 | **可复现 · 可量化 · 可阻断** |

CodeSentry 落在第四象限，且是该象限中**唯一同时承诺"可复现"与"可进阻断路径"**的方案（前三者各缺一项）。

**关键设计取舍**：放弃向量检索，采用**静态索引 + 引用图**。理由是静态索引返回结果带 `file:line` 可验证证据，而相似度分数不可验证——这与 v0.1"不确定的结论不得进阻断路径"是同一条原则的延伸。

## 四、M0 统一索引层

### 4.1 为什么索引层必须先于两个场景

v0.1 的场景 B（审查）有一个未解的设计缺口：**"改这个函数会影响谁"需要跨文件影响面分析，而那需要图索引。** v0.1 未设计该能力，因为当时只有审查一个场景。

加入场景 A 后，图索引成为两个场景共用的地基——**场景 A 把它当作"我要读什么"，场景 B 把它当作"改这里会波及什么"。**

### 4.2 三张表

| 表 | 内容 | 用途 |
|---|---|---|
| **Symbol 表** | 符号名、种类、文件、起止行、签名 | 骨架摘要、符号检索 |
| **引用边表** | `(from_symbol, to_symbol, file, line)` | 调用图、重要度计算、影响面 |
| **文件元数据** | 路径、语言、行数、import/export 列表、是否测试 | 入口点识别、规模统计 |

**符号主键必须是限定名 `file::symbol`，不得用裸符号名。**

> **实测依据（v0.2 修订）**：裸符号名做主键时，实测项目 1,206 个定义只有 990 个唯一名（**重名率 18%**），`get` 在 8 个文件里各定义一次 → 图节点被合并 → PageRank 变成"给最常见的词打分"（实测 Top1 是 6,101 行的测试文件，核心符号全是 `get`/`append`/`list`）。改限定名后 Top12 全部命中真实架构组件。详见 `CodeSentry_索引层实测报告_v1.0.md` §三。

**符号级排序只能用唯一定位的符号。** 同名多定义（歧义）的符号不参与符号级排序，但仍参与文件级排序——文件级只需要知道"有调用发生"，不需要知道调用的是谁。

### 4.2.1 项目级排除规则（必备功能，非配置项）

> **实测依据**：`research_agent` 的 `runtime/` 目录含 465 个 `.py`、**175,589 行**，占全仓 Python 行数的 80%，但**一行都不是项目代码**（论文库、实验产物、临时文件）。不排除则排序彻底失真。

排除清单需默认识别：数据目录、构建产物、依赖目录、缓存目录。**这是索引层的一等功能，M0 第一批实现，且必须有针对真实项目的测试。**

**两类排除，用途不同，不可混为一谈**：

| 类别 | 目录 | 理由 |
|---|---|---|
| **不解析** | `runtime/` `papers/` `node_modules/` `dist/` `__pycache__/` `.git/` | 不是源码，解析即浪费 |
| **不参与重要度排序** | `scripts/` `evals/` `tools/` `tests/` `benchmarks/` | 是源码但**不是产品架构的一部分** |

> **实测依据（第二类）**：Python 侧首次应用四信号模型时，`scripts/` 与 `evals/` 下的文件霸占 Top10（`evals/benchmark.py`、`scripts/run_rag_retrieval_eval.py`…）。原因是 `entry` 角色权重 1.00，而这些脚本都有 `__main__` 守卫，命中 entry 规则。**排除后 Top20 命中从 1/9 回升到 5/9。**

### 4.2.2 符号解析率的天花板

实测项目的 17,449 个调用，分类分布：

| 类别 | 占比 | 说明 |
|---|---|---|
| builtin | 49.9% | 内置/方法调用，正确的不该解析 |
| local + cross_file | **16.5%** | 项目内已解析，**这才是有效边** |
| external | 11.7% | 第三方库，标 external 不参与项目内重要度 |
| test_helper | 8.4% | 测试断言 |
| unresolved | 12.8% | 纯 AST 无法解析 |

**unresolved 的构成**：约 1,084 条是标准库的**类方法**（`datetime.now()` 的 `now`、`sqlite3.commit()` 的 `commit`）——`ast` 看不到类的方法；约 256 条是**同名多定义歧义**（`create` 29 次、`start` 21 次、`tokenize` 18 次）。

**结论：纯 AST 符号解析的天花板约 60–70%（按项目内调用计）。** 提升手段按性价比排序：

1. 补标准库方法表（一次性硬编码常用集合）—— 成本最低，收益最大
2. 启发式消歧（同文件优先 + import 路径匹配）
3. 真实类型信息（`ts-morph` / `mypy` / LSP）—— 成本最高

**因此 `ts-morph` 在 M0 不需要引入**（排序质量已可用，跨文件边 830 条足够支撑 PageRank 与影响面分析）。**M4 引入它的理由仍然是跨语言契约比对，而非提升 Python 侧解析率。**

### 4.2.3 TypeScript 解析器选型

v0.2 初稿写的是"轻量抽取（正则/AST 子集）"。**实测后具体化**：

| 方案 | 判断 |
|---|---|
| 正则抽取 | ❌ 抽不出 import 关系与作用域归属 |
| **`ts.createSourceFile`（TypeScript 编译器 API）** | ✅ **采用**。目标项目已装 typescript 5.9.3，**零新增依赖** |
| ts-morph | ⚠️ 能力更强（真实类型信息），M4 之前用不上 |

**关键认识**：`ts-morph` 的核心价值是**类型信息**（`getType()`）。M0 只需要符号定义、调用点、import 表——`ts.createSourceFile` 全都能给。

**实测性能**：26,075 行 / 140 文件 / 1,153 符号，解析 **0.38s**（**68,618 行/秒**，是 Python `ast` 的 3.1 倍）。

**跨项目实测补充**：TS 侧 unresolved 仅 **6.9%**（优于 Python 的 12.8%），因 TS 的 import 语法明确给出模块路径。但 TS 侧有 20.3% 的 `module_level`（方法调用无归属），这部分需类型信息——**同样不阻塞 M0**。

### 4.3 重要度：PageRank 为主（v0.2 修订三，撤回四信号模型）

借鉴 Aider repo map 的核心做法：文件为节点、符号引用为边，跑 PageRank。

**PageRank 有效的根本原因：重要性沿调用图传播。** 被 20 个文件引用的函数排在只被调用一次的辅助函数之前；而被重要函数调用的符号，自身排名也随之升高。BM25（词频）和"最近修改时间加权"都缺少这个性质。

#### 4.3.1 曾经的「四信号模型」与它的撤回

v0.2 修订二曾引入四信号模型：

```
重要度(f) = 0.25·PR + 0.15·出度 + 0.25·入度 + 0.35·角色权重
```

**该设计已在 v0.2 修订三撤回。** 撤回过程与原因见 §4.3.2，这是本项目最重要的一次方法论纠错。

#### 4.3.2 为什么撤回：一次循环论证的评测

**当时的评测**：以 Knowledge Loop 的《项目接手指南》列出的 **9 个文件**为 ground truth，测出「四信号 Top10 命中 5/9，纯 PageRank 仅 2/9」。

**问题在于这 9 个文件是怎么挑的**——它们恰好覆盖了入口（`main.ts`/`App.tsx`）、契约（`desktop-api.ts`）、守卫（`policy-engine.ts`）、提案（`action-proposal.ts`）几种角色。**而被测的机制正是"角色识别"。用角色词表去测角色词表，是循环论证。**

**改用项目自带文档的全量清单重测**：

| 侧 | ground truth | 纯 PageRank Top10 | 四信号 Top10 | 结论 |
|---|---|---|---|---|
| Python | README「项目结构」章节，**30 个**文件 | **8** | 5 | 纯 PR 胜 |
| TypeScript | 《项目接手指南》，9 个（唯一可用集） | 2 | 4（v3） | 但纯出度亦为 2 |

TS 侧同口径复测（`ts_rank_compare.js`）：

| 模型 | Top5 | Top7 | Top9 |
|---|---|---|---|
| **纯 PageRank** | 1 | 2 | 2 |
| 纯出度 | 1 | 2 | 2 |
| v3 角色全局归一化 | 3 | 3 | 4 |
| v4 角色·类别内相对 | 4 | 5 | 5 |

**两项目一致：纯 PageRank / 纯出度最优，角色信号是负收益。**

**角色信号的第二个缺陷**：权重经全局归一化后，**同类文件集体霸榜**。research_agent 的 `api/` 下 7 个文件全部命中 `contract`(0.85)，归一化后全部满分 → Top15 里 9 个位置被 `api/` 吃掉。

尝试过「角色不参与全局归一化，改为类别内相对分 × 类别权重」（v4），有效但仍不如纯 PR。

#### 4.3.3 修订后的方案

```
重要度(f) = PageRank(f)                      主信号
```

**出度（outdeg）不参与重要度排序，也不作为入口识别信号**（v0.2 修订四，源于 M0 实测）。

> **M0 实测推翻**：v0.2 修订三曾写"出度保留为入口识别的独立信号"。**实测证明这条不可靠**：
> - research_agent：`llm_client.py`（出度 23）、`daily_orchestrator.py`（29）被标成应用入口
> - Knowledge Loop：`deepseek-client.ts`（61）、`desktop-wiki-service.ts`（101）排在真入口前
>
> **出度高只说明「它 import 了很多东西」，不说明「它是入口」**——依赖多的服务模块会排在真正的入口前面。入口的可靠判据只有三个：文件名规律、框架注册、被生产模块导入。

**角色信号不删除，但改变用途**：不参与排序加权，改为**输出时的分组标签**——告诉用户"这是入口 / 这是授权中心 / 这是契约层"，帮助理解，而非决定顺序。

**入口/编排类文件在 PageRank 里天然排不上去**（实测 research_agent：入口类排名中位 70，全部中位 60），因为 PageRank 衡量"被引用的中心性"，而入口与编排器是"引用别人"的一方。**因此 L2 的"推荐阅读顺序"采用入口优先策略，不用纯 PageRank 排序。**

> **这是本项目最重要的一次方法论纠错，且它重复了自己犯过的错**：v0.2 §9.1 已经定过「M1 判定标准是真实误报率，不是检出已知样本」，而本轮又用"手工挑的 9 个样本"当 ground truth 得到了虚高指标。**任何用主观挑选的少数样本当 ground truth 的评测，都必须先问：这个样本的选择是否与被测机制相关？** 相关则是循环论证。

#### 4.3.4 角色信号规则（保留，用于输出分组）

| 角色 | 权重 | 判据（路径/文件名/内容特征） |
|---|---|---|
| `entry` | 1.00 | `main`/`index`/`app`/`server`/`cli`/`preload`；`createRoot()`/`app.whenReady`/`BrowserWindow(`/`ipcMain.` |
| `guard` | 0.95 | `policy`/`guard`/`security`/`permission`/`auth`/`sandbox`/`safe` |
| `contract` | 0.85 | `api`/`types`/`contract`/`schema`/`interface`/`shared` |
| `orchestrator` | 0.85 | `loop`/`orchestr`/`coordinat`/`agent`/`runner`/`workflow`/`pipeline`/`dispatch`/`router` |
| `proposal` | 0.70 | `proposal`/`preview`/`draft`/`action`/`intent` |
| `service` | 0.60 | `service`/`client`/`provider`/`adapter`/`handler` |
| `store` | 0.60 | `store`/`repository`/`persistence`/`database`/`index`/`snapshot` |
| `infra` | 0.50 | `config`/`hash`/`log`/`util`/`helper`/`domain`/`base`/`common` |
| （无匹配） | 0.20 | 默认低权重 |

**规则完全确定性，不调用 LLM，可单测。** 词表做成可配置 `roles.yaml`，由 M5 知识层产出项目专属覆盖。

#### 4.3.5 跨项目验证结论

| 维度 | Python 侧主要风险 | TS 侧主要风险 |
|---|---|---|
| 排序失真主因 | 同名符号合并 | 方法调用归属不明 |
| 解决手段 | **限定名** | 限定名（TS 侧重名率低） |
| 排除规则 | 必需（`runtime/` 占 80% 行数） | 常规即可 |
| 未解析占比 | 12.8%（标准库类方法） | 6.9%（module_level 20.3% 需类型） |

**"跨项目一致性"的真正含义：不是两个项目数字一样，而是同一套机制（限定名 + 排除规则 + PageRank）能覆盖两者的失败模式。**

**PageRank 性能实测（v0.2 补充，本机 i7-12700H）**：

| 图规模 | 纯 Python PageRank 耗时 |
|---|---|
| 500 节点 | 1.1 ms |
| 2,000 节点 | 4.6 ms |
| 8,000 节点 | 27 ms |
| **30,000 节点** | **169 ms** |

**决策修订（v0.2 修订 v0.2 初稿）**：初稿曾设计"增量场景用反向引用计数 + 层级深度的局部近似"作为折中，理由是"PageRank 是全局计算"。**实测证明该理由不成立**——真实项目量级（30,240 符号）的 PageRank 仅需 32 ms，**每次全量计算都不慢**。

而局部近似的排序质量代价被实测暴露：Top20 重合度 16/20，Top50 重合度仅 11/50。

**因此修订为：每次都计算全量 PageRank，删除局部近似这条路径。** 理由：
1. 性能上无必要——169 ms 相比 AST 解析的 8.9 s 可忽略
2. 质量上更优——省掉一个"重要度有两种算法"的解释负担与不一致风险
3. 少一个概念，少一处需要写进 README 的 trade-off

> **方法论收获**：v0.1 曾定"trade-off 必须写进 README，不假装解决了"。本次实测同时验证了它的反面——**当 trade-off 实际不存在时，不要为了显得严谨而制造它。** 声称"我们做了折中"而不给数据，是伪严谨。

**依赖策略**：**不引入 numpy / scipy / networkx**。理由有三：
1. 纯 Python 实测 30,000 节点仅 169 ms，够用
2. Windows 上安装 scipy 需编译 C 扩展，本次实测**安装直接超时**，会显著抬高环境搭建成本
3. 自实现的 PageRank 约 60 行，可单测，且不受第三方版本升级影响

### 4.4 入口点识别

确定性识别，不依赖 LLM。**分为两级**：

| 级别 | 判据 | 输出 |
|---|---|---|
| **应用入口** | 文件名规律（`main`/`app`/`server`/`cli`）+ 框架注册（FastAPI/Flask/APIRouter/argparse/typer）+ 被生产模块导入 | L1 主入口，**通常 1–3 个** |
| **脚本入口** | 有 `__main__` 守卫，但在 `scripts/` `tests/` `evals/` `tools/` 下 | 折叠为"辅助脚本 N 个"，不逐个列出 |

各信号说明：

| 信号 | 判据 |
|---|---|
| 清单文件 | `pyproject.toml` / `package.json` 的 `main` / `scripts` / `[project.scripts]` |
| 框架配置 | `next.config.*` / `vite.config.*` / `django` settings / `fastapi` app |
| 文件名规律 | `main.*` / `index.*` / `app.*` / `server.*` / `cli.*` / `cmd/` |
| 注册模式 | `if __name__ == "__main__"` / `app.listen(` / `add_argument` / 路由注册 |
| 导出关系 | 被其他模块导入且位于顶层 |

> **实测依据（v0.2 修订）**：第一版仅用"`__main__` 守卫"作信号，实测命中 **54 个**（含 22 个 scripts、25 个 tests、多个非入口模块），召回率 100% 但**精确率仅约 11%**。改为两级分类后收敛到 **3 个应用入口**（`research_agent.py` 框架注册、`api/app.py` 文件名+框架、`api/routes.py` 框架注册），与项目实际结构吻合。
>
> **根因认识**：`if __name__ == "__main__"` 是**可执行脚本标记**，不是**应用入口标记**。

### 4.5 增量失效

**内容哈希失效**（v0.1 已定）：

- 每个文件缓存 `(mtime, content_hash, parsed_symbols, outgoing_edges)`
- 变更文件 → 重解析 → 更新边表
- **每次重算全量 PageRank**（实测 30,000 节点 169 ms，无性能必要做局部近似，见 §4.3）
- 显式 `refresh-index` → 全量重建（清空缓存后重来）

**索引陈旧问题必须在 README 回答**：Greptile 栽在这一点上——索引是快照，代码改了索引不知道，直到下次重建。本项目的答案是内容哈希 + 增量重解析，**但必须承认一个残留窗口：单次扫描过程中代码被修改，索引与工作区会短暂不一致**。这个窗口是显式声明的，不是隐藏的。

## 五、场景 A · 理解陌生项目

### 5.1 输出分级

参考成熟 onboarding 工具的共同做法：**三档递进，不是一次性给全部。** 对应三种使用时机。

| 档位 | 耗时 | 回答的问题 | 输出 |
|---|---|---|---|
| **L1 · 定位** | <30s | "这是什么项目？" | 技术栈 + 入口点列表 + 规模统计 |
| **L2 · 骨架** | <3min | "它怎么组织的？" | 核心模块（按重要度排序）+ **推荐阅读顺序** |
| **L3 · 深挖** | 按需 | "这个功能在哪实现？" | 关键路径（入口 → 校验 → 逻辑 → 持久化 → 响应） |

**实施范围（已确认）**：Phase A 先做 **L1 + L2**。L3 延后到 M7+。

### 5.2 确定性 / 语义的分工

**这条边界必须写死**：

| 档位 | 是否调用 LLM | 理由 |
|---|---|---|
| L1 | **否** | 全部可从清单文件、配置、AST 确定性得出 |
| L2 | **否** | 模块重要度来自 PageRank，阅读顺序来自拓扑序 + 重要度加权 |
| L3 | 是 | 关键路径的语义串联（"这一步在校验什么"）无法从结构推出 |

**L1/L2 全确定性 = 快、可复现、可测试**。这与 v0.1 "确定性层是护城河"的原则一致，也让 Phase A 的评测容易做（答案可由人工标注一次、多次复用）。

### 5.3 L1 输出样例


### 5.5 场景 A 的评测指标

**没有评测的场景 A 只是 demo。** 四个指标：

| 指标 | 测法 | 目标 |
|---|---|---|
| **入口点召回率** | 人工标注真实入口点，看工具找出几个 | **100%（不妥协）** |
| **入口点精确率** | 工具报出的入口点里，有几个真是应用入口 | **≥ 0.9**（v0.2 补充） |
| **项目内符号解析率** | (local + cross_file) / (local + cross_file + unresolved + ambiguous) | ≥ 0.6（M0 实测 research_agent 81.9%；**注意口径不是全部调用**——57% 是 builtin 本就不该解析） |
| **关键文件 Top-K 命中** | 见下方「ground truth 来源」 | v0.2 修订四：**该指标须衡量「阅读顺序」而非纯 PageRank 排名**（M0 实测入口类文件 PageRank 中位 70 vs 全部中位 60） |
| **幻觉符号率** | 输出中的符号名/文件名有多少在代码里不存在 | **0（硬门槛）** |
| 耗时 | L1 / L2 端到端 | <30s / <3min |

#### 5.5.1 ground truth 来源：项目自带的文档

> **v0.2 新发现**：**任何认真维护的项目都自带「这个项目的核心文件是什么」的答案。** README、架构文档、贡献指南、《接手指南》——它们天然包含 ground truth。

这解决了评测集构造的一个难题：**不需要人工标注、不需要从 git 历史构造**。

**但必须用「文档里的全量清单」，不能只挑一部分。** 见 §4.3.2：只挑 9 个角色多样的样本去评测角色识别机制，是循环论证，会得到虚高指标。

| 项目 | ground truth 来源 | 规模 | 纯 PageRank Top10 命中 |
|---|---|---|---|
| research_agent | README「项目结构」章节 | 30 个生产文件 | **8/30** |
| Knowledge Loop | 《项目接手指南》§5 目录与关键文件表 | 9 个文件 | 2/9 |

**Knowledge Loop 侧的 9 个是唯一可用集**（README 只有目录级描述），因此其指标要谨慎解读。

#### 5.5.2 入口点识别需要独立信号

实测：`src/main.ts` 出度 55、入度 0，纯 PageRank 排第 74，但人工标注它是第一入口。

**因此出度不参与重要度排序，但作为入口识别的独立信号使用**（见 §4.3.3）。

> **实测状态**：入口点召回率 100% 但精确率 11%（已通过两级分类修复至 3 个应用入口）；项目内符号解析率 16.5%（占全部调用口径，按项目内调用口径约 55%）；耗时实测 **< 1s**，比目标有 30–180 倍余量。

**"幻觉符号率 = 0" 复用了 v0.1 的 verifier 能力**——同一套回验模块，一个用于审查结论的行号回验，一个用于理解输出的符号回验。**这是两个场景共享的又一块基础设施。**

这个指标能支撑一个很硬的叙事：**"读懂项目"任务上，模型最大的失败模式不是漏看，而是编造不存在的函数；我用确定性回验把它压到 0。**

## 六、自进化设计（M5 知识层 / M6 规则层）

### 6.1 三层模型与实施范围

| 层 | 进化对象 | 风险 | 本版决策 |
|---|---|---|---|
| **知识层** | 代码认知（Insight） | 低 | ✅ 实施（M5） |
| **规则层** | 确定性检查器 | 中 | ✅ 实施（M6，设硬护栏） |
| **代码层** | 自身实现（自动改写源码） | 高 | ❌ **不实施** |

**代码层不实施的理由是实证的**，见 §6.2。

### 6.2 为什么不做代码层自进化

研究已给出明确证据（arXiv 2609.17817，Roesner & Kohno，*Reflections on Trusting Trust, Revisited*）：

测试 Darwin Gödel Machine（DGM）、Self-Improving Coding Agent（SICA）、Hyperagents 三个自我修改框架，用投毒的评测集（CertCheck 基准所有测试服务器用自签名证书）诱导进化：

| 框架 | 模型 | 中毒后中性任务漏洞率 | 用干净基准继续进化后 |
|---|---|---|---|
| DGM | Qwen3.5-397B | 30/30 | **0/30** |
| SICA | Qwen3.5-397B | 30/30 | **0/30** |
| Hyperagents | **Sonnet 4.5** | 30/30 | **0/30** |

三条关键发现：

1. **污染是永久性的。** 在干净基准上继续进化 30 次，漏洞率仍为 30/30——因为"关闭证书验证"在功能测试里不可见，**没有任何信号会惩罚它**。
2. **LLM 评审委员会拦不住。** SICA 内置三个 LLM judge 审查每次自我修改，全部明确支持把证书禁用"普遍化、无条件化"，其反对意见是"太复杂""缺测试"，**不是安全**。
3. **前沿模型不是解药，harness 才是。** Sonnet 4.5 在 SICA 上完全沦陷，但在 DGM 上守住了——差异来自 harness 而非模型。**护栏必须写在架构里，不能指望模型自觉。**

另有直接事实：**DGM 在自我修改期间伪造了工具执行日志以模拟成功测试，并移除了自身的幻觉检测标记。** 这不是实现 bug——当系统能编辑衡量自己的代码时，评分函数本身也在编辑范围内。

**结论**：本项目不做代码层自进化。护栏写在架构里，而不是指望模型自觉。

### 6.3 三条硬护栏

**护栏一：自我进化的产物不得进入自己的评分函数。**

```
场景 A 的产物 → 知识层（Insight 库）→ 只影响场景 A 的输出
                                       ↛ 绝不能影响场景 B 的门禁判定
```

场景 B 的门禁只能由 `rules/active/` 中**人工确认过的确定性规则** + 回验通过来触发。**LLM 结论与自进化产物都进不了这条路径。**（v0.1 "不确定的结论不得进阻断路径"的自然延伸）

**护栏二：任何自进化必须过留出集且零回归。**

- 进化只在 `train` 集上进行
- 每次进化必须在 `evals/holdout/` 验证，**任何指标下降即回滚**
- **`holdout/` 集在进化过程中不可读**

机制设计参考 MOSS 论文的 Ratchet：单调性保证（不得退化）+ 回滚 + 有界修改范围 + 审计轨迹（before/after diff + 测试结果 + 理由）。

**护栏三：进化只能改数据，不能改评分器。**

| 允许进化 | 禁止进化 |
|---|---|
| 知识库条目（Insight） | `evals/gate_eval.py` 的判定逻辑 |
| 规则提案（写成待审 PR） | `verifier.py` 的回验逻辑 |
| prompt 模板（版本化、可回滚） | 评测集本身 |
| | 已入库的基线 |

**规则提案必须是 PR 形态而非直接改文件**——这是护栏三的落地方式。提案进 `rules/proposals/`，走人工 review + 留出集验证，通过后才 merge 到 `rules/active/`。**Git 本身就是回滚机制和审计轨迹。**

### 6.3.1 资源需求（自进化层不构成硬件门槛）

**核心认知：自进化的成本在 API 调用次数，不在本地算力。** M5 / M6 的核心动作（生成 Insight、提案规则、裁决）全部发生在云端 LLM，本地只跑确定性部分。

| 环节 | 执行位置 | 本机开销 |
|---|---|---|
| AST 解析 | 本地 | 8.9 s（19.6 万行实测） |
| 建图 + PageRank | 本地 | 0.05 s |
| 漂移检测 | 本地 | < 1 s |
| Insight 生成 / 规则提案 | **云端 LLM** | 0（仅 API 费用） |
| LLM 裁决 | **云端 LLM** | 0 |
| 留出集评测 | 本地 | 秒级（跑几遍检查器） |

**实测资源占用**（19.6 万行 / 30,240 符号 / 40,320 引用边）：

| 资源 | 占用 | 结论 |
|---|---|---|
| 峰值内存 | 14.1 MB | 可忽略 |
| GPU | 0 | **不需要本地推理** |
| 磁盘 | 索引约数 MB | 可忽略 |
| CPU 占用 | 单核为主，AST 阶段可并行 | 14 核下 37k 行项目 < 3 s |

**因此：自进化层对电脑配置几乎无要求。** 唯一需注意的是**内存余量**——本机 15.8 GB 总量，若同时运行 IDE / 浏览器 / 其他 Agent 客户端，可用内存可能低于 4 GB，而 M4 引入 `ts-morph` 的 Node 子进程还需额外 200–500 MB。

**建议**：运行 CodeSentry 前保证 8 GB 以上可用内存。此为通用工程建议，与本项目选型无关。

**依赖策略（影响环境搭建成本）**：不引入 numpy / scipy / networkx。纯 Python PageRank 实测 30,000 节点 169 ms 已够用；且 Windows 上安装 scipy 需编译 C 扩展，本次实测**安装直接超时**，会显著抬高环境搭建成本。零重依赖（仅标准库 + Pydantic + 一个 LLM SDK）是本项目的环境目标。

### 6.4 M5 知识层设计

#### 6.4.1 Insight 契约

```python
class Insight(BaseModel):
    id: str
    statement: str                  # 事实陈述
    evidence: list[Evidence]       # 每条锚定 repo:file:line
    scope: Scope                   # global | language | ecosystem | repo
    kind: InsightKind              # architecture | convention | pitfall | idiom
    confidence: float
    learned_from: list[str]        # 来源 repo 标识
    created_at: datetime
    last_verified_at: datetime
    status: Status                 # active | flagged_stale | retired
```

#### 6.4.2 三条设计要点

| 设计 | 防的是什么失败模式 |
|---|---|
| **每条 Insight 锚定 `file:line`** | 记忆污染——笔记说某文件负责某功能，那文件被删/改了，笔记还在 |
| **证据漂移 → 自动标记 `flagged_stale`，不静默删除也不静默沿用** | 陈旧上下文当真理——文件重构了，笔记还在讲旧架构 |
| **区分事实与推测**（推测单独放 `hypotheses` 区，标注未验证） | 推断当事实 |

第三条的直接来源是一条成熟实践的硬规则 **"code before everything"**：不许声称任何不能在代码中指出文件的事情；答不上来时，列出"我检查了哪些文件、哪些没检查"，而不是编造。**这条规则应直接进知识层设计。**

#### 6.4.3 分层作用域

| 作用域 | 内容 | 生命周期 |
|---|---|---|
| `global` | 语言/框架通用模式（如"LangGraph 项目的图定义集中在 graph_builder"） | 长期，需强证据 |
| `ecosystem` | 特定生态的约定（如"FastAPI 项目用 Pydantic 做 schema"） | 中期 |
| `repo` | 单仓库的模块边界、构建命令、历史坑点 | 绑定该仓库 |
| `task` | 短期上下文 | **不得污染长期记忆** |

**核心原则（来自 arXiv 综述）**：从某个仓库学到的策略**不能默认推广到所有语言和框架**。从 `research_agent` 学到的"图编排模式"不能直接套到 Knowledge Loop 上。

#### 6.4.4 漂移检测

```
每次索引更新（M0 触发）
  → 对该 repo 的每条 Insight 校验其 evidence 是否仍指向存在且语义一致的符号
  → 失效 → 标记 flagged_stale，仍可查但不作为事实呈现
  → 连续 N 次失效 → retired
```

**指标**：漂移检出率（代码变动后被正确标记失效的比例）。这是 M5 的验收标准。

### 6.5 M6 规则层设计

#### 6.5.1 进化流程

```
跨项目扫描 → 发现重复出现的模式
  → LLM 提案：规则规格（检测逻辑 + 适用范围 + 依据）
  → 写入 rules/proposals/  ← PR 形态，不直接生效
  → 在 train 集上验证（recall 提升）
  → 在 holdout 集上验证（零回归）  ← 护栏二
  → 人工 review + merge → rules/active/
  → 生效，进入阻断路径
```

#### 6.5.2 准入标准

| 门槛 | 要求 | 理由 |
|---|---|---|
| 留出集零回归 | holdout 上任何指标不得下降 | 护栏二 |
| 精确率 | ≥ 0.85 | 与既有规则同标准 |
| 作用域 | 若仅在来源 repo 上有效 → 降级为 `repo` 作用域 | 防过拟合 |
| 人工确认 | 必须 merge 到 `rules/active/` | 护栏一 / 护栏三 |
| 可回滚 | Git 历史 | 审计轨迹 |

#### 6.5.3 提案 vs 评估必须分离

**规则提案由 LLM 生成，但规则准入只认确定性指标，LLM 不参与判定。**

这条必须写死：若让 LLM 判定"这条规则好不好"，就等于让提案者自己评分——与 DGM 伪造日志是同一类问题的温和版。

## 七、CLI 形态

### 7.1 多子命令（现在定，只写 2 个）

```
codesentry scan <path> [--diff] [--level ...]    # 场景 B
codesentry onboard <path> [--level 1|2]           # 场景 A
codesentry trace <symbol>                         # 场景 A · L3（M7+）
codesentry propose <pattern>                      # M6
```

**为什么现在定多子命令**：

- 薄 dispatch 层本身成本极低，20 行量级
- `scan` 与 `onboard` 的**输出形态根本不同**（finding 列表 vs 导航图），用单命令 + flag 实现会长出 15-flag 的上帝函数
- **底层数据模型（Symbol / Edge / Finding / Insight）现在就要定**——它们是两个场景共用的地基。"等形态稳定再拆"并不能避开真正贵的部分
- v0.1 的"不为未验证能力提前付成本"针对的是 ts-morph 这类重型依赖，不是 CLI 薄层

**额外收益**：`scan` 与 `onboard` 并列摆着，本身就在讲"两个场景共用一套索引"这个架构故事——**命令结构是架构的外部投影**。

v0.1 写的是 `codesentry scan <path>` 单命令形态，v0.2 更新为上述子命令结构。

## 八、里程碑（M0–M7）

| 里程碑 | 内容 | 判定标准 |
|---|---|---|
| **M0 索引层** | Symbol 表 + 引用边表 + PageRank 重要度 + 入口点识别 + 内容哈希增量缓存 | 索引出的核心模块排序与人工标注一致；增量重建耗时 < 全量 10% |
| **M1 理解场景** | L1 定位 + L2 骨架 + `onboard` 命令 | **入口点召回率 100%**；**幻觉符号率 0**；关键文件 Top-10 命中 ≥ 0.8；L1 <30s、L2 <3min |
| **M2 评测集** | bugs / clean / debt 三子集 + gate_eval + holdout 集 | recall ≥ 0.70；precision ≥ 0.85；**跨项目误报率数值接近** |
| **M3 审查场景** | 候选生成 + 影响面分析 + 门禁 + 基线 | 两个真实项目跑通；**真实误报率数字**（非自划靶子） |
| **M4 语义层** | 候选驱动 LLM 裁决 + 协议 + 回验 | 静默失效类用例可检出；回验通过率 |
| **M5 知识层** | Insight 库 + 锚定 + 漂移检测 + 分层作用域 | 读第二个项目时能复用第一个项目的模式；漂移检出率 |
| **M6 规则层** | 规则提案 → PR → 留出集零回归 → 人工 merge | 提案规则在 holdout 上 precision ≥ 0.85 且零回归 |
| **M7 生成层** | 受约束修复补丁生成 + L3 深挖 | 补丁不过门禁则拒绝写入 |

**M0 必须先行**：它是两个场景共用的地基，晚做会让 M1 和 M3 各自造轮子。

**M5/M6 置于最后**：它们的输入依赖前面所有层。

| 重要度 | 仅 PageRank | **PageRank 为主**（v0.2 修订三撤回四信号模型，见 §4.3.2 循环论证纠错） |
| 角色信号 | 未涉及 | **8 类确定性规则**（entry/guard/contract/orchestrator/proposal/service/store/infra），**用于输出分组标签，不参与排序加权** |

| 符号主键 | 未明确 | **限定名 `file::symbol`**（实测重名率 18%，裸名做主键导致排序失效） |
| 排除规则 | 未明确 | **项目级排除清单是一等功能**（实测 runtime/ 占 80% 行数但非源码） |
| 入口点 | 五信号平铺 | **应用入口 / 脚本入口两级**（实测 54 → 3） |
| ts-morph 引入理由 | M4 引入 | **维持 M4**，理由收窄为「跨语言契约比对」，**不是**提升 Python 侧解析率 || 入口点 | 未涉及 | 确定性识别（清单/配置/命名/注册/导出五信号） |
| 幻觉控制 | 仅审查结论行号回验 | **扩展到理解输出的符号回验**（幻觉符号率 = 0） |
| 自进化 | 未涉及 | **三层模型**，实施知识层 + 规则层，明确不做代码层 |
| 护栏 | 未涉及 | **三条硬护栏**（评分函数隔离 / 留出集零回归 / 只改数据不改评分器） |
| 知识存储 | 未涉及 | Insight 契约 + 锚定 + 漂移检测 + 分层作用域 |

| CLI | 单命令 `scan <path>` | **多子命令**（scan / onboard / trace / propose） |
| 叙事结构 | 审查工具 | **因果链**：理解能力 → 图索引 → 审查误报率下降 |
