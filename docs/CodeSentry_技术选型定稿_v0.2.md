## 一、本版变更摘要

v0.2相对v0.1新增理解场景、统一索引与受约束演进；修订八补环境/执行边界，修订十一把**本地网页工作空间**确定为主产品形态，修订十二增加文件读取与模型使用权限合同，修订十三分离启动角色、展示锚点与真实静态依赖距离，修订十四确定DeepSeek首轮接入与逐次确认的片段审查范围。

| # | 变更 | 性质 |
|---|---|---|
| 1 | **新增第二场景**（理解陌生项目），定位为优先级最高 | 场景扩展 |
| 2 | **新增 M0 索引层**，成为两个场景共用的地基 | 架构重构 |
| 3 | **新增自进化设计**（M5 知识层 + M6 规则层），附三条硬护栏 | 能力扩展 |
| 4 | **新增环境上下文与按需隔离执行**（修订八；静态部分已有实现、runner待验收） | 公共地基与执行边界 |
| 5 | **本地网页 + 每个代码目录独立工作空间**（修订十一，首版已有本机验收） | 产品入口与应用状态边界 |
| 6 | **完全排除 / 仅限本地分析 / 模型候选范围**（修订十二，本地实现完成并通过本机功能验收） | 统一文件访问、原文模型准备与存量确认；真实模型出口未接入 |
| 7 | **启动证据分层与分支阅读路线**（修订十三，P1整体仍未通过） | 有证据入口计算距离，装配/桥接补充分支线索，优先窗口保留完整清单 |

v0.1 的未撤销决策继续有效；修订九替换 Finding 信任字段、符号主键、指纹归一化与指标口径；**修订十补齐候选流程、评测隔离、diff 范围与云端数据边界**（§3.3–§3.5、§4.2、§5.5–§5.6、§6.3）。旧文档中的自报验证、前 N 行归一化、空输出 precision=1、LLM 筛选后才进入门禁、fix message 直接作标签及反复使用 holdout 调参等约定均由本版相应条款覆盖。

> **修订八状态**：本次确定「环境上下文 + 按需隔离执行」的设计与验收要求；环境画像、受控工具链和沙箱 runner **尚未实现**。现有 M0/M1 仅代表静态导航功能已落地，不代表已具备环境还原或隔离执行能力。

> **修订九状态**：本次仅修订前四项技术方案；相关代码、测试与验收脚本改造均待实施。P@10≥80% 的口径已由用户确认。以下新增契约是后续实施要求，不代表当前代码已符合，也不沿用旧数据宣称通过。

> **修订十状态**：本轮仅完善技术方案，不修改代码或新增实现测试。新增约束均待实施；历史实测只说明当时的实现与样本，不证明新契约通过。已确认的 P@10≥80% 保持不变；不确定的样本规模、模型、预算与后端能力在第十节列为待验证事项。

> **修订十一状态**：用户已确认本地网页形态。新增工作空间、API与前端的目标合同，并前置到P1实施；导航、审查和漂移既定指标保持不变。240项测试及P@10的50%/60%是此前内核开发快照，不代表新工作台通过。

> **修订十二状态**：用户已确认同时提供“完全排除”与“仅限本地分析”。统一AccessPolicy、权限UI、旧工作空间确认及撤销传播已实现，已通过本机功能验收；全量359通过/1跳过、前端26通过、真实浏览器4通过，独立证据见权限实施记录。模型范围仅有重新读取原文的本地准备入口与mock检查，无真实模型/embedding调用，也无可信衍生内容构造器。P1.7–P1.9及原278项后端、19项前端、3项浏览器测试只作历史记录；导航质量未重验，P1整体仍未通过。

## 二、场景定位

### 2.1 两个场景

| | 场景 A · 理解 | 场景 B · 审查 |
|---|---|---|
| 用户是谁 | 刚接手一个陌生项目的人 | 提交代码前需要把关的开发者 |
| 核心问题 | "从哪开始读？" | "这次改动有没有问题？" |
| 输出 | 导航图 + 阅读顺序 + 关键路径 | Finding 列表 + 影响面 + 门禁判定 |
| 优先级 | **高（先做）** | 中 |

### 2.2 场景定位的确认

用户明确：**主要目的是用这个 agent 帮助理解其他项目的代码**。审查场景降为第二优先级，但保留——因为它是"能作为 CI 门禁"这一工程说服力的来源，且与场景 A 共用同一套索引。

### 2.3 场景连接与待验证价值

场景 A 先提供项目骨架、阅读顺序与有证据的依赖关系；开发者修改后，场景 B 复用索引辅助影响面与候选审查。两者共享结构事实，但导航推荐不自动成为门禁事实，语义解释也不自动获得阻断资格。

“更快理解项目”和“图索引降低审查误报”是待验证的产品假设。当前仅有静态导航实现与代理指标历史测量，不能宣称已经五分钟读懂或已把误报从 X 降到 Y。验证方式见 §5.6.4。

### 2.4 技术机制对照与取舍（修订十纠正）

原稿将产品固定分为 diff-only、纯向量、自由探索、图索引四类，并比较不同任务的百分比；这种分类与唯一性结论撤回。CodeRabbit 官方已描述代码图与全仓上下文，Greptile 官方也描述依赖图，不能再按单一检索机制代表其全部能力。[CodeRabbit 官方说明](https://www.coderabbit.ai/blog/context-engineering-ai-code-reviews)、[Greptile 官方说明](https://www.greptile.com/docs/introduction)

| 可组合的机制 | 本项目取舍 | 需要验证的边界 |
|---|---|---|
| 变更范围与周边上下文 | 用于差异入口，保留基点与目标快照 | diff 不是全部证据，必须处理删除、配置变化及跨文件影响 |
| 静态符号/依赖图与排序 | 作为默认本地导航基础，借鉴 Aider 的图与预算裁剪思路 | 图有不完整和错误绑定风险，中心性不等于关键性或语义正确 |
| 向量/语义检索 | 首版暂不建设，减少工具与评测变量 | 检索返回的代码仍可定位验证；相似度或图边本身均不能证明结论正确 |
| 按需工具探索与动态验证 | 受任务范围、可信策略、runner 与预算限制 | 自由探索不默认阻断；可复现性依赖输入/工具链/策略固定及证据记录 |

Aider 的 repo map 是本项目可借鉴的机制实例，不是本项目精确率的证明。[Aider repo map](https://aider.chat/docs/repomap.html) 没有同任务、同版本、同标签与同预算的独立对照前，不比较竞品检出率/误报率，不宣称本项目是“唯一可复现且可阻断”的方案。可进入 CI 来自明确状态与门禁策略，不由检索路线自动保证。

### 2.6 主产品形态：本地网页工作空间（修订十一）

用户选择启动本地服务后在浏览器使用。打开一个代码目录即创建或重开其工作空间，在同一界面浏览文件、阅读代码、运行静态分析、查看环境与导航，并逐步接入真实审查能力。

主流程是“项目列表 → 工作空间 → 代码/结构/分析任务”。工作空间指向授权源目录，源码默认只读；配置、任务、快照、结果和UI状态独立关联。相同canonical root重复打开复用工作空间，独立目录或worktree分开。产品界面提前交付，CLI继续作为自动化与诊断入口。

这会调整交付顺序：先形成工作空间导航版，前端不再只是M7末期的报告展示。结构接口稳定即可开发API/UI；旧文档代理P@10未达标不阻塞独立UI开发，也不因此降低80%门槛或将P1整体改为通过。完整目标见[工作空间与本地前端方案](CodeSentry_工作空间与本地前端方案_v0.1.md)。

### 3.1 分层职责

| 层 | 职责 | 关键约束 |
|---|---|---|
| **工作空间/应用层** | 授权代码目录、独立状态、任务与API | workspace身份贯穿请求/快照/结果，源只读，本地单用户 |
| **前端层** | 项目选择、代码阅读、分析导航与任务状态 | 消费结构化API，不自行提升结论可信度或执行源码 |
| **环境层** | 项目边界、运行时/依赖/配置、环境画像 | 声明与实际观测分开；默认只读发现 |
| 解析层 | 把代码变成结构化事实 | 原生 AST；工具来源受控；显式报告解析不完整 |
| **执行层** | 为测试、构建、运行探针提供隔离与证据 | 按需启用；项目代码、插件及安装构建不得绕过 runner |
| **索引层** | Symbol 图、引用边、重要度、增量缓存 | **两个场景共用的地基** |
| 规则层 | 判定与跨语言比对 | 只读 `rules/active/` |
| 语义层 | LLM 裁决 / 叙事 | 结论必须锚定证据 |
| 门禁层 | 确定性判定 + 基线 | 不接受不确定结论 |
| 知识层 | 沉淀认知 | 锚定 + 漂移检测 + 分层作用域 |

### 3.2 环境上下文与隔离执行（修订八方案）

当前P1已实现只读画像、受控语法工具链与部分恢复/缓存契约；配置/类型关系还原和runner仍未实现。静态功能的实现不代表本节全部动态反例通过，证据见执行台账。

**决策：环境上下文进入公共地基；隔离执行作为按需能力。** 是否执行由要回答的问题决定。静态导航不要求先安装并启动整个项目；类型解析、测试与行为验证需要相应环境，并声明结论适用范围。

#### 3.2.1 问题、反例与当前证据

“代码理解不能脱离环境”对运行行为成立，但不意味着所有理解都要执行：未安装依赖时仍能提取函数、入口候选与 import 关系；依赖版本、编译选项、平台分支及外部服务则可能改变实际行为。TypeScript 官方 API 将源码 AST 与基于 Program 的类型检查分开，这也是本项目分层的依据。[TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)

当前架构并非完全没有环境依赖，而是**已有依赖、缺少显式模型和执行边界**。2026-10-23 接手核查发现：

- CodeSentry 自身补装 pytest 后，54 项单测通过；这仅证明分析工具的开发环境可用，不能证明被分析项目能运行。
- `research_agent/frontend/node_modules/typescript` 存在，但解析器仅从项目根与父目录查找。本轮 32 个 TS 文件返回 `unknown`，`parse_failures` 仍为 0，错误结果还可能被缓存。问题同时涉及项目边界发现、失败反馈与缓存恢复。
- 当前 TS 子进程通过 `NODE_PATH` 查找并 `require("typescript")`，还继承宿主环境变量。**加载目标项目的工具包本身就会执行包内 JavaScript**，即便没有运行目标业务入口，也已经跨过代码执行边界。[Node.js 模块加载](https://nodejs.org/api/modules.html)

反例也必须保留：把项目装进 Linux 容器，并不能验证 Windows 专属路径、原生模块或 Electron 桌面能力。**隔离强度与环境匹配度是两个独立维度**，执行成功不等于已还原目标环境。[Microsoft 容器与虚拟机说明](https://learn.microsoft.com/en-us/virtualization/windowscontainers/about/containers-vs-vm)

#### 3.2.2 三种环境与环境画像

| 对象 | 记录什么 | 不得混淆的结论 |
|---|---|---|
| 分析工具环境 | CodeSentry、Python/Node、解析器版本及可信来源 | 分析器能启动，不代表目标项目可运行 |
| 目标项目环境 | 子项目边界、声明的运行时范围、锁文件、编译/模块配置、服务与平台要求 | 清单声明不是已安装状态；dev/test/prod 配置分别描述 |
| 实际执行环境 | runner 后端、OS/架构、工具链/镜像身份、实际依赖与服务、资源/网络限制 | 只有实际运行过的环境和任务可以标为已观测 |

最小环境画像包括 `project_units`、`declared`、`observed`、`unknowns`、证据路径与环境指纹；字段实现时用薄契约，不提前建设通用环境调度平台。

默认发现只读取 `pyproject.toml`、requirements/锁文件、`package.json`、工作区声明、`tsconfig*.json`、版本文件及 CI/容器配置等文本。按工作区和源码归属识别 `frontend/` 等子项目，再解析其配置；锁文件缺失或配置冲突时保留未知。**不执行 `setup.py`、JS 配置文件、项目解释器或项目插件来“读取配置”。**

只提取配置所需的环境变量名称与非敏感默认项；不读取或复制 `.env` 密钥值，不把完整宿主环境、用户凭据或生产数据库带入分析和 runner。运行服务依赖记录为待满足条件，需要执行时再使用专用测试数据与服务。

#### 3.2.3 能力分层与结论边界

| 能力 | 所需环境 | 可以输出什么 | 失败如何表达 |
|---|---|---|---|
| **静态导航（默认）** | 环境声明 + CodeSentry 受控解析工具链 | AST 事实、候选入口、依赖骨架、阅读顺序 | 逐文件标注缺失/不兼容/语法失败；保留其余可用结果 |
| **配置与类型解析（按需）** | 子项目配置、匹配的分析器与必要类型声明 | 受当前配置支持的模块/类型关系 | 缺依赖或配置无法解析时标为部分结果，不推断运行行为 |
| **动态验证（显式选择任务）** | 匹配目标要求的隔离环境、依赖、测试服务 | 特定输入下的测试、构建或运行观测 | 区分环境未就绪、测试失败、超时、资源耗尽及不支持平台 |

输出必须区分 `static`（静态事实）、`resolved`（配置/类型解析）和 `observed`（运行观测），并带适用环境。未执行、未覆盖或缺环境均不是“通过”。动态测试只证明记录的环境、输入和断言，不自动证明架构解释正确，也不自动获得 Finding 的阻断资格；既有确定性来源与回验门槛继续有效。

缺少沙箱时仍可使用受控工具链生成静态导航；请求动态验证而后端不可用时，返回明确的未执行状态，**不得静默退回宿主机执行**。静态读取同样不是对任意恶意输入的安全保证，需设文件大小、任务时间和解析进程资源边界；Python 官方说明复杂 AST 输入可能耗尽栈并使解释器退出。[Python ast](https://docs.python.org/3.14/library/ast.html)

#### 3.2.4 解析工具链与执行边界

默认 TS 语法解析改为使用 **CodeSentry 管理、来源可核验且版本明确的 TypeScript**；源码作为数据传给解析器，模块搜索路径不得落入被分析仓库或继承其 `NODE_OPTIONS` / `NODE_PATH`。Python 同样使用受控解释器，避免从目标工作目录导入同名模块或加载启动钩子。此项撤销“默认加载目标 node_modules 以保持零新增依赖”的取舍；TS 支持可以按需安装受控工具链。

项目声明的 TypeScript/Python 版本用于兼容性判断；所选工具不支持目标语法时报告不兼容。必须使用项目自带编译器、解释器或插件时，转入隔离执行，并记录与默认工具链的差异。类型解析读取类型声明本身不等同运行项目；其中如需加载插件、可执行配置或构建生成声明，则按执行任务处理。

**下列动作均进入执行边界**：导入目标模块、加载目标工具/插件、安装或构建目标依赖、收集并运行测试、启动服务、生成补丁后的验证。新建子进程或 `.venv` 不能代替 OS 访问隔离。Python `venv` 提供的是独立包环境；pip 的构建隔离仍会调用构建后端；npm 禁用生命周期脚本也不阻止显式运行测试脚本。[Python venv](https://docs.python.org/3.14/library/venv.html)、[pip 构建接口](https://pip.pypa.io/en/stable/reference/build-system/)、[npm ci](https://docs.npmjs.com/cli/commands/npm-ci/)

#### 3.2.5 沙箱选型与最小执行契约

**首个后端选择 Docker runner，先覆盖 Linux 上可验证的测试/构建任务；完成隔离与平台验收后再启用。** Docker 不成为默认 onboard 的安装前置。Windows 上使用 Docker 的 Linux 后端时，报告实际 guest OS；Windows/Electron 专属任务需要匹配的 Windows 隔离环境另行选型，未支持时明确报告。远程执行与多后端调度暂不建设；如未来使用远程后端，代码上传权限必须独立处理。

容器配置会影响隔离程度，不能以“用了 Docker”作为任意不可信代码的安全证明。首版仅在已声明威胁模型和测试范围内开放；若面向恶意公开仓库执行，应评估具有独立内核的 VM/强化隔离后端，未达到所需边界就不执行。[Docker 安全说明](https://docs.docker.com/engine/security/)、[Microsoft 隔离模式](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container)

最小 runner 契约只覆盖这些职责：

1. **任务与策略**：上层传入结构化命令参数、工作目录、源快照、环境和限额；策略由 CodeSentry 可信配置与当前会话授权决定，仓库配置不能自行提升权限。执行授权可按项目和任务持久化，无需重复询问，但不得隐式扩展到联网、密钥或额外挂载。
2. **文件系统**：从有内容清单的源码快照生成隔离工作副本；副本可按任务需要写入，原项目与工具安装目录不可写回。默认排除凭据、宿主依赖与无关文件；处理符号链接、junction 和越界路径，不透传宿主用户目录、设备或 Docker socket。
3. **进程与网络**：使用非特权身份，限制 CPU、内存、进程数、执行时长和输出量；取消或超时必须回收进程树及运行资源。验证阶段默认断外网，允许的测试服务仅在受限内部网络；服务不可用不能被误报为代码缺陷。安装阶段的源访问另设白名单，不开放通用外网。
4. **准备环境**：首版仅使用可信预制基础镜像并固定其身份，优先按锁文件恢复依赖；没有锁文件则记录本次解析版本并标注复现限制。目标依赖安装、生命周期脚本及应用构建命令均在 runner 内执行。项目 Dockerfile/容器配置只作环境声明读取；镜像构建需要独立的 build 后端隔离验收，首版不支持直接执行项目 Dockerfile，运行容器的限制不能被视为已覆盖镜像构建。
5. **结果与证据**：由 runner 记录命令、平台、环境/源快照指纹、退出状态、有效测试/断言数和有界日志；证据文件也按不可信数据读取并脱敏。区分 `not_run`、`unavailable`、`unsupported`、`environment_error`、`failed`、`timeout`、`cancelled` 与 `passed`；环境不匹配、未收集有效测试或必要断言未运行时不能记为验证通过。构建等非测试任务按其明确成功条件判定。

Docker 默认不会替任务配置资源上限，需要显式设置；网络隔离与只读挂载也需要配置并检查后端实际能力。限额、网络或挂载策略无法满足时拒绝执行。[资源限制](https://docs.docker.com/engine/containers/resource_constraints/)、[隔离网络](https://docs.docker.com/engine/network/drivers/none/)、[挂载权限](https://docs.docker.com/engine/storage/bind-mounts/)

#### 3.2.6 实施顺序与验收反例

环境画像、解析完整性与缓存恢复先纳入 **M1.1 环境闭环**；runner 在首个执行任务之前验收，之后供 M2 历史用例复现、M3 审查和 M7 补丁验证复用。这里只确定一个执行边界，不在当前阶段实现自动环境修复、生产服务复制或通用多平台编排。

| 反例/测试 | 验收要求 |
|---|---|
| 无目标依赖、无 Docker、离线仓库 | 受控解析工具已就绪时仍可输出静态导航；动态能力明确未执行 |
| `frontend/` 才有 TS 配置和锁文件 | 正确识别子项目，报告声明与实际工具链；不把宿主版本当项目版本 |
| TS 缺失/不兼容后恢复，源码未变 | 失败可见；恢复后能重新解析，不复用先前失败的空缓存 |
| 仅改锁文件、tsconfig 或解析器版本 | 对相关解析/解析关系/执行证据正确失效，未受影响的纯语法缓存可保留 |
| 假 TypeScript 包、NODE_OPTIONS 注入、导入副作用、测试收集钩子 | 静态模式不加载仓库可执行物；需要加载时只能通过 runner |
| 尝试越界写、读取宿主凭据、外联或遗留子进程 | 在声明支持的平台验证拒绝/隔离和回收，宿主源码不变 |
| Windows/Electron 任务被放入 Linux 环境 | 标注环境不匹配，不把容器启动成功算目标功能验证成功 |
| 命令退出 0 但无测试、安装失败、服务缺失、超时或取消 | 各自保留状态与证据，不折算为通过，也不自动归因项目 bug |

以上是完整目标清单。P1静态画像、工具链和缓存恢复已有相应反例；P2后端已有本机合成只读/外联/限额/超时取消与状态检查，真实项目适配、有效断言和Windows/Electron仍待验收，不能将整表标为已通过。原有54项是历史基线，最新证据分别见P1复测和P2交付记录。

### 3.3 证据、身份与验收契约（修订九；信任与指纹首版已实施）

#### 3.3.1 Finding 的信任字段由可信流水线决定

**已实施的首版约束**：模型输出与可信报告模型分开，`LLMFindingDraft`拒绝模型填写`source/verified/extraction/fingerprint`等字段与其他额外字段。转换来源只能为LLM/Explore。`Finding`默认`source=unknown/confidence=0/verified=false`；JSON的verified仅属报告提示，不能恢复资格。`VerificationContext.evaluate()`独立重算可生成确定性结果，`verify()`处理外来数据时只返回无阻断凭据警告；当前生产规则均为report-only。具体证据见P3实施记录，最终gate仍待后续。

拟由可信扫描流程创建验证上下文，绑定项目根、规则身份/版本、源码快照与可信规则实现。验证时须核对项目内实际文件、行号、证据片段，并重新判定规则条件及符号绑定；首版拟用**不序列化的进程内凭据**表达最低验证资格。阻断资格检查必须绑定当前上下文；来源、置信度、Finding 内容、证据源码或规则上下文不匹配时不得复用凭据。规则实现不得来自模型或目标仓库配置；规则还依赖的其他源码、配置与环境事实须纳入完整规则输入快照。

**最低资格不等于最终门禁。** M3 的 gate 还须核验 active 规则、可信策略、规则适用范围、源快照一致性和已批准基线；只有所声明必检范围完整时才能给出通过，已确认的阻断项不会因其他部分不完整而被隐藏。源码变化后须重新验证；扫描中途变化应重试或标记不完整，不能只等待下次 status。该进程内机制不能代替 OS 沙箱，也不对已能执行任意 Python 的调用方提供隔离保证。

**验证对象是规则结论，不是模型叙述。** 可信规则须重算位置、提取事实、规则触发条件及允许的严重级别；不能给模型提供的原因或级别直接盖章。确定性只表示在固定输入下可复现，不能证明规则零误报；confidence 是报告信号，不能当作验证概率、规则准入或单独的阻断凭据。行数超阈一类政策违规与可复现的行为缺陷须分开标注。

#### 3.3.2 问题身份与本次证据分开

| 内容 | 目标契约（v2与只读建议已有首版，批准流程待完成） |
|---|---|
| 问题身份 | 问题身份由规则身份、完整作用域符号、结构锚点及重复出现序号共同构成；符号必须包含完整作用域，结构锚点由规则提供，同锚点的重复问题保留出现次数，不能集合去重后全部豁免 |
| 证据哈希 | 覆盖规则实际依赖的完整源码/片段、提取事实、规则/策略/分析器、语言/方言与归一化版本及适用配置/环境身份；跨文件规则须覆盖相关文件和否定证据（如缺失声明）。物理行数等 AST 不保留的度量必须进入 facts |
| 版本与调用边界 | 拟升级为带版本的 v2 SHA-256 摘要，分开存储问题身份与证据，并提供组合摘要；符号级默认锚点不得用于合并同符号内的多处问题，多处问题须保留独立结构锚点与出现序号 |
| 语言归一化 | 归一化须相对于具体规则证明等价。Python 可用完整 AST，保留控制流、字面量、类型注释和影响规则的指令；物理行数、编码/源码格式规则须另纳入原始事实。含 `type: ignore`、抑制指令或不完整片段等无法可靠等价的情况保留完整源码；首版 TS/其他语言同样保守处理 |
| 基线迁移 | 旧 `sha1:` 指纹与 v2 不兼容，禁止自动继承豁免；旧基线须重新生成并审阅。版本未知的摘要仅供报告，不应被未来 gate 用作已批准豁免 |

哈希只标识输入一致性，不授予可信来源、验证或豁免权限。P3首版已实现v2指纹与只读迁移建议；baseline批准存储、生效豁免和完整跨版本匹配仍待实施。未来复用豁免必须同时检查仓库/路径作用域、问题身份、证据与规则/策略版本，证据变化先重新判定，不能因身份相同跳过检查；复制同一问题一份必须增加匹配次数。基线须记录审阅人、理由、批准范围和版本；存量问题清单不等于自动豁免，基线更新不得与本次被检查改动一起自动批准。重命名、移动或重复定义顺序变化无法唯一匹配时，标为待重审，优先重新打开问题。

#### 3.3.3 两条判定路径与门禁状态（修订十；待实施）

| 路径 | 处理方式 | 对门禁的影响 |
|---|---|---|
| 已准入的确定性阻断规则 | 在可信输入快照上运行并重验，按可信策略和已批准基线判定 | 独立于模型执行；LLM 否定、超时或不可用均不得删除、降级或豁免该结论 |
| 语义候选与 explore | 确定性触发器提供位置与事实，LLM 给出带证据的草稿，回验后作为警告 | 不自动升级为 deterministic；发现可形式化的新规则也须先走规则提案与人工准入 |

因此撤销 v0.1 中“所有候选先经 LLM 裁决，再合并进入门禁”的单通道流程。结构化输出只保证数据形状，片段回验只保证位置可复现，两者均不证明语义判断正确。模型失败不得使确定性门禁静默失效；语义警告是否完成另行报告。

| 最终状态 | 条件 | CI 行为 |
|---|---|---|
| `pass` | 声明必检范围完整，可信规则均完成，快照一致，且无未豁免阻断项 | 才可返回成功；不声称证明不存在未知缺陷 |
| `block` | 存在可信规则确认的新阻断项 | 返回非零；同时保留可能存在的解析/语义不完整信息 |
| `incomplete` | 无已确认阻断项，但必检解析/规则缺失、超时、范围截断或快照变化 | 返回非零，说明缺少什么；不归因为目标代码缺陷 |
| `error` | 输入/配置非法、差异基点不可确定或工具内部失败 | 返回非零并报告错误，不输出通过结论 |

必检清单须由可信策略明确给出；空清单、全部被排除/禁用或无适用规则须说明未评估/不适用，不能利用空循环宣称门禁验收通过。CLI 的数值退出码在实现时固定，并与 JSON 状态一致；`onboard` 可展示部分结果，但必须显式标记覆盖边界，不能套用门禁通过状态。必检范围、阻断策略、active 规则及基线必须来自可信已审版本，不能由被审 PR 修改后立即生效；仓库自带规则/配置仅作候选输入，不能自行降低要求。

### 3.4 diff 范围、快照与影响面（修订十；待实施）

`scan --diff` 是规划接口。报告必须记录基点、目标快照、范围模式和排除策略，不把不同差异模式混为一次评测。

| 模式 | 基点 → 目标 | 范围约束 |
|---|---|---|
| 全量 | 无差异基点 → 当前声明源码快照 | 使用明确的扫描清单，记录未支持语言、排除与失败 |
| 本地 diff（默认差异模式） | HEAD → 当前工作区快照 | 包含已暂存及未暂存的净变化；新文件按发现规则单独纳入，不能只调用默认 git diff 而漏掉暂存/未跟踪文件 |
| PR/CI diff | 指定 base/head 的 merge-base → 指定 head 提交 | 不混入本地脏工作区；须有明确提交身份，基点缺失或多义时停止并要求显式选择，不静默改用 HEAD~1 |

Git 的默认工作区差异、暂存差异与两提交差异语义不同，merge-base 也可能不唯一；上述默认是本项目的设计选择。[git diff](https://git-scm.com/docs/git-diff)、[git merge-base](https://git-scm.com/docs/git-merge-base)

变更行只作为候选入口，不能限制所有证据只能来自 diff。调用/导入影响面须结合基点与目标快照：删除文件/符号从旧图追踪存活调用者，新增与修改从目标图追踪；重命名保留前后路径，不自动继承豁免。配置、锁文件、导出接口或规则变化须重新评估关联范围。未知/启发式边可以提示人工探索，但不得被展示为确定影响链。

首版不默认自动 fetch、重置目标工作区或加载 Git 的外部 diff/textconv 驱动；历史快照读取不得触发仓库可执行钩子。无法覆盖的子模块、LFS 内容、生成文件或不支持语言须报告，不能当作零变化。超出依赖遍历、文件或时间预算时列出截断项并标记不完整；必检范围不能靠 Top-K 候选预算静默缩小。暂存区专用模式等扩展在参数实现前不承诺支持。

### 3.5 模型调用、仓库内容与数据留存（修订十、十二；本地权限已实现，真实模型待接入）

**本地优先的含义**：默认 L1/L2 与确定性规则在本地运行；云端语义能力按项目显式启用。启用一次可持久化已确认的服务、用途与数据范围，扩大到新服务或新范围时重新确认。缺少授权或密钥时仍提供静态结果，并把语义能力标为未执行；不能暗中发送源码。

**修订十二文件权限合同与实现**：详细规则以[工作空间方案§3.1](CodeSentry_工作空间与本地前端方案_v0.1.md#31-文件访问范围)为准，本轮本地实现完成并通过本机功能验收，实际行为与局限见[实施记录](execution/P1_文件访问权限验收.md)。新工作空间默认只启用本地静态功能，默认没有模型可用候选范围；未显式启用模型并确认其可用范围前，任何模型不得读取项目内容。当前不接入真实模型。

| 文件权限 | 允许范围 |
|---|---|
| `exclude` · 完全排除 | 不读取内容，不计算内容哈希，不解析、索引、缓存、记录内容日志或提供给模型；不能为环境发现、旧缓存复用或生成摘要而绕过 |
| `local_only` · 仅限本地分析 | 可作本地确定性处理；任何模型及embedding均禁止使用，包括本地模型、源码片段及其符号、摘要、调用图等衍生信息 |
| `model_eligible` · 模型候选范围 | 仅表示可被选入模型输入范围；仍须具体模型服务、用途与数据范围授权，不构成自动发送许可 |

默认执行工作空间root与允许遍历目录内的嵌套`.gitignore`；已被Git跟踪但命中规则的文件同样排除，这是权限规则而非Git索引语义。首版不自动读取宿主全局Git配置、`.git/info/exclude`或工作空间外规则，须记录适用范围。`.gitignore`不是机密清单，另设独立敏感文件默认排除；硬拒绝和用户拒绝优先，`!`只改变Git规则匹配，不解除用户`exclude`或`local_only`。仓库自带配置不能授权扩大访问范围。多来源产物继承其中最严格的使用限制；无法证明逐条来源时不得默认模型可用。

`.gitignore`控制文件同样受`exclude`限制，不得为了规则匹配或敏感检测读取禁读内容；规则文件被禁读、为链接或不可解析时，对受影响范围保守阻断并提示待确认，不能静默全放行。模型侧需要的结构上下文必须从model_eligible来源重算或证明可分离，混合来源不明的结果只能按本地范围处理。

当前模型实现范围进一步收窄：只有重新读取当前获准候选文件的原文准备函数与mock调用检查，不存在真实云端、本地模型或embedding transport。外部传入的摘要、图、历史结果字典等衍生内容全部拒绝，即使自报来源允许也不接受；可信衍生内容构造器尚未提供，上段结构重算是后续接入要求，不能据此宣称已支持衍生内容发送。

| 数据/动作 | 边界 |
|---|---|
| 仓库源码、注释、README、日志、依赖元数据和模型返回 | 均按不可信数据处理；其中的指令不能改变系统策略、工具权限、基线、评分器或发送范围 |
| 模型及embedding输入 | 云端与本地模型统一检查当前文件权限、衍生来源、具体服务/用途授权；仅提交获准的候选事实与最小证据。发送前脱敏并提供清单，脱敏不能替代授权或解除`local_only`；禁止 `.env` 密钥值、凭据文件、生产数据和未许可路径 |
| 外部链接与工具调用 | 仓库或模型提供的链接不自动抓取，模型建议的命令不直接执行；只有可信调度器能按既有 runner 与网络策略选择工具 |
| 本地缓存、索引、报告、Insight | 同样可能含标识符、签名、路径及代码片段；默认在用户目录按仓库隔离，不自动提交/同步，提供明确位置、保留/清理策略与缓存禁用方式 |
| 日志与模型结果 | 默认不记录完整提示词/源码；调试留存须显式开启并限定范围。记录服务/模型、提示词版本、证据摘要、预算与状态；重试次数、并发、token/费用预算有界，超预算不伪装完成 |

只记录引用位置不能证明“无敏感信息风险”。用户已选DeepSeek；片段审查逐次确认具体片段及用途，项目对话另按§3.5.2确认持续授权。供应商留存/训练承诺未知处明示，组织限制与金额上限不能靠请求数预算代替。不声明供应商已满足零留存要求。规则与解析缓存按 §4.5.3 失效；模型输出缓存还须绑定模型/提示词、证据与授权策略身份，历史输出不能恢复验证或阻断资格。

权限版本贯穿任务、缓存、结果与准备入口。收紧权限先由服务端拒绝旧产物访问并停止旧任务，不只修改下一次扫描；当前实现对所有策略变更都保守失效该空间全部旧分析与日志，并清理受管结果，而非保留仅变为`local_only`的历史。受管清理失败时访问保持关闭并显示待清理，不能继续提供旧内容；源文件不被删除或改写。浏览器同页保存时先清空旧内容，其他页面依靠版本轮询清除，服务端不等待轮询才拒绝。最终缓存并发隔离验证与完整回归另行汇总，不能用旧测试证明不同scope下的并发一致性。删除不承诺介质级安全擦除，已经外发的数据不能撤回。当前mock只证明本地准备入口边界，不得宣称真实模型API验收通过；P4接入时必须复用同一策略再验证真实出口。

### 3.5.1 DeepSeek 首轮接入与密钥配置（修订十四、十五）

采用固定官方HTTPS Chat Completion地址，`deepseek-flash`为默认、`deepseek-v4-pro`可选，非流式/关闭思考/JSON模式；不跟随重定向、不自动重试、没有模型工具调用。[官方接口](https://api-docs.deepseek.com/api/create-chat-completion/)

每工作空间独立设置和会话预算，默认禁用，`model_scope`默认空。服务启动可读取CodeSentry固定目录`.env`、显式`--env-file`或优先的`DEEPSEEK_API_KEY`环境变量；不自动加载被审项目环境文件。工作空间页面输入仅作服务内存临时覆盖。选一个文件及连续片段，显示完整请求后逐次确认；原文件任意字节、权限版本或模型设置改变，预览与迟到结果都不能沿用。严格schema和原文引证核对只产生未验证警告，不能取得确定性结论、门禁或批准资格。首轮不提交符号/图/旧摘要等衍生上下文。

片段120行/8KiB、输出1024token、请求30秒/0重试、响应256KiB；每工作空间每次服务最多3次请求、预留32768token，失败不退预算。重启会重置预算，尚未实现跨重启账单硬限额。长期密钥由用户保存在Git忽略的可信`.env`或系统启动环境，服务只读并持内存快照，不存数据库、不回显或导出给分析worker/执行后端；修改文件重启生效。清除当前空间同时移除临时覆盖、持久抑制启动密钥回退；显式“使用启动配置密钥”才恢复，其他空间不受影响。关闭或清除设置会取消在途并清理模型历史，访问范围变更沿用全历史清理，失败保持关闭。

官方说明上下文缓存默认开启，通常数小时至数天清理未使用缓存；不能由此推断全部数据零留存或禁止训练。确认页显示提示及来源，具体留存/训练承诺未独立核实。[缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

本轮以工具合成代码与本机HTTP服务验证通道和权限；没有真实DeepSeek调用、真实质量/费用测量。真实试用和阶段质量评估仍属P4后续任务，见[实施记录](execution/P4_DeepSeek接入与P3开发交接.md)。

## 四、M0 统一索引层

### 4.1 为什么索引层必须先于两个场景

v0.1 的场景 B（审查）有一个未解的设计缺口：**"改这个函数会影响谁"需要跨文件影响面分析，而那需要图索引。** v0.1 未设计该能力，因为当时只有审查一个场景。

加入场景 A 后，图索引成为两个场景共用的地基——**场景 A 把它当作"我要读什么"，场景 B 把它当作"改这里会波及什么"。**

### 4.2 三张表

| 表 | 内容 | 用途 |
|---|---|---|
| **Symbol 表** | 符号名、种类、文件、起止行、签名 | 骨架摘要、符号检索 |
| **引用边表** | `(from_symbol, to_symbol, file, line)` | 调用图、重要度计算、影响面 |
| **文件元数据** | 路径、语言、行数、import/export 列表、是否测试 | 入口点识别、规模统计 |

**修订九设计要求（待实施）：符号主键须包含完整词法作用域**，如 `file.py::A.save`、`file.py::B.save`、`file.py::outer.inner`；同作用域重复定义/重载须有各自的定义记录；TS 重载声明与运行实现分别标记。`parent` 与调用归属必须使用相同身份。文件路径应相对扫描根，并包含子项目路径。旧的仅 `file::叶子名` 方案不能保证唯一。

**唯一性与跨版本稳定分开验收。** 单次快照内定义身份、父子关系及边端点必须唯一、自洽；跨编辑不承诺身份永不变化。重复定义插入/重排或移动后须做一对一匹配，匹配不唯一就重新核验，不能按出现序号把旧豁免转给另一处定义。

> **实测依据（v0.2 修订）**：裸符号名做主键时，实测项目 1,206 个定义只有 990 个唯一名（**重名率 18%**），`get` 在 8 个文件里各定义一次 → 图节点被合并 → PageRank 变成"给最常见的词打分"（实测 Top1 是 6,101 行的测试文件，核心符号全是 `get`/`append`/`list`）。改限定名后 Top12 全部命中真实架构组件。详见 `CodeSentry_索引层实测报告_v1.0.md` §三。

**绑定分层设计（待实施）：确定绑定与启发式必须分开记录。** `local` / `cross_file` 仅允许用于有证据支持的词法/导入绑定；仅全局同名唯一、目录相近等猜测标记 `heuristic`，多候选保留 `ambiguous`。未知对象接收者的方法不得冒充本地同名方法。确定图与 PageRank 不纳入启发式边；不能因为“有调用发生”就猜出目标文件。没有真实类型信息时，所支持绑定范围之外继续保留未知。解析率与已解析边的正确率是两个指标，后者尚需独立标注。

“确定”限定为声明环境与受支持语法内可证明的静态名称绑定，不代表调用实际发生、分支可达或运行时接收者必然如此。原始调用点须保留接收者表达式、导入别名、词法上下文与绑定依据。装饰器、默认参数、类体/模块初始化等定义时求值须与函数体执行分开；不能仅按行号区间归属调用，不支持时保留未知。

### 4.2.0 两张图：调用图与依赖图

**它们是两回事，必须都建。**

| 图 | 边来源 | 覆盖 |
|---|---|---|
| **调用图** | 符号级函数调用（`call(...)`） | 实现型模块 |
| **依赖图** | import 关系（`from x import y`） | 实现型 + **接口/契约/常量模块** |

> **实测依据（v0.2 修订六）**：Knowledge Loop 有 5 个核心文件
> （`knowledge-repository.ts` 只读接口、`desktop-api.ts` 类型契约、
> `json-post.ts` / `fetch-api-request.ts` HTTP 工具、`preload.ts` 桥接）
> **在调用图里入度出度全为 0**——它们只有 import 关系、没有任何函数调用，
> 是调用图里的孤立点。只用调用图，它们会全部漏出阅读顺序。

**import 边只用于阅读顺序与影响面分析，不进 PageRank** —— 保持
"重要度 = 调用结构中心性"这个语义不变（v0.2 修订五已定的重要度口径）。

**依赖图执行相同分层。** 确定导入边必须有模块路径、项目边界及配置证据；目录相近/唯一同名猜测单列，不得进入确定依赖 BFS 或影响面。类型依赖与运行依赖须分别标记。文件阅读顺序沿依赖展开，不意味着 import 边就是一次运行调用；确定调用图继续作为调用中心性排序的基础。

### 4.2.1 项目级排除规则（必备功能，非配置项）

> **实测依据**：`research_agent` 的 `runtime/` 目录含 465 个 `.py`、**175,589 行**，占全仓 Python 行数的 80%，但**一行都不是项目代码**（论文库、实验产物、临时文件）。不排除则排序彻底失真。

排除清单是索引层的一等功能，但目录名不能证明内容不是源码。`runtime/` 等排除是本项目样例的具体配置，不应自动推广为所有仓库的硬规则；须结合项目声明和文件发现，允许显式恢复纳入，并报告有效清单与理由。正式评测前冻结范围，不能看到推荐或告警后再排除。

本节的“不解析/不排序”是分析范围设置，与§3.5文件权限分开求值；它们不能恢复`exclude`，也不能使`local_only`源码或衍生信息获得模型资格。读取与派生处理前先通过统一访问策略；因权限缺失的配置或源码须报告适用范围和未知项，不能当作已完整分析。

**两类排除，用途不同，不可混为一谈**：

| 类别 | 目录 | 理由 |
|---|---|---|
| **不解析** | 已确认的数据/产物/依赖目录，如样例中的 `runtime/`，以及 `.git/`、缓存等 | 不属于所声明的一方源码范围；不能仅凭通用目录名全局排除 |
| **不参与重要度排序** | 本次任务明确排除排序的脚本/测试等 | 仍参与必要解析与影响面；这些目录也可能是开发工具项目的核心架构 |

> **实测依据（第二类）**：Python 侧首次应用四信号模型时，`scripts/` 与 `evals/` 下的文件霸占 Top10（`evals/benchmark.py`、`scripts/run_rag_retrieval_eval.py`…）。原因是 `entry` 角色权重 1.00，而这些脚本都有 `__main__` 守卫，命中 entry 规则。**排除后 Top20 命中从 1/9 回升到 5/9。**

### 4.2.2 绑定覆盖率与正确性边界（修订十）

旧样例的 17,449 次调用分类来自历史启发式实现，分类本身尚未获独立验证；旧“builtin 49.9%”“项目内 60–70% 天花板”等数字不能证明能力上限。按叶子名识别 `get/start/print` 会把项目自定义实现或未知接收者误当内置，因此撤回“补方法名表即可提高有效解析率”的实施依据。

| 分类 | 新契约 |
|---|---|
| local / cross_file | 在当前受支持范围内有明确绑定依据的项目内目标 |
| heuristic / ambiguous / unresolved | 猜测、多个候选或无法证明；保留调用点与原因，不伪装为确定边 |
| builtin / external / test_helper | 仅在绑定/来源可证实时排除出项目内候选分母；函数名长得相同不足以归类 |

项目内候选确定绑定率采用 §5.5 的分母，并同时报告各类原始计数；unresolved 可能包含尚未识别的外部调用，因此这不是已知真实项目内关系的精确覆盖率。真正的绑定正确率需要人工金标，不能由“解析器指向的符号存在”自证。

先修复作用域、导入与分类，再测量缺口。类型信息可按任务增加，但 Python 不能靠引入 TS 工具提高解析率；不凭单个样例预设静态分析的百分比天花板，也不以边数足够多来证明影响面可靠。

### 4.2.3 TypeScript 解析器选型

v0.2 初稿写的是"轻量抽取（正则/AST 子集）"。**实测后具体化**：

| 方案 | 判断 |
|---|---|
| 正则抽取 | ❌ 抽不出 import 关系与作用域归属 |
| **`ts.createSourceFile`（TypeScript 编译器 API）** | ✅ **采用**。修订八：默认使用 CodeSentry 管理的受控 TS 工具链；项目自带版本只在隔离执行中加载（§3.2.4） |
| ts-morph | 暂不引入；是编译器 API 的工程封装，是否采用取决于配置/类型解析的实际开发收益 |

**能力边界**：`ts.createSourceFile` 负责语法树；`Program` / `TypeChecker` 同样属于 TypeScript 编译器 API，类型解析不强制依赖 ts-morph。M0 的语法抽取、配置/模块解析与类型推断分别验收，不能因为取得 AST 就声称绑定完整。[TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)

**实测性能**：26,075 行 / 140 文件 / 1,153 符号，解析 **0.38s**（**68,618 行/秒**，是 Python `ast` 的 3.1 倍）。

> **修订八补充**：上面的性能是既有实现的历史测量，不证明工具来源安全或项目环境完整。AST 抽取、配置/类型解析和运行验证分开计量；类型解析需读取对应子项目配置及声明依赖，不能仅凭 AST 输出推断已还原环境。

**历史观测**：TS 侧曾报告 unresolved 6.9%、module_level 20.3%，但旧分类、样本和语言任务不同，不能据此断言优于 Python。保留部分静态导航不等于影响面已完整；收紧绑定契约后须重新测量。

### 4.3 重要度：PageRank 为主（v0.2 修订三，撤回四信号模型）

借鉴 Aider repo map 的核心做法：文件为节点、符号引用为边，跑 PageRank。

**采用 PageRank 的机制理由：中心性可沿调用图传播。** 被 20 个文件引用的函数排在只被调用一次的辅助函数之前；而被重要函数调用的符号，自身排名也随之升高。BM25（词频）和"最近修改时间加权"都缺少这个性质。

#### 4.3.1 曾经的「四信号模型」与它的撤回

v0.2 修订二曾引入四信号模型：

```
重要度(f) = 0.25·PR + 0.15·出度 + 0.25·入度 + 0.35·角色权重
```

**该设计已在 v0.2 修订三撤回。** 撤回过程与原因见 §4.3.2，这是本项目最重要的一次方法论纠错。

#### 4.3.2 为什么撤回：一次循环论证的评测

**当时的评测**：以 Knowledge Loop 的《项目接手指南》列出的 **9 个文件**为 ground truth，测出「四信号 Top10 命中 5/9，纯 PageRank 仅 2/9」。

**问题在于这 9 个文件是怎么挑的**——它们恰好覆盖了入口（`main.ts`/`App.tsx`）、契约（`desktop-api.ts`）、守卫（`policy-engine.ts`）、提案（`action-proposal.ts`）几种角色。**而被测的机制正是"角色识别"。用角色词表去测角色词表，是循环论证。**

**改用项目自带文档的全量清单重测**：

| 侧 | ground truth | 纯 PageRank Top10 | 四信号 Top10 | 结论 |
|---|---|---|---|---|
| Python | README「项目结构」章节，**30 个**文件 | **8** | 5 | 纯 PR 胜 |
| TypeScript | 《项目接手指南》，9 个（唯一可用集） | 2 | 4（v3） | 但纯出度亦为 2 |

TS 侧同口径复测（`ts_rank_compare.js`）：

| 模型 | Top5 | Top7 | Top9 |
|---|---|---|---|
| **纯 PageRank** | 1 | 2 | 2 |
| 纯出度 | 1 | 2 | 2 |
| v3 角色全局归一化 | 3 | 3 | 4 |
| v4 角色·类别内相对 | 4 | 5 | 5 |

**当时两个开发样例在该标签口径下，纯 PageRank / 纯出度优于所试的角色加权。** 这是保留简单排序的局部依据，不证明所有项目角色信号均为负收益；已参与选型的样例不能再作独立验证。

**角色信号的第二个缺陷**：权重经全局归一化后，**同类文件集体霸榜**。research_agent 的 `api/` 下 7 个文件全部命中 `contract`(0.85)，归一化后全部满分 → Top15 里 9 个位置被 `api/` 吃掉。

尝试过「角色不参与全局归一化，改为类别内相对分 × 类别权重」（v4），有效但仍不如纯 PR。

#### 4.3.3 修订后的方案

```
重要度(f) = PageRank(f)                      主信号
```

**出度（outdeg）不参与重要度排序，也不作为入口识别信号**（v0.2 修订四，源于 M0 实测）。

> **M0 实测推翻**：v0.2 修订三曾写"出度保留为入口识别的独立信号"。**实测证明这条不可靠**：
> - research_agent：`llm_client.py`（出度 23）、`daily_orchestrator.py`（29）被标成应用入口
> - Knowledge Loop：`deepseek-client.ts`（61）、`desktop-wiki-service.ts`（101）排在真入口前
>
> **出度高只说明「它 import 了很多东西」，不说明「它是入口」**——依赖多的服务模块会排在真正的入口前面。修订十三进一步按§4.4的启动声明与受支持静态证据区分角色；文件名、框架对象注册或被导入本身都不足以证明进程入口。

**架构角色标签不参与 PageRank 加权**，用于解释入口、授权中心、契约等职责。修订十三的启动角色与证据是另一层信息，可决定阅读路线的展示优先级；不能把角色名称当作已运行或人工裁决的证明。

**入口/编排类文件在 PageRank 里天然排不上去**（实测 research_agent：入口类排名中位 70，全部中位 60），因为 PageRank 衡量"被引用的中心性"，而入口与编排器是"引用别人"的一方。**因此 L2 的"推荐阅读顺序"采用入口优先策略，不用纯 PageRank 排序。**

> **这是本项目最重要的一次方法论纠错，且它重复了自己犯过的错**：v0.2 §9.1 已经定过「M1 判定标准是真实误报率，不是检出已知样本」，而本轮又用"手工挑的 9 个样本"当 ground truth 得到了虚高指标。**任何用主观挑选的少数样本当 ground truth 的评测，都必须先问：这个样本的选择是否与被测机制相关？** 相关则是循环论证。

#### 4.3.4 角色信号规则（保留，用于输出分组）

| 角色 | 权重 | 判据（路径/文件名/内容特征） |
|---|---|---|
| `entry` | 1.00 | `main`/`index`/`app`/`server`/`cli`/`preload`；`createRoot()`/`app.whenReady`/`BrowserWindow(`/`ipcMain.` |
| `guard` | 0.95 | `policy`/`guard`/`security`/`permission`/`auth`/`sandbox`/`safe` |
| `contract` | 0.85 | `api`/`types`/`contract`/`schema`/`interface`/`shared` |
| `orchestrator` | 0.85 | `loop`/`orchestr`/`coordinat`/`agent`/`runner`/`workflow`/`pipeline`/`dispatch`/`router` |
| `proposal` | 0.70 | `proposal`/`preview`/`draft`/`action`/`intent` |
| `service` | 0.60 | `service`/`client`/`provider`/`adapter`/`handler` |
| `store` | 0.60 | `store`/`repository`/`persistence`/`database`/`index`/`snapshot` |

**规则完全确定性，不调用 LLM，可单测。** 词表做成可配置 `roles.yaml`，由 M5 知识层产出项目专属覆盖。

#### 4.3.5 跨项目验证结论

| 维度 | Python 侧主要风险 | TS 侧主要风险 |
|---|---|---|
| 排序失真主因 | 同名符号合并 | 方法调用归属不明 |
| 解决手段 | **限定名** | 限定名（TS 侧重名率低） |
| 排除规则 | 必需（`runtime/` 占 80% 行数） | 常规即可 |
| 未解析占比 | 12.8%（标准库类方法） | 6.9%（module_level 20.3% 需类型） |

**"跨项目一致性"的真正含义：不是两个项目数字一样，而是同一套机制（限定名 + 排除规则 + PageRank）能覆盖两者的失败模式。**

**PageRank 性能实测（v0.2 补充，本机 i7-12700H）**：

| 图规模 | 纯 Python PageRank 耗时 |
|---|---|
| 500 节点 | 1.1 ms |
| 2,000 节点 | 4.6 ms |
| 8,000 节点 | 27 ms |
| **30,000 节点** | **169 ms** |

**决策修订（v0.2 修订 v0.2 初稿）**：初稿曾设计"增量场景用反向引用计数 + 层级深度的局部近似"作为折中，理由是"PageRank 是全局计算"。**实测证明该理由不成立**——真实项目量级（30,240 符号）的 PageRank 仅需 32 ms，**每次全量计算都不慢**。

而局部近似的排序质量代价被实测暴露：Top20 重合度 16/20，Top50 重合度仅 11/50。

**因此修订为：每次都计算全量 PageRank，删除局部近似这条路径。** 理由：
1. 性能上无必要——169 ms 相比 AST 解析的 8.9 s 可忽略
2. 质量上更优——省掉一个"重要度有两种算法"的解释负担与不一致风险
3. 少一个概念，少一处需要写进 README 的 trade-off

> **方法论收获**：v0.1 曾定"trade-off 必须写进 README，不假装解决了"。本次实测同时验证了它的反面——**当 trade-off 实际不存在时，不要为了显得严谨而制造它。** 声称"我们做了折中"而不给数据，是伪严谨。

**依赖策略**：**不引入 numpy / scipy / networkx**。理由有三：
1. 纯 Python 实测 30,000 节点仅 169 ms，够用
2. 当时环境尝试安装 scipy 曾超时，原因未独立确认；不据此推论所有 Windows 安装都需要源码编译
3. 自实现的 PageRank 约 60 行，可单测，且不受第三方版本升级影响

### 4.4 入口点识别

按受支持的启动声明与静态绑定规则识别，不依赖LLM。**角色与证据来源分别记录**，不再把文件名、路由注册和进程启动混成一张已确认入口名单。

| 角色 | 含义与可接受依据 | 阅读路线中的职责 |
|---|---|---|
| `process` · 进程入口 | 有已识别执行上下文的启动声明，或受支持框架的模块级启动调用 | 证据为declared/static时作为距离根，零出度不排除 |
| `mount` · 界面挂载 | HTML源脚本声明或绑定确认的模块级界面挂载调用 | 证据为declared/static时作为距离根，不等于已运行界面 |
| `bridge` · 桥接上下文 | 宿主加载preload等独立上下文的声明与源码映射 | 单列上下文；必要时作分支展示锚点，不作为进程根 |
| `assembly` · 应用装配 | 应用工厂、路由/组件注册等绑定与调用证据，或尚不足以证明进程启动的加载声明 | 说明装配关系；必要时作分支展示锚点 |
| `candidate` · 待确认候选 | 文件名提示、直接main守卫，或执行上下文尚不明确的命令目标 | 保留候选依据与限制，不因候选名称获得入口优先席位 |

`confidence`使用`declared`（启动/加载声明）、`static`（解析器确认的受支持绑定与调用语法）、`heuristic`（名称等线索）。这里记录证据来源，不是概率、运行观测或人工标签。每项保留源码行号、声明文件/位置与映射证据；未知入口行号不补造。读取不到启动配置、目标无法映射、声明上下文不确定等问题，另列`entry_evidence_issues`，不能藏进“入口已找齐”的结论。脚本目录中的辅助入口仍可折叠统计，不与应用角色混算。

默认只读解析允许范围内的清单、HTML及受支持启动配置；不执行配置或目标程序，不加载目标依赖。源码中的`__main__`守卫只证明直接执行意图，框架工厂或路由注册只证明装配线索；`package.main`也需要宿主/命令上下文才能支持进程角色。声明映射到源码不证明构建产物存在或与源码一致。

声明解释以官方规范为依据：Docker的[CMD与ENTRYPOINT关系](https://docs.docker.com/reference/dockerfile/#understand-how-cmd-and-entrypoint-interact)需要结合解释，PyPA的[entry points](https://packaging.python.org/en/latest/specifications/pyproject-toml/#entry-points)描述入口对象映射，Node的[main字段](https://nodejs.org/api/packages.html#main)描述包加载入口；这些声明各有上下文，不能单凭字段存在就判为应用进程已启动。

> **历史分类纠正**：旧实现从54个main守卫候选收敛到3项的记录，不是独立入口质量证据。此前将`api/app.py`工厂与`api/routes.py`注册模块直接列为应用入口的解释已撤回；启动声明、装配与挂载的只读核对见[启动链路证据](execution/P1_启动链路证据.md)。候选角色仍不等于人工金标，入口precision/recall须等待独立标签与范围裁决。

### 4.5 增量失效

**内容哈希失效**（v0.1 已定）：

- 每个文件缓存 `(mtime, content_hash, parsed_symbols, outgoing_edges)`；修订八要求额外区分解析工具链与相关环境/配置身份（§4.5.3）
- 变更文件 → 重解析 → 更新边表
- **每次重算全量 PageRank**（实测 30,000 节点 169 ms，无性能必要做局部近似，见 §4.3）
- 显式 `refresh-index` → 全量重建（清空缓存后重来）

**索引与工作空间的时效性必须显式报告。** P1通过内容哈希与增量重解析，并在扫描前后核对源/配置；变化时标为不完整。已保存的结果仍属于历史快照，工作台打开当前代码前要核对同口径摘要并显示stale，不能把旧定位当作当前精确证据。此设计不依赖未经同口径核验的竞品失败断言。

#### 4.5.1 缓存边界（实测确定）

**当前实现只有 parse 阶段走缓存**，其余每次全量重算；修订八补充的工具链与环境失效条件见 §4.5.3：

| 阶段 | 耗时（research_agent 42k 行） | 是否缓存 |
|---|---|---|
| parse | **0.87–1.32 s** | ✅ 缓存 |
| resolve | 0.025 s | ❌ 重算 |
| pagerank | 0.028 s | ❌ 重算 |
| entrypoints | 0.031 s | ❌ 重算 |
| roles | 0.107 s | ❌ 重算 |

**为什么 PageRank 也要重算**：§4.3 已定"每次全量算，不做局部近似"——实测 30,000 节点仅 169 ms，而局部近似 Top50 重合度只有 11/50。缓存 PageRank 会引入"索引陈旧"的第二个来源，得不偿失。

**实测效果**：

| 场景 | 冷启动 | 热缓存 | 加速 |
|---|---|---|---|
| research_agent（154 文件 / 42k 行） | 1.12–1.63 s | **0.26–0.40 s** | **4.1–6.1x** |
| 改动 1 个文件后 | — | 0.46 s（命中 153/154） | — |

**增量结果与全量重建逐项比对：符号数、边数、PageRank、入口点、调用分类全部一致** ✅

#### 4.5.2 缓存与索引的落盘位置（重要）

**默认写到用户缓存目录，不写进被审查项目。**

> 实测：写进项目内会生成 **4.7 MB** 的 `parse_cache.json`，还会污染被审查项目的 `git status`。**一个"帮你审查代码"的工具，在被审查方留垃圾是减分项。**

| 内容 | 默认位置 | 可选 |
|---|---|---|
| 解析缓存 | `%LOCALAPPDATA%/codesentry/cache/<项目路径哈希>/` | — |
| 索引快照 | `%LOCALAPPDATA%/codesentry/index/<项目路径哈希>/` | `--save-to-project` 写到项目根 |

**残留窗口（显式声明，不隐藏）**：单次扫描过程中文件被修改，本轮索引可能包含旧内容。`codesentry status <path>` 会在下次运行时发现这一点。

#### 4.5.3 工具链、配置与环境失效（修订八、九；待实施）

P1已实施作用域缓存/索引版本迁移、失败可见且不作成功空缓存、解析工具链/实现身份及索引环境/策略/算法身份；扫描前后校验输入，完整性明确报告。下面仍描述完整目标，实际类型/模块解析与动态证据复用尚未实现，不能由静态缓存升级推断已覆盖。

源码内容相同，不代表换了解析器、依赖或配置后结果仍有效。按证据实际依赖区分身份，避免把“宿主环境变了”当作所有缓存一律失效的理由：

| 结果 | 身份/失效输入 |
|---|---|
| 纯语法解析缓存 | 源码内容、语言/解析选项、解析 schema、实际解释器/编译器工具链身份 |
| 配置/类型解析与索引快照 | 以上输入 + 子项目映射、传递配置（含 extends）、声明/锁文件、实际可用依赖与类型声明身份、已解析模块位置及相关解析策略；不能仅凭锁文件不变复用结果 |
| 动态验证证据（暂不默认复用） | 源快照、命令/输入、实际平台与依赖、镜像/工具链、服务/配置、执行限制；仅有锁文件哈希不足以证明环境相同 |

**失败状态不作为成功解析缓存入库**。缺工具、配置错误、语法失败与成功但零符号的文件必须可区分；环境恢复或工具链变化后，即使源码未改也应重试。新增指纹前的旧缓存迁移时作废；`status` 除源码陈旧外，还应报告工具链/配置已变和验证证据不适用。全局解析与 PageRank 仍按现有策略重算。

## 五、场景 A · 理解陌生项目

### 5.1 输出分级

参考成熟 onboarding 工具的共同做法：**三档递进，不是一次性给全部。** 对应三种使用时机。

| 档位 | 耗时 | 回答的问题 | 输出 |
|---|---|---|---|
| **L1 · 定位** | <30s | "这是什么项目？" | 技术栈 + 入口点列表 + 规模统计 + 环境声明/缺口与解析完整性（修订八待实现） |
| **L2 · 骨架** | <3min | "它怎么组织的？" | 核心模块 + **推荐阅读顺序** + 结论依据/环境适用范围（修订八待实现） |
| **L3 · 深挖** | 按需 | "这个功能在哪实现？" | 关键路径（入口 → 校验 → 逻辑 → 持久化 → 响应） |

**实施范围（已确认）**：Phase A 先做 **L1 + L2**。L3 延后到 M7+。修订八新增环境画像与解析不完整提示；默认 L1/L2 仍走静态导航，安装依赖、运行测试与启动项目另行请求。静态分析、环境准备与动态验证分别计时，不把准备环境开销隐藏在热缓存数字里。

### 5.2 确定性 / 语义的分工

**这条边界必须写死**：

| 档位 | 是否调用 LLM | 理由 |
|---|---|---|
| L1 | **否** | 全部可从清单文件、配置、AST 确定性得出 |
| L2 | **否** | 模块重要度来自 PageRank，阅读顺序来自入口/契约优先与依赖 BFS；配置与类型事实按环境标注 |
| L3 | 是 | 关键路径的语义串联（"这一步在校验什么"）无法从结构推出 |

**L1/L2 的设计目标是在源码、工具链、相关配置与排序/遍历顺序一致时可复现、可测试**。这与 v0.1 "确定性层是护城河"的原则一致，也让 Phase A 的评测容易做（答案可由人工标注一次、多次复用）。

### 5.4.1 L2 阅读顺序的推导策略

阅读路线综合启动证据、分支覆盖与静态依赖，不用纯PageRank排成一张总榜。**距离计算独立于展示顺序**，前置文件不能改变图距离，也不能成为虚构的启动根。

| 步骤 | 当前规则与边界 |
|---|---|
| **确定距离根** | 只使用生产范围内、证据为declared/static的process/mount。零出度有效；名称候选、工厂、桥接和契约均不因此成为根 |
| **计算层级** | 从所有距离根做BFS，记录展开深度内的最短静态依赖距离。L0只属于根；`·`表示未在当前深度内到达，不代表文件缺失、不可读或没有任何关联 |
| **补充分支锚点** | 对全部根沿有向依赖不可达、且有declared/static证据的assembly/bridge，按候选间有向可达关系形成强连通分量；从源分量各选一个确定性代表。它们仅是展示锚点，其自身与分支文件的距离仍只按真正根计算 |
| **分配优先窗口** | 根与分支锚点前置，共享契约适量前置；各分支按深度轮询，并为更深层保留预算。同层候选按PageRank与稳定路径次序排列，弱候选不因名称提示抢占优先位置 |
| **保留完整清单** | `max_items`是优先阅读窗口，`max_depth`限制依赖展开；剩余合格生产文件按PageRank与稳定路径次序补全，每个文件只出现一次，不因低排名、孤立或超出窗口而丢弃 |

共享契约候选仍要求无向下依赖、至少两个生产文件依赖，以及接口/类型/枚举等符号形态；前置预算受剩余优先窗口限制。契约可以显示L1、其他真实距离或`·`，不会因为展示在前就固定成L1。装配锚点的分支轮询也不改变这些距离。

静态依赖边包括用于导航的结构关系，不能解释成已发生的函数调用、实际初始化顺序或完整运行路径。没有足够启动证据时保留未知与完整文件清单，不把弱候选升级为入口来填补空白。

> **历史试验范围**：旧阅读算法曾报告Top30命中Python 19/44→23/44、TS 7/11→9/11，使用了出度筛选根与展示层级等旧约定。它们只保留为历史试验，不证明修订十三的算法质量。当前结构反例、开发消融与正式质量验收分别记录；冻结v1合同与旧GT不因本次修改覆盖，权限范围不同的结果不可直接横比。P1仍未整体通过，也不据结构修正宣称质量提升。

### 5.5 场景 A 的评测指标

**修订九统一指标定义**：阅读顺序准确率、关键文件覆盖率、位置检查、解析覆盖与性能分开报告。文档标签目前只是代理标注，未标注推荐是未知，不能直接当作人工确认的错误。

| 指标 | 测法 | 目标 |
|---|---|---|
| **入口点召回率** | 人工标注真实入口点，看工具找出几个 | **100%（不妥协）** |
| **入口点精确率** | 工具报出的入口点里，有几个真是应用入口 | **≥ 0.9**（v0.2 补充） |
| **项目内候选确定绑定率** | (local + cross_file) / (local + cross_file + unresolved + ambiguous + heuristic) | 分开报告确定/启发式/歧义；保守解析后的基线重新测量，不能用旧值证明达标 |
| **阅读顺序 P@10** | 前10项命中文档关键文件数 / 10 | **≥0.8（用户确认）**；推荐不足10项或无有效GT时不可验收，实际前N项比例可报告但不得冒称P@10达标 |
| **Recall@K** | 前K项命中关键文件数 / 范围内唯一关键文件总数 | 独立报告覆盖率，不替代P@10；空GT为N/A |
| **输出位置检查** | 索引自洽 + 磁盘文件及行号核验 | 错误0；这不能证明符号绑定、解释或审查判断正确 |
| 耗时 | L1 / L2 端到端 | <30s / <3min |

**验收脚本改造要求（待实施）**：`evals/m0_acceptance.py` 后续须按阅读顺序 P@10、位置检查、解析完整性与端到端耗时共同判定退出码，并计入实际 L1/L2 渲染，分别报告各层耗时。未匹配/歧义 GT、缺失解析、空 GT 或不足10项必须明确不可验收，不能仅因位置检查为0而返回成功。入口点召回/精确率和已解析边正确率需要额外的独立标注，脚本通过也不等于全部 M1 目标达成。还须提供不写目标项目缓存的测量方式；具体选项待实现。正式比较必须记录阈值与缓存状态，不能降低阈值掩盖失败。当前脚本尚未满足这些新要求。

**入口空分母**：无真实入口金标时召回为 N/A，无预测入口时精确率为 N/A，均不折算为100%或支持达标。确实不含应用入口的库项目须事先登记任务与适用目标，不强迫生成假入口；不适用不等于已验证入口识别能力。

**审查指标定义**：precision = TP/(TP+FP)，无告警时为 N/A；recall = TP/(TP+FN)，无正例时为 N/A。TP/FP/FN 需来自对同一问题的标注匹配，clean 集单列误报条数/密度或每次提交误阻断率，不能单靠 clean 集估计总体 precision。未标注结果不是自动 FP，样本数与未知项须同时报告。具体标签构造与封存集设计留待后续评测集阶段。

**计分边界**：P@10 的命中按唯一文件计，重复推荐占位置但不能重复得分。输出不足10项时单列实际 P@K，不能宣称 P@10 达标；若任务范围内原本有足够文件但输出不足，应标结果不完整。可用关键标签不足8项时优先标“标签不足，无法验收”；只有独立复核确认任务本身确有不足8个关键文件或适用文件总数不足10，才可在评测前登记该目标不适用，不通过缩分母制造达标。GT 路径必须精确或唯一匹配，歧义/缺失先裁决；排除与去重均报告。

**历史数据口径**：旧报告“8/30”是 Recall@10，不能与“8/10”的 P@10 混用。旧 81.9% 解析率的计数应为 3867/(3867+1587+266)=**67.6%**；修订九要求收紧绑定语义，实施后须重测，旧计数不能充当新契约的验收基线。文件 GT 派生的目录覆盖只作聚合展示，零命中的目录仍计入分母，不称完整架构覆盖率。

真实项目复测时同时报告源码/工具链版本、扫描范围、唯一 GT 数、未匹配与排除项、解析失败、确定绑定/启发式/歧义数量、P@10、Recall@K、端到端耗时和最终状态。未完成实现与复测前，不把历史命中率、临时试验结果或测试数量作为新方案达标证据。

### 5.6 标签、封存评测与真实效果（修订十；待实施）

本节覆盖 v0.1 的“fix message + diff 直接作答案”“流行开源项目视为 clean”“只审前50条后推广误报率”以及“两项目误报率相近即通用”的旧要求。2026-10-28已实现合成数据离线计分、全局声明分组审计及阶段ID流失；真实标签、独立封存身份隔离、真实通道采集和正式统计仍待实现/验收，不能称整套评测已就绪。

#### 5.6.1 标签构造与裁决

固定项目/文档版本、任务、扫描范围及排除策略。标签记录规则/问题类别、路径/符号、正/负/未知、依据与裁决状态。文档清单只能作为导航代理标签；正式人工复核须覆盖推荐结果与潜在遗漏关键文件，不能只审查命中项。争议或未标注不自动作负例；正式验收的必要未知项须先裁决。

历史 fix 提交仅提供缺陷候选，须核对修复前后的语义与规则适用性。可运行用例记录修复前失败、修复后通过及匹配环境；无法复现、混合多项变更或尚有争议时标未知，不强行纳入金标。按已知基点建立隔离副本，不在用户脏工作区机械反向应用补丁。

`bugs` 只含已裁决的行为缺陷；`clean` 指针对所声明规则审阅的负例，不保证整个项目无缺陷；`debt` 单列政策违规/结构债与报告质量，不混入 bug 的 precision/recall。问题匹配须按问题身份及允许的位置/符号范围预先确定，并一对一计数，不能一条告警同时命中多个复制问题。

#### 5.6.2 train、dev 与封存 holdout

train 用于提案/学习；dev 用于反复选择规则、阈值与 prompt；holdout 仅在预登记发布点评估。按仓库/派生关系及缺陷家族分组，避免相邻提交、复制代码、同一缺陷及其修复变体跨集合。已有两个真实项目反复参与设计，只作为开发/回归项目，不追认为独立 holdout。

冻结源码、标签、匹配准则、分割与评分器版本。封存评估由独立执行身份读取，提案进程不挂载这些文件；仅建一个名为 holdout 的目录不构成隔离。候选规则同样不得与金标同进程执行：其运行身份只在隔离 runner 中接收本次声明输入并输出结构化预测，不挂载金标、评分器或历史反馈；可信评估者在 runner 外匹配和计分，不能接受候选自报分数/通过状态。记录候选版本、评估次数和可见反馈。开发循环只看 dev；依据某批 holdout 反馈修改候选后，该批次降级为 dev，下一次正式结论须使用新封存批次或预先保留的未启用分片。

#### 5.6.3 候选召回与端到端指标

语义候选召回率 = 被候选集合覆盖的适用金标问题数 / 全部适用金标问题数。在只经该候选通道发现问题的范围内，端到端 recall 不高于候选召回率；模型不能找回未进入候选的问题。分别记录生成候选、预算截断、进入裁决、模型接受、位置回验保留及最终正确的问题数，按规则/缺陷/语言分层；确定性通道与 explore 独立统计，不混合提高分数。

保留既定 precision≥0.85、recall≥0.70 为目标，同时报告 TP/FP/FN、未知、样本数、项目/规则分层与不确定性。无告警 precision 或无正例 recall 为 N/A，不能支持通过。告警过多时使用预登记随机/分层抽样并报告权重，不用阅读顺序前若干条估计总体。负例集单列误报条数、每千行或每次变更误报密度及误阻断率，明确各自分母。

项目构成不同可合理产生不同误报率；数值相近既不证明通用，差异也不自动证明过拟合。应分析适用范围、缺陷类型与失败例。样本规模、独立项目/审阅者和可接受统计误差由先导评测确定，正式测量前登记，不在看到结果后补定通过标准。

#### 5.6.4 理解效果与图索引价值

P@10 与 Recall@K 只验证导航代理目标。另设定位入口、解释数据流、判断变更影响等固定任务，采用独立答案与证据评分，对比“原有 README/检索”和“增加 CodeSentry”的正确完成率、到正确答案的耗时、错误断言与关键遗漏。平衡任务/项目顺序，避免参与者先做同一道题取得学习优势；先做小规模流程试验，再定正式规模。

“图索引降低审查误报”仍是假设：需固定任务集、规则、候选、模型与预算，仅切换上下文是否包含图索引，并分别报告候选召回与裁决误报。没有这类对照前不写成已证实因果。

#### 5.6.5 最小反例与完成条件

先验证分母、重复计数、未知标签、不完整状态及阶段流失计数；再用同缺陷变体/复制代码确认分割不会泄漏，并验证提案进程及候选规则运行身份无法读取封存标签、修改评分器或伪造评分结果。封存集反馈一旦用于修改，台账中必须可见其降级。发布报告须能从冻结清单和原始计数复算，不能只有汇总百分比。首轮离线反例已覆盖计数与显式分组关系；真实分组完整性、阶段流失、候选执行/封存隔离仍待验收，不以导航脚本或合成评分退出0代替。

## 六、自进化设计（M5 知识层 / M6 规则层）

### 6.1 三层模型与实施范围

| 层 | 进化对象 | 风险 | 本版决策 |
|---|---|---|---|
| **知识层** | 代码认知（Insight） | 低 | ✅ 实施（M5） |
| **规则层** | 确定性检查器 | 中 | ✅ 实施（M6，设硬护栏） |
| **代码层** | 自身实现（自动改写源码） | 高 | ❌ **不实施** |

**代码层不实施是本版范围与风险控制决策**，相关风险证据与适用边界见 §6.2。

### 6.2 为什么本版不做代码层自修改

Roesner 与 Kohno 的概念验证表明，投毒评测可诱导自修改代理固化不安全做法；部分污染在干净基准续跑中仍持续，但定向去污染也能改善或移除。它支持保护评测、验证与权限边界，不能证明污染永久不可逆，或所有自修改方案必然失败。[原论文 §3.6–§3.7](https://arxiv.org/html/2609.17817v1)

原稿表格把“从干净种子独立进化的对照”误当作“中毒后干净续跑”，并据此声称永久性，现撤回该表与推论；缺少准确原始出处的“伪造日志/移除幻觉标记”也不作本项目论据。

本版不做自主修改核心实现，是工程范围与风险控制的选择：优先完成导航、规则质量与门禁闭环。知识和规则提案可以演进，但无权修改评分器、验证器、可信权限策略或已批准基线；提案产生的规则须经独立准入后才可生效。

### 6.3 三条硬护栏（修订十明确）

**护栏一：未经准入的进化产物不得进入门禁。**

Insight 仅作为导航提示，语义草稿及 explore 只作警告；它们不能修改场景 B 的必检范围、可信策略或基线。规则提案进入 proposals，完成独立评测与人工审阅后，作为有版本的确定性规则进入 active；故不再写成“所有进化产物永远不能进入门禁”。同一模型不能通过自报正确决定其产物准入。

**护栏二：开发回归与封存评估分开。**

开发循环在 train/dev 完成，固定的安全/契约反例必须全部保持通过。holdout 只在预登记发布点由独立身份运行；一旦反馈用于修改候选，该批次按 §5.6.2 降为 dev。访问控制须落到执行身份、挂载与审计，不能只约定提案者“不看文件”。

“非退化”是本项目的准入要求，不是任何有限评测能保证的未来性质：确定性反例不得回归，统计指标的比较口径、不确定性和允许的权衡须评测前登记，不能按一次小样本点估计声称永久零回归。

**护栏三：提案方不能修改评分和授权依据。**

| 可提案，独立批准后采用 | 提案进程无权直接改动 |
|---|---|
| 带证据与作用域的 Insight | 评分器、金标、分割和匹配准则 |
| 确定性规则候选及适用范围 | verifier、最终 gate 和可信权限策略 |
| 版本化 prompt 模板 | 已批准基线、active 规则及封存评测文件 |

这里的评分器指评测与匹配逻辑，不是禁止审阅后升级检测规则。PR/Git 用于差异审阅、版本与回滚，但仓库文件可写并不等于具备批准权限；提案与准入执行身份分离。每次晋升记录规则/候选版本、dev 与封存结果、人工决定和回滚点。

试运行、人工批准与回滚可参考 MOSS；Ratchet 是另一项针对技能库管理的研究，不能把它们混为同一论文或据此保证逐次单调提升。本项目的具体门槛由自身评测合同决定。[MOSS](https://arxiv.org/html/2605.22794v1)、[Ratchet](https://arxiv.org/html/2605.22148v1)

### 6.3.1 资源与成本边界

**成本口径**：本版语义能力拟使用显式启用的云端服务，受 §3.5 数据与预算策略约束；本地仍有证据准备、结果处理与验证成本。API、网络、隔离执行和依赖准备均需分别测量，不能以无本地推理等同零成本。

| 环节 | 执行位置 | 本机开销 |
|---|---|---|
| AST 解析 | 本地 | 8.9 s（19.6 万行实测） |
| 建图 + PageRank | 本地 | 0.05 s |
| 漂移检测 | 本地（待实现） | 待测 |
| Insight 生成 / 规则提案 | 授权后使用云端服务 | 本地准备与处理；API 费用/时延另记，待测 |
| LLM 裁决 | 授权后使用云端服务 | 同上；重试、并发和预算有界 |
| 封存评测 | 本地可信评估者 + 隔离候选执行 | 待测；取决于任务和环境 |

**实测资源占用**（19.6 万行 / 30,240 符号 / 40,320 引用边）：

| 资源 | 占用 | 结论 |
|---|---|---|
| 峰值内存 | 14.1 MB | 可忽略 |
| GPU | 0 | **不需要本地推理** |
| 磁盘 | 索引约数 MB | 可忽略 |
| CPU 占用 | 单核为主，AST 阶段可并行 | 14 核下 37k 行项目 < 3 s |

**已有资源测量只覆盖历史静态分析路径；表中待实现环节没有测量结果，不含隔离环境与目标项目运行成本。** 还需注意**内存余量**——历史测量机器的 15.8 GB 总量，若同时运行 IDE / 浏览器 / 其他 Agent 客户端，可用内存可能低于 4 GB，后续配置/类型解析子进程的额外资源尚需实测，不以未经验证的固定内存估计作为选型依据。

**修订八资源要求**：分别记录静态分析、镜像/工具准备、依赖安装、沙箱启动与实际验证的耗时、峰值内存和磁盘占用。当前没有后四项的本机实测，不据此宣称沙箱资源可忽略，也不预设统一的内存门槛；限额随首个真实任务验证。

**依赖策略（影响环境搭建成本）**：不引入 numpy / scipy / networkx。纯 Python PageRank 实测 30,000 节点 169 ms 已够用；当时环境尝试安装 scipy 曾超时，原因未独立确认；本版不引入它的主要依据是现有纯 Python 实现已满足当前测量需求。轻量依赖目标适用于默认静态核心；现有 Python 运行依赖为 Pydantic + PyYAML，TS 另需受控 Node/TypeScript 工具链。可选 Docker 后端、镜像与目标依赖单独列示，不计入“零新增依赖”的承诺。

### 6.4 M5 知识层设计

#### 6.4.1 Insight 契约

```python
class Insight(BaseModel):
    id: str
    statement: str                  # 事实陈述
    evidence: list[Evidence]       # 每条锚定 repo:file:line
    scope: Scope                   # global | language | ecosystem | repo | task
    kind: InsightKind              # architecture | convention | pitfall | idiom
    confidence: float
    learned_from: list[str]        # 来源 repo 标识
    created_at: datetime
    last_verified_at: datetime
    status: Status                 # active | flagged_stale | retired
```

以上为拟定数据草案。Evidence 还须带仓库/源码快照、完整作用域符号与证据摘要，并区分静态、配置解析和运行观测；仅有存在的 file:line 不足以证明语义持续有效。跨仓库使用仍受 §3.5 授权与数据隔离约束。

#### 6.4.2 三条设计要点

| 设计 | 防的是什么失败模式 |
|---|---|
| **每条 Insight 锚定 `file:line`** | 记忆污染——笔记说某文件负责某功能，那文件被删/改了，笔记还在 |
| **证据漂移 → 自动标记 `flagged_stale`，不静默删除也不静默沿用** | 陈旧上下文当真理——文件重构了，笔记还在讲旧架构 |
| **区分事实与推测**（推测单独放 `hypotheses` 区，标注未验证） | 推断当事实 |

第三条的直接来源是一条成熟实践的硬规则 **"code before everything"**：不许声称任何不能在代码中指出文件的事情；答不上来时，列出"我检查了哪些文件、哪些没检查"，而不是编造。**这条规则应直接进知识层设计。**

#### 6.4.3 分层作用域

| 作用域 | 内容 | 生命周期 |
|---|---|---|
| `global` | 语言/框架通用模式（如"LangGraph 项目的图定义集中在 graph_builder"） | 长期，需强证据 |
| `ecosystem` | 特定生态的约定（如"FastAPI 项目用 Pydantic 做 schema"） | 中期 |
| `repo` | 单仓库的模块边界、构建命令、历史坑点 | 绑定该仓库 |
| `task` | 短期上下文 | **不得污染长期记忆** |

**核心原则（来自 arXiv 综述）**：从某个仓库学到的策略**不能默认推广到所有语言和框架**。从 `research_agent` 学到的"图编排模式"不能直接套到 Knowledge Loop 上。

#### 6.4.4 漂移检测

```
每次索引更新（M0 触发）
  → 对该 repo 的每条 Insight 校验其 evidence 是否仍指向存在且语义一致的符号
  → 失效 → 标记 flagged_stale，仍可查但不作为事实呈现
  → 连续 N 次失效 → retired
```

**指标**：漂移检出率（代码变动后被正确标记失效的比例）。这是 M5 的验收标准。

### 6.5 M6 规则层设计

#### 6.5.1 进化流程

```
在已授权项目扫描 → 提出规则及适用范围
  → rules/proposals/（待审，不生效）
  → train 开发 + dev 选参/反例回归
  → 冻结候选版本与评估合同
  → 独立封存评估（预登记发布点）
  → 人工 review + 批准晋升 → rules/active/
  → 独立确定性执行，可审计且可回滚
```

封存失败后若据此修订，原批次不再作为下次正式 holdout；未获足够准入证据的规则维持 report-only，不进入默认阻断。

#### 6.5.2 准入标准

| 门槛 | 要求 |
|---|---|
| 固定反例 | 已确认的安全/契约反例全部通过，不能用汇总分数抵消回归 |
| 精确率与召回 | 保留既定目标，提供原始计数、未知、分层及不确定性；precision 目标 ≥0.85 不等于无样本时默认通过 |
| 封存评估 | 候选/标签/评分器冻结，独立身份按预登记口径执行；不基于分数反复选优 |
| 作用域 | 只在证据支持的语言/规则/项目范围启用，不能仅因两项目误报率接近就宣称通用 |
| 人工确认 | 审阅规则逻辑、风险、影响与结果，由可信准入流程写入 active |
| 版本与回滚 | 记录晋升依据及旧版本，可恢复已知状态；代码/策略变更后重新验证 |

#### 6.5.3 提案与评估分离

LLM 可以提案和解释，但不能担任最终标签裁决者、改变问题匹配口径或批准自己进入阻断。金标、评分器与门禁依据由独立可信流程管理；运行候选规则遵守 §3.2 与 §5.6.2 的隔离边界，金标匹配和计分由 runner 外的可信评估者完成。样本不足、规则越界或封存反馈已被用于修改时，不以“模型认为正确”补足证据。

```
codesentry onboard <path> [--level 1|2]           # 场景 A
codesentry doctor <path>                         # P1已实现：只读环境/受控工具诊断
codesentry verify <path> --task <name>            # 修订八规划：显式任务，经 runner，待实现
codesentry trace <symbol>                         # 场景 A · L3（M7+）
codesentry propose <pattern>                      # M6
```

**为什么现在定多子命令**：

- 薄 dispatch 层本身成本极低，20 行量级
- `scan` 与 `onboard` 的**输出形态根本不同**（finding 列表 vs 导航图），用单命令 + flag 实现会长出 15-flag 的上帝函数
- **底层数据模型（Symbol / Edge / Finding / Insight）现在就要定**——它们是两个场景共用的地基。"等形态稳定再拆"并不能避开真正贵的部分
- v0.1 的"不为未验证能力提前付成本"针对的是 ts-morph 这类重型依赖，不是 CLI 薄层

**额外收益**：`scan` 与 `onboard` 并列摆着，本身就在讲"两个场景共用一套索引"这个架构故事——**命令结构是架构的外部投影**。

**接口状态**：当前可用`onboard/index/status/init/doctor`，并新增显式`scan --preview`的Python策略债务只报告模式；预览完成返回3，门禁未评估，不带preview的正式scan仍关闭。diff、通用verify、trace、propose仍为规划。doctor只读，通用verify须经可信任务与runner；diff须明确§3.4范围。网页目前仍以静态导航为主，审查集成待后续。

### 7.2 v0.1 遗留的 CLI 描述更新

v0.1 写的是 `codesentry scan <path>` 单命令形态，v0.2 更新为上述子命令结构。
