## 三、缺陷一 · 符号未限定（致命）

### 3.1 现象

第一版实现把符号名直接当图节点。跑真实项目的 L2 输出：

```
1   tests\test_core.py              0.16716   6101行  496符号
2   api\redis_runs.py               0.08604   1205行  106符号
3   session_store.py                0.02746   1014行   54符号

核心符号 Top10:
  1  get       0.01809   badcase_store.py:253
  2  append    0.00515   api\run_manager.py:31
  3  execute   0.00355   tool_runtime.py:83
  4  list      0.00216   badcase_store.py:260
```

**排第一的是 6101 行的测试文件，核心符号是 `get` / `append` / `list` —— 全是通用动词。**

### 3.2 根因

统计生产代码的符号定义：

```
定义总数        1,206
唯一名数量        990
重名率            18%
```

而重名最严重的是：

```
__init__    40 次
get          8 次
_now         7 次
main         6 次
list         6 次
start        6 次
```

**因为图节点用符号名做唯一标识，`get` 在 8 个不同文件里被定义 → 合并成同一个节点。** 于是 PageRank 在给"最常见的词"打分，而不是在给"最重要的模块"打分。

**这与符号解析率无关**——即使 100% 解析正确，节点合并本身就已经毁掉了排序。

### 3.3 修订：限定名

改用 `file::symbol` 作为节点唯一标识（Sourcegraph SCIP 的 `pkg::path::Symbol` 思路）：

```
唯一名数：990 → 1,101（限定后）
```

**修订后排序：**

```
1  api\run_manager.py          0.04987   195行  17符号  被引 68
2  api\sse.py                  0.01560    62行   3符号  被引  4
3  tests\test_core.py          0.01176  6101行 345符号  被引 31
4  tool_runtime.py             0.01070   146行   9符号  被引 11
5  runtime_paths.py            0.01045   199行  29符号  被引 34
6  session_store.py            0.00553  1014行  54符号  被引 13
7  resilience.py               0.00429    72行   8符号  被引  5
8  paper_artifacts.py          0.00422   890行  36符号  被引 15
9  paper_store.py              0.00391  1013行  36符号  被引 11
```

**`api/run_manager.py` 排第一是合理的**——195 行、被 68 个文件引用，是典型的架构枢纽（运行任务管理）。`tool_runtime.py`（工具执行边界）、`session_store.py`、`paper_store.py` 紧随其后，与该项目简历描述的"29 工具 Schema 化注册 / 权限边界"一致。

### 3.4 但仍有问题：测试文件排第三

`tests/test_core.py` 仍在前三。原因：它有 345 个符号，且被大量测试文件引用。

**这引出缺陷二的解法方向：重要度必须区分「生产重要度」与「测试耦合度」。** 测试文件之间的互相引用不应抬高其架构地位。

处理方案（待 M0 实现）：
- 计算 PR 时**排除测试文件之间的边**（测试→测试的引用不参与生产重要度传播）
- 或者：分层计算——生产图与测试图分开，测试文件的分值单独展示为"测试覆盖集中区"

**这是 v0.2 未考虑的问题，需在 M0 补上。**

## 四、缺陷二 · 入口点过宽

### 4.1 现象

第一版用"文件里有 `__main__` 守卫"作为入口点信号，结果：

```
入口点识别: 54 个
  api_worker.py       (__main__ 守卫)
  mcp_server.py       (__main__ 守卫)
  paper_store.py      (__main__ 守卫)    ← 这是存储模块，不是入口
  pdf_reader.py       (__main__ 守卫)    ← 这是读取模块，不是入口
  research_agent.py   (__main__ 守卫)
  api\app.py          (文件名规律)
  + 22 个 scripts/*
  + 25 个 tests/*
```

**召回率 100%，精确率约 11%（6/54 算应用入口）。**

这直接违反 v0.2 §5.5 的硬门槛——"入口点召回率 100%"，但**没有配套的精确率指标**，导致实现者只优化召回。

### 4.2 根因

`if __name__ == "__main__"` 是**可执行脚本标记**，不是**应用入口标记**。项目里 22 个 scripts 和 25 个 tests 都有它。

### 4.3 修订：入口点分两级

| 级别 | 判据 | 输出 |
|---|---|---|
| **应用入口** | 文件名规律（`main`/`app`/`server`/`cli`）+ 框架注册（FastAPI app / Flask app / argparse with subcommands）+ 被其他生产模块导入 | L1 主入口（通常 1–3 个） |
| **脚本入口** | 有 `__main__` 守卫，但在 `scripts/` `tests/` `evals/` `tools/` 下 | 折叠为"辅助脚本 N 个"，不逐个列出 |

**L1 输出应只展示应用入口**，脚本入口作为一行统计。

**同时 v0.2 §5.5 的指标表需补一条：入口点精确率 ≥ 0.9。**

## 五、缺陷三 · 未解析调用未分类

### 5.1 数据

```
调用总数        17,566
跨文件边        2,360
未解析         15,206  (86.6%)
```

单看 86.6% 像是解析器失败。**但按被调用名 Top30 拆开后，结论完全不同**：

| 类别 | 代表 | 次数 | 占比 | 性质 |
|---|---|---|---|---|
| **内置 / 方法调用** | `get` 2229、`str` 1120、`len` 529、`append` 513、`strip` 325、`join` 253 | ~11,000 | 55% | **正确的不该解析**——是 `dict.get`、`str()` |
| **测试断言** | `assertEqual` 840、`assertIn` 242、`assertTrue` 138 | 1,220 | 7% | 测试专用 |
| **第三方库** | `Path` 188、`dumps` 90、`TemporaryDirectory` 80、`perf_counter` 77 | ~500 | 12% | 真实外部依赖 |
| **真正未解析的项目内调用** | 剩余 | ~2,500 | 12% | **解析器需改进部分** |

### 5.2 结论与修订

**86.6% 里大部分是"正确的不该解析"。** v2 原型已实现四分类，分布如下：

| 类别 | 次数 | 占比 | 处置 |
|---|---|---|---|
| builtin（内置/方法） | 8,703 | 49.9% | 不入图 |
| cross_file（跨文件已解析） | 830 | 4.8% | **入图** |
| local（同文件） | 2,051 | 11.8% | 同文件，不入跨文件边 |
| external（第三方库） | 2,044 | 11.7% | 入图但标 external，不参与项目内重要度 |
| test_helper（测试断言） | 1,468 | 8.4% | 不入生产图 |
| module_level | 119 | 0.7% | 无调用者归属，忽略 |
| unresolved | 2,234 | 12.8% | **解析器需改进部分** |

**项目内解析率 = (2,051 + 830) / 17,449 = 16.5%**（其余为不该解析的调用）。

### 5.3 unresolved 2,234 的细分：纯 AST 的天花板

进一步拆解 2,234 条未解析：

**① 1,084 条是标准库方法**（未识别为 import 的类成员）：

```
casefold  56    now       40    isoformat  38    fetchall  33
commit    29    fetchone  29    connect    22    fromkeys  16
```

根因：`from datetime import datetime` 导入的是**类**，而 `datetime.now()` 的 `now` 是**类的属性**，不在 import 名列表里。**纯 AST 看不到"类的方法"。**

**② 256 条是同名多定义（歧义）**：

```
create  29    start  21    list_papers  20    tokenize  18    step  13
```

`create` 在 29 处被调用，但项目内有多个 `create` 定义——**纯 AST 无法判断调用的是哪一个**。

**③ 剩余约 894 条**为其他第三方库方法与动态调用（`getattr` 派生的调用等）。

**关键结论：纯 AST 符号解析的天花板约在 60–70%**（按项目内调用计）。剩余部分需要：

| 手段 | 能解决 | 成本 |
|---|---|---|
| 补全标准库方法表 | ①类，约 +1,084 | 低（一次性硬编码常用集合） |
| 启发式消歧（同文件优先、import 路径匹配） | ②类，约 +150 | 中 |
| **真实类型信息**（`ts-morph` / `mypy` / LSP） | ②类剩余 + ③的大部分 | 高（跨语言子进程） |

**这直接回答了 v0.2 §4.2 的一个问题**：`ts-morph` 到底什么时候值得引入？

**答：M0 阶段不需要。** 因为：
1. 排序质量已经可用——Top12 全是真实架构组件，没有一个 `get`/`append` 噪音
2. 跨文件边 830 条已足够支撑 PageRank 与影响面分析
3. 未解析的 12.8% 主要是标准库方法，**补一张方法表比引入类型系统划算得多**

**M4 引入 ts-morph 的真正理由仍然是跨语言契约比对**（§4.2 的原判断成立），而不是提升 Python 侧的符号解析率。

### 7.1 一个容易犯的错：符号级排序必须用限定名做边

修订过程中踩到第二个坑，比第一个更隐蔽：

**错误做法**：按符号名统计入度，再分配给同名定义。

```python
# 错：get 在 8 个文件里各定义一次
for caller, callee in calls:
    for s in all_symbols:
        if s.name == callee:      # ← 8 个都匹配
            sym_in[s.qname].add(caller_file)
```

结果：8 个 `get` **每个都拿到全部入度**（85 个文件），排序依然是 `get` 霸榜。

**正确做法**：只统计**项目内唯一定义**的符号的入度；歧义符号（`create`/`start`/`tokenize`）暂不参与符号级排序，但**仍参与文件级排序**（文件级只需要知道"有调用发生"，不需要知道调用的是谁）。

## 九、对项目定位的影响

实测下来，有三条结论值得回到 v0.2 主文档：

**① 性能不是任何一层的约束。** L1 + L2 端到端 < 1s，比 v0.2 设定的 L1<30s / L2<3min 有 30–180 倍余量。**因此所有优化决策应优先选"质量更好"的那一侧**（如删除局部近似折中）。

**② 真实项目会暴露模拟数据测不出的问题。** 本次三个缺陷全部只在真实代码上出现。特别是缺陷一——**符号重名率 18% 这个事实，模拟数据永远测不出来**。因此 M0 的验收必须在真实项目上跑，不能只靠合成用例。

**③ 排除规则是索引层的一等功能，不是配置项。** `runtime/` 占 80% 行数。如果不排除，排序完全失真。**这应该进 M0 的第一批实现，且必须有针对真实项目的测试。**
