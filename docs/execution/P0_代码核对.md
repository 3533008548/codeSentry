## 一、当前能力与真实命令行为

| 对象 | P0开始时的事实 | 不能据此声称的能力 |
|---|---|---|
| `onboard` | 调用索引并输出L1/L2或JSON；Python/TS/TSX分派已存在 | 受控工具链、环境完整还原、解析完整或新P@10目标已达标 |
| `scan` | 仅构建索引并输出占位说明；JSON仍为索引；未实现Finding检查器、diff或门禁 | 退出0不是审查通过，不能作CI合格判定 |
| `index` | 全量刷新构建后调用保存；默认用户索引目录，可显式导出项目 | 当前未检查保存返回值，打印“已保存”不证明落盘成功 |
| `status` | 加载已有快照，再构建索引并比较源码哈希；索引缺失返回1 | 不只是读取快照，也可能更新解析缓存；代码陈旧时同样返回0，不是CI新鲜度门槛 |
| `init` | 写默认policy；已有文件默认拒绝覆盖，force可覆盖 | policy可解析不等于规则已执行或策略已获准入 |
| 解析缓存 | 当前`CACHE_VERSION=2`；按源码内容命中，符号解析/排序每次重算 | 尚无环境、工具链及配置依赖身份 |
| 索引快照 | 当前`INDEX_VERSION=2`；保存摘要与源码哈希 | 不覆盖配置/工具链变化或当前扫描中的源快照变化 |
| 旧导航验收 | TopK比例实际是命中/GT覆盖；性能只计构建；最终主要依赖索引自洽判定退出码 | 不能代替阅读顺序P@10、磁盘位置、解析完整性、实际输出耗时与入口指标 |

这些是静态代码核对结果，不是本次实际命令/质量测试结果；工具自身测试及环境版本由P0基线主记录另行留证。

## 二、P1差距及优先级

| 优先级 | 差距 | 代码依据与建议 |
|---|---|---|
| 先处理 | 工具来源与注入边界 | TS仅从目标根/父目录找`node_modules/typescript`，Node继承宿主环境并设置NODE_PATH。需要改用显式受控工具链，清除目标可执行配置/注入路径，运行前核对身份；受控工具不可用就明确未解析 |
| 先处理 | 子项目环境画像 | 当前无environment模块；frontend配置/锁文件、声明和实际工具状态未分开。P1先以只读文本发现建薄契约，不运行目标配置或插件 |
| 同步修复 | 作用域与绑定 | 现有限定名未包含完整词法作用域；同名/目录猜测可标为cross_file。需要完整身份、接收者/导入/遮蔽信息与确定/猜测分层 |
| 同步修复 | builtin分类 | 即使采用备份实现，方法名大表仍不能证明内置来源；`get/start`等不能只按叶子名排除出分母。只在绑定来源可证实时分类 |
| 同步修复 | 失败完整性 | 原builder仅在异常抛出时计parse_failures；未知语言空结果可被当成功缓存，读取失败可能跳过。须保留失败文件、原因与重试资格 |
| 同步修复 | 缓存恢复与迁移 | 旧缓存不含完整环境输入。按语法/配置解析依赖区分指纹，版本不兼容作废；环境恢复后源码不变也重试 |
| 输出前完成 | 新验收口径 | P@10与Recall分开、入口独立标签、空/未知/不足10不通过、输出位置和L1/L2分别计时；GT不足不能由程序猜裁决 |
| 输出前完成 | 落盘及状态 | IndexStore.save未建父目录，失败返回False但CLI忽略；需要可靠创建/原子保存与明确失败状态。status的陈旧含义须与JSON/退出码约定一致 |

静态分析也需要有界文件、解析时间及进程回收；这不等于已经具备目标代码执行沙箱。当前无execution/runner，运行目标依赖、测试收集和目标代码仍须等P2B相应验收。

## 三、可复用备份与最小闭包

已定位本地备份：`.venv/task-backups/plan-only-20261023-223619/`。其manifest列明撤回文件；备份位于忽略目录，只有在重新审阅、纳入当前契约并重测后才可复用，不是新的验收证据。

| 组 | 可复用文件 | 依赖/作用 |
|---|---|---|
| 符号数据 | `codesentry/core/symbol.py` | 新增完整绑定上下文、导出可见性与确定性标记，需与下列解析/解析关系一起使用 |
| 语言解析 | `codesentry/parsers/python_parser.py`、`ts_parser.py`、`_ts_extract.js` | 作用域身份、重复定义、遮蔽/导入/调用归属及语法失败标记；JS脚本与嵌入脚本须同步 |
| 图与构建 | `codesentry/index/resolver.py`、`builder.py` | 仅确定边进入图、影响面和排序；精确导入与猜测分开；失败不作为成功空缓存 |
| schema迁移 | `codesentry/index/cache.py`、`store.py` | 备份分别升到CACHE_VERSION=4与INDEX_VERSION=3；只含schema/语义迁移，不含完整环境指纹 |
| 输出 | `codesentry/output/report.py` | 确定绑定率分母及启发式数量，与新resolver输出匹配 |
| 导航指标 | `evals/metrics.py`、`m0_acceptance.py` | P@K/Recall、目录口径、严格GT匹配、完整性与非零退出；不依赖P3 Finding或新fingerprint API |
| 回归用例 | `tests/test_parsers.py`、`test_resolver.py`、`test_report.py`、`test_metrics.py`、`test_acceptance.py` | 对应上述接口；TS测试需明确可信工具路径，否则会skip，不能把跳过算TS已验收 |

不要整文件恢复`codesentry/core/__init__.py`：备份在此导出P3的Finding验证/指纹API，而当前P1不应同时恢复这些实现。P1所需symbol接口可直接从core.symbol导入。

## 四、备份不能直接补齐的契约

1. 备份TS仍从目标项目查找工具，复制宿主环境并追加NODE_PATH，也会在启动时改写包内`_ts_extract.js`。它不是受控工具链实现，复用前必须收紧，不能直接对目标仓库启用旧启动路径。
2. 备份调用图已分层，导入图仅输出精确边；配置别名、类型/运行依赖区分、可解释的未知导入仍需补充或明确不支持，不得宣称完整模块解析。
3. 备份builder修复了失败空缓存，但未提供全部环境/配置身份、结构化失败原因和完整读取/快照一致性模型。
4. 备份验收仅以“构建+L1/L2渲染合计<30秒”为更严格代理，不是技术稿要求的L1<30秒/L2<3分钟分别测量；没有入口独立金标的召回/精确率验收。
5. 备份精确率/Recall helper是测量基础，不提供新人工标签、封存隔离或真实理解任务答案。备份中的历史测试通过数和两项目分数不能沿用为当前结果。

## 五、建议实施顺序与阶段边界

1. P0冻结源码/配置/标签候选及统计定义，记录已知未知；保留当前文档差异。
2. P1.1/P1.2先建环境与受控工具链薄接口，确保不加载目标工具；同时准备可复用解析/图闭包。
3. 复用并复核符号/解析/图/失败恢复用例，补builtin分类、配置/工具链身份及状态报告。
4. 更新新导航验收、单层时延与入口金标处理；在固定dev范围运行，再解释失败，不为提高分数修改标签或排除策略。
5. Finding可信凭据、完整证据指纹、批准基线和门禁状态属于P3；本轮P1不顺带恢复。真实目标代码与候选规则运行能力属于P2B及后续，不以静态分析替代隔离验收。

目前未发现阻止P0完成的代码读取问题。P1正式验收仍取决于受控工具就绪、标签未知项裁决、完整解析与指标实测；本记录不能把这些未知标为已解决。
