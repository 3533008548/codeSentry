## 先确定要完成的接手任务

用户已于2026-10-27确认首轮按“整体接手”验收：说明主要模块分工、找到启动位置，并沿一条事先选定的主要流程解释数据如何流动。v2草稿已写入这个任务范围与关键文件判断原则；v1空白任务版本保留。这个确认不是文件标签批准；具体主要流程与部署方式仍须在标文件前填写并固定。

在标文件前，先填写草稿 `task`：

- `prompt`：整体接手问题已预填；在 `main_flow` 补充流程名称、触发动作、预期结果，不在看到排名或得分后挑流程。
- `reading_key_definition`：什么情况下算关键文件。例如，缺少它会使该任务的启动说明、模块关系或指定流程解释出现关键遗漏；文件复杂或排名高不自动算关键。
- `deployment_context`：本次考察哪种启动/部署方式。浏览器、服务端、桌面主进程可以有不同入口；无法读取的配置和不支持的语义保留未知。
- `id`：任务版本标识。任务或范围改变时另建版本，保留已有记录。

## 在本地核对文件

使用[本地工作台](http://127.0.0.1:8765)读取已确认范围内的代码。不需要为标注放开隐私文件，也不需要运行目标项目。草稿的完整清单包含不参与排序的文件，`ranking_scope` 保留原有适用范围；不能为提高得分将文件移出分母。

| 字段 | 填写方式 |
|---|---|
| `reading_key` | `null`：尚未判断；`true`：对已固定任务关键；`false`：人工核对后不关键。文档没写到不等于 false。 |
| `entry_roles` | `null`：入口情况未知；`[]`：核对后没有该任务的入口角色；其余填写下面的角色，可以多项。 |
| `evidence` | 写依据的文件、已确认行号与理由。不确定行号就留未知，不默认第1行；不要粘贴隐私内容。 |
| `note` | 歧义、缺失声明、不适用条件或需另一人复核的问题。 |

| 角色 | 判断的问题 |
|---|---|
| `process` | 外部启动或加载声明指向哪里？它是进程启动/加载目标吗？ |
| `mount` | 界面在哪里真正挂载到页面或窗口？ |
| `bridge` | 哪个文件提供跨环境/进程的桥接上下文？ |
| `assembly` | 哪个文件负责创建应用、注册路由或组装组件？ |
| `candidate` | 只有名称或其他尚不充分的入口线索吗？ |

应用入口指标只合并 `process` 和 `mount` 文件。工厂、路由注册、名为 main/App 的文件不能只凭名称算进程入口；关键文件也不一定是入口。确实不能判断时保留未知，不强迫凑数。

## 留下审阅依据

填写 `reviewer` 的身份、日期、核对方法与分歧。范围确认只是允许本地读取，不是对关键文件或入口标签的批准。工具推荐、模型回答和结构反例通过都不能代替独立人工核对。

草稿填完后仍是草稿：现有工具只验证结构，不提供“改个 status 就通过”的捷径。正式评分前还要重新校验源码、配置、权限和任务版本，并完成独立裁决。原 v1 合同与旧 GT 保留，不用新任务追认旧成绩。

草稿绑定的是冻结清单，生成时没有重新读取源码，`source_snapshot_revalidated=false`。文件可能已改变；当前受限文件仍不得访问。本地导出副本不随工作台撤销自动删除，按现行权限保管，不能发给模型或恢复旧授权。
