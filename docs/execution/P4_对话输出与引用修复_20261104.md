# P4 对话输出与引用修复

日期：2026-11-04。对应技术定稿修订十八 §3.5.2。

## 现象与已知范围

用户在项目带学中连续两次收到“模型回答格式或引用不完整，本次未发布，请重新发送”。只读检查确认两轮状态均为failed。旧实现把响应空白、截断、JSON/字段错误、引用越界或不匹配合并成相同提示；未保存失败原始响应，因此无法认定这两次具体属于哪一类，也不能据此推断密钥或模型质量问题。

旧实现另有可复现的兼容问题：将`function_call:null`误认为实际函数调用；发送JSON模式请求时，历史assistant内容却使用Markdown正文。引用还要求模型同时生成准确路径、绝对行号和完全一致的原文，增加可避免的生成失败点。

## 修改

- 每个本轮允许发送的片段由服务端附上`source_id`，例如S1。模型只需返回`{"source_id":"S1"}`，服务端从该片段生成路径、完整片段起止行、原文及完整文件摘要。引用指向取材片段，不是证明某个论断或运行行为正确。
- 仍严格拒绝未知编号、额外引用字段和越范围引用；兼容旧路径/行号/quote格式，但不放宽原文匹配。敏感内容、权限撤销、源码漂移、迟到响应及取消仍走原检查。
- 历史assistant回答以合法JSON节选携带，旧片段编号不进入后续引用；提示词要求简洁、完整结束，输出上限仍为2048token。
- 错误分别说明空白、输出上限、JSON、正文/追问字段、引用来源/范围/原文、工具调用和供应商响应问题。提示只来自固定文案，不回显供应商原始内容；`function_call:null`按未调用处理，非空调用继续拒绝。
- 不自动重试、不增加预算或扩大文件权限；未发布响应仍不存正文。旧失败记录不改写，手动重新提问后使用新协议。

DeepSeek官方说明JSON模式也可能返回仅含空格的内容，即使finish_reason为stop；输出上限可能截断JSON。此资料支持新增对应诊断，不能反推用户两次旧响应的具体原因。见[官方JSON模式说明](https://api-docs.deepseek.com/guides/json_mode/)和[Chat Completions接口](https://api-docs.deepseek.com/api/create-chat-completion/)。本轮未采用文档举例中的自动重试。
