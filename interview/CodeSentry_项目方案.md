# CodeSentry · 代码审查 Agent 项目方案

> 定位：项目上线前的安全阀门 —— 在合并前发现逻辑混乱、接口不一致、规范偏离，并给出可验证的结论
> 版本：v1.0 方案草案 · 2026-10-19

---

## 一、命名

**CodeSentry**（代码哨兵）

选它的理由：语义直白——"上线前的哨兵"，面试官一听就知道是工程门禁而非玩具；且与 `Sentry` 这个开发者熟悉的错误监控品牌有语义联想，容易记住。备选：`Gatekeeper`（过于通用）、`Precheck`、`LintWarden`。

**项目一句话介绍**（面试用）：

> 一个本地优先的代码审查 Agent：用确定性 AST 分析 + LLM 语义审查检查接口一致性、逻辑复杂度与规范偏离，输出可定位到行号的结论，并通过发布门禁阻断不合规改动。

---

## 二、为什么做这个项目

### 2.1 定位选择

在调研过几个候选方向后选代码审查，理由是三重：

**其一，切入 Coding Agent 这个更大的赛道。** 完整的编码 Agent（IDE 内嵌补全）个人无法复现，但**代码审查与规范校验**是其中输入静态、输出可控、风险可控的子任务，适合独立完成。

**其二，形成自举飞轮。** 自己的两个项目（41.6k 行 Python、19.1k 行 TypeScript）就是第一批被审查对象。审查他人代码以理解规范，反过来审查自己的代码以真正改进它们——这是其他方向给不了的价值。

**其三，复用率高。** 现有项目已有的评测框架、脱敏机制、运行事件契约、工具执行边界可整体迁移，不是从零开始。

### 2.2 第一版不做代码生成

代码审查与代码生成是两个难度阶梯。生成需要模型对整个仓库有正确的抽象理解，而审查是局部的、可枚举的。

更重要的是**可验证性差异**：

| | 输出能否自动判定对错 |
|---|---|
| 审查结论 | ✅ 可——确定性规则精确匹配，LLM 结论可对标注集算准召|
| 生成代码 | ❌ 难——没有标准答案 |

第一版把审查做到"能作为 CI 门禁"，比"能生成代码但说不清对错"更有工程说服力。生成放在第二阶段，且绑定在很窄的场景（见 §6）。

## 三、已获取的审查素材（实测数据）

以下均为对现有项目的真实测量结果，直接作为检查器的验证基线。

### 3.1 规模失衡

| 文件 | 行数 | 问题 |
|---|---|---|
| `frontend/src/App.tsx` | 2,582 | 单文件承载整个工作台界面 |
| `frontend/src/MarkdownContent.tsx` | 12 | 对比 216倍差距 |
| `tests/test_core.py` | 6,087 | 测试集中堆积 |
| `research_agent.py` | 1,290 | 入口层过重 |

**结论**：项目存在明确的"逻辑混乱"信号——单文件职责过载、组件粒度失控。这正是产品要检出的首要问题。

### 3.2 超长函数（>80 行，共 38 个）

| 行数 | 函数 | 文件 |
|---|---|---|
| 793 | `build_graph` | `graph_builder.py` |
| 508 | `_raw_tool_schemas` | `tool_schemas.py` |
| 390 | `run` | `research_orchestrator.py` |
| 323 | `llm_node` | `graph_builder.py` |
| 290 | `step` | `research_agent.py` |
| 230 | `verify_node` | `graph_builder.py` |

**结论**：`build_graph` 793 行是一个可被确定性检出的高危信号（单函数承载完整图编排 + 路由 + 工具执行）。

### 3.3 跨语言接口契约

已存在一份前后端事件类型契约：

- 后端 `run_contract.py`：`SSE_EVENT_TYPES = {status, token, tool, done, error}`
- 前端 `types.ts`：定义了 `MessageRole` / `RunKind` / `DailyRunKind` / `DailyPaperStatus` / `ResearchScope` / `BadcaseCategory` 等类型

**待审查点**：前端类型定义与后端契约是否严格对齐。这类"人工维护两份定义"的模式是接口不一致的高发区，也是产品的核心用例。

### 3.4 真实修复历史（评测集来源）

`research_agent` 有 8 个可追溯的 fix 提交，构成 bug-reintroduction 评测集的素材：

```
ad36172  tokenize 兼容两种分词器形态，分块守卫不再静默失效
a5b3c4b  离线质量门控在无模型缓存 / Python 3.11 环境下失败
45481ff  recover deep research from model timeouts
42cba6d  preserve daily run resume semantics
f212145  bound retrieval for engineering answers
```

其中 `ad36172`（分块守卫**静默失效**）最具代表性——这类 bug 不报错、不崩溃，只是保护机制悄悄不起作用，人工 review 极易漏掉。**这正是 LLM 审查优于人工的地方，也是产品价值的最佳证明材料。**

## 四、架构设计

```
CodeSentry/
├── analyzers/                     # 确定性检查器（AST / 静态分析，可单测）
│   ├── interface_contract.py      # 跨语言接口字段比对（Python schema ↔ TS types）
│   ├── complexity.py              # 函数/文件规模、圈复杂度、嵌套深度
│   ├── naming.py                  # 命名一致性（snake_case / camelCase / 语义后缀）
│   ├── dead_code.py               # 不可达分支、未使用导出、循环依赖
│   └── silent_failure.py          # 静默失效模式（如 except: pass 掩盖保护逻辑）
│
├── llm_reviewer.py                # 语义审查：只接受结构化、可定位的结论
│   ├── scope.py                   # 分块策略：按符号边界切分，控制上下文
│   ├── protocol.py                # 强制输出 schema：{file, line, severity, rule, reason, evidence}
│   └── verify.py                  # 结论回验：行号是否存在、证据是否可复现
│
├── gates/                         # 发布门禁（可作为 CI 阻断）
│   ├── policy.yaml                # 规则集与阈值配置
│   ├── gate.py                    # 判定逻辑：阻断 / 警告 / 通过
│   └── baseline.py                # 基线对比：只对新增问题阻断（避免存量淹没）
│
├── report/                        # 报告生成
│   ├── terminal.py                # 终端输出
│   └── web/                       # Web 报告（补前端能力）
│
├── evals/                         # 评测与回归（迁移自 research_agent）
│   ├── cases/                     # bug-reintroduction 用例集
│   ├── gate_eval.py               # 精确率 / 召回率门禁
│   └── reports/                   # 历史对比
│
└── cli.py                         # 入口：codesentry scan <path>
```

### 4.1 三层检查体系

核心设计取舍：**不让 LLM 自由发挥找问题，而是让它在固定规则集上给出可验证的判定。**

| 层 | 检查内容 | 手段 | 可自动验证 |
|---|---|---|---|
| **结构层** | 接口一致性、命名、规模失衡、重复代码、依赖环 | AST + 静态分析 | ✅ 精确匹配，零误报前提 |
| **语义层** | 逻辑混乱、职责不清、边界条件缺失、静默失效 | LLM 审查，强制输出行号 + 理由 + 证据 | ⚠️ 需标注集校准准召 |
| **门禁层** | 提交前是否满足阈值 | 规则配置 + 基线对比 | ✅ 完全可判定 |

**结构层必须自研 AST 分析，不能全靠 LLM。** 这是项目的技术护城河：LLM 会看漏、会幻觉、每次结果不稳定；确定性分析不会，而且只有它能支撑"作为上线门禁"这个定位。

### 4.2 关键设计：基线对比机制

存量项目第一次扫描必然报出几百条问题，直接阻断无法落地。设计：

1. 首次运行生成 `baseline.json`，记录全部存量问题
2. 后续审查只对**新增问题**阻断（存量可配置为"警告"或"豁免"）
3. 存量问题作为**待偿债务**可视化，随版本逐步清零

这让 Agent 能在真实存量项目上落地，而不是只能在理想代码上跑。

### 4.3 语义审查的输出协议

强制 LLM 输出结构化结论，禁止自由文本：

```json
{
  "file": "graph_builder.py",
  "line": 938,
  "symbol": "build_graph",
  "rule": "complexity.function_length",
  "severity": "medium",
  "reason": "函数承担图定义、路由决策与工具执行三重职责",
  "evidence": "add_node / add_conditional_edges / tool_node 均在同一函数内",
  "suggestion": "拆分构图、路由表、工具执行三部分",
  "confidence": 0.9
}
```

`verify.py` 负责回验：**行号是否存在、evidence 里的符号是否真的出现在该位置**。回验不通过的结论直接丢弃——这是防止 LLM 幻觉污染门禁的最后一道闸。

## 五、评测集：bug-reintroduction

这是本项目区别于"接个API 让 LLM 点评"的核心，也是最难被抄走的部分。

### 5.1 方法

从 git 历史反向构造用例：

```
1. 取一个 fix 提交（如 ad36172）
2. checkout 到其父提交 —— 即"有 bug"的代码状态
3. 以 commit message + 代码 diff 作为标准答案（label）
4. 让 Agent 审查该状态，检查是否能检出该问题
5. 统计精确率 / 召回率，纳入 release_gate
```

### 5.2 用例来源

| 来源 | 数量 | 说明 |
|---|---|---|
| `research_agent` fix 提交 | 8 | 真实 bug，有标准答案 |
| 规模失衡样本 | 3 | `App.tsx` 2,582 行、`build_graph` 793 行等 |
| 契约不一致样本 | 待构造 | 人工在 TS types 中增删字段验证能否检出 |
| 合成用例 | 待构造 | 静默失效、循环依赖、命名漂移 |

### 5.3 门禁指标

```
精确率 precision ≥ 0.85    # 误报是门禁产品的生命线
召回率 recall    ≥ 0.70    # 漏报可接受但不能过低
单文件审查耗时   < 30s
```

**误报比漏报更致命**——一个满屏误报的审查工具，用户一周内就会弃用。所以精确率门槛定得高，且 LLM 结论必须过 `verify.py` 回验。

## 六、第二阶段：受约束的代码生成

第一版验证后再做，且场景收窄到：

```
审查发现问题 → 生成修复补丁 → 补丁必须通过
  1. analyzers 全部检查器（不得引入新问题）
  2. 项目测试套件
  3. release_gate
→ 全部通过才允许写入，人工确认后落盘
```

设计要点：**模型有产出权，但产出必须过闸门才能生效。** 这与 Knowledge Loop 里"写入必须经预览确认"是同一条工程哲学，可在面试时作为连贯的能力线讲述——模型被允许做事，但工程约束决定了它能留下什么。

## 九、差异化与面试价值

### 9.1 相对同类项目的差异

市面上的代码审查工具大多落在两端：纯静态检查（AST linter，不懂语义）或纯 LLM 点评（能读懂但不可靠、不能当门禁）。

本项目的定位是**用确定性方法兜住可靠性，用语义方法补上静态分析看不到的部分，再用评测把两者都量化**。

### 9.2 面试可讲的三个点

**其一，可验证性意识。** 大多数同类项目只能演示"AI 指出问题"，本项目能回答"它的精确率和召回率是多少，测试集怎么来的"——bug-reintroduction 评测是客观的、有标准答案的。

**其二，误报治理。** 主动讨论"审查工具的误报比漏报更致命"，并给出基线对比机制解决存量问题落地问题。这是产品思维，不只是技术。

**其三，模型产出受工程约束。** 生成代码必须过全部门禁才能落盘——与Knowledge Loop 的写入确认是同一条能力线，可以讲成"我 consistently 让模型的产出被工程约束住"。

### 9.3 目标 JD 对应

| JD 要求 | 本项目对应 |
|---|---|
| Coding Agent / 代码智能 | 代码审查 + 受约束生成 |
| Agent 架构 | 多检查器编排、结论回验、门禁决策 |
| Tool Calling | 代码读取工具的注册与执行边界 |
| Context Engineering | 按符号边界分块，控制审查上下文 |
| 评测与质量门禁 | bug-reintroduction + release_gate |
| 安全合规 | 代码内容脱敏、敏感目录排除 |
| 全栈交付 | CLI + Web 报告 |
| Product Sense | 基线机制、误报治理 |

## 十、风险与应对

| 风险 | 应对 |
|---|---|
| LLM 审查误报高 | `verify.py` 行号与证据回验；结构层兜底；基线机制隔离存量 |
| 大文件审查超时 | 按符号边界分块；超长函数只审签名 + 关键路径 |
| 审查结果不稳定 | 结构层确定性；语义层固定 prompt + temperature=0；结论缓存 |
| 审查代码含密钥 | 迁移 `redact_known_secrets`，读取即脱敏 |
| 项目显得"只是 linter" | 语义层 + 受约束生成 + 评测体系构成三层差异 |
| 前端能力仍不足 | Web 报告必须做，含执行过程可视化 |

## 十一、下一步

建议直接从 **M1 + M2** 开始，因为这两个步骤的产出就能验证方向是否正确：

1. 写 `complexity.py`，跑在 `research_agent` 上——看能否自动报出 793 行的 `build_graph` 和 2,582 行的 `App.tsx`
2. 从 8 个 fix commit 构造首批 bug-reintroduction 用例，跑出第一组精确率/召回率

两步跑完即可判断这个方向是否值得投入。**如果确定性检查器在你自己的项目上就报不出有价值的问题，那说明产品假设有问题，应当重新定义而不是硬推。**
